Workflows ​

A workflow is a multi-step automation pipeline that runs on the server. Chain together LLM calls, data transformations, external API requests, delays, and conditional logic — all defined as version-controlled TOML config. Primitive executes the steps in sequence, persists every step's input and output, and surfaces the run's status to your app, the CLI, and the Admin Console. The same workflow can be invoked from your app, on a schedule, or by an inbound webhook — the definition doesn't care who triggered it.

Defining a Workflow ​

toml
# config/workflows/welcome-email.toml
[workflow]
key = "welcome-email"
name = "Welcome Email Workflow"
accessRule = "true"   # any app member may start it; see Controlling Access to Workflows

[[steps]]
id = "generate-message"
kind = "llm.chat"
model = "gpt-4o-mini"
temperature = 0.7
saveAs = "message"

[[steps.messages]]
role = "system"
content = "You write friendly, concise welcome emails."

[[steps.messages]]
role = "user"
content = "Write a welcome email for {{ input.userName }}."

[[steps]]
id = "send-email"
kind = "email.send"
to = "{{ input.userEmail }}"
subject = "Welcome!"
htmlBody = "{{ steps.generate-message.content }}"

Push it to the server:

bash
primitive config push

config push creates and updates the workflow's active configuration in place. A pushed workflow is in service immediately — availability is not something the file declares.

To stop a running workflow without a checkout, use primitive workflows disable <workflow-id-or-key> (and enable to put it back). That is an operational switch, not configuration: it writes the server-owned status, which is deliberately not a TOML key, so a later config push cannot re-enable it and config diff reports the workflow as "inactive; configuration unchanged" rather than as drift.

Retiring a workflow for good is a third verb, primitive workflows archive <workflow-id-or-key>. It is the delete lifecycle rather than availability: the definition row is kept so the workflow's runs, revisions, configurations and test cases keep resolving what they point at, but new runs are refused, enable refuses it, and there is no un-archive. The archived row goes on holding its workflowKey; reclaim it by removing workflows/<key>.toml and running a confirmed primitive config push --prune, which hard-deletes the row and its cascade, then re-adding the file and pushing. Like every destructive command it confirms first and takes --yes/-y.

Steps ​

A workflow is a sequence of steps. Each step has an id (unique within the workflow) and a kind — what the step does — plus whatever configuration that kind needs. Steps run in order, and every step's output is recorded on the run and available to the steps after it.

A few kinds you'll reach for constantly:

KindPurpose
transformShape a value with the templated output field — typically the workflow's final result
llm.chat / prompt.executeLLM chat completion, or run a managed prompt
integration.callCall an external API via a configured integration
database.query / database.mutateRun registered database operations
email.sendSend an email

The full catalog — branching, delays, fan-out to child workflows, blob and analytics steps, and more — is in the Step Reference at the end of this page.

How Data Flows Through a Run ​

A run carries a single growing JSON context from the first step to the last:

  1. Every run starts with one JSON object — the input. It's the input passed to start() or runSync(), a webhook's (mapped) payload, or a cron trigger's configured input. If the workflow declares an inputSchema, the input is validated against it first. A value bound to a scalar input property is coerced to the declared type where that's safe — a number into a string field, a numeric string into a number or integer field, "true"/"false" into a boolean — so a templated value carried in as text lands as the right type. A value that can't convert (a non-numeric string into a number) fails the run with a clear type error. Set coerce = false on a property to opt it out.

  2. Steps read from the context through templates. A step has no implicit input argument. Just before it runs, the {{ ... }} expressions in its config strings are resolved against the run context — input.* plus the recorded output of every step that already ran — and the step executes with that filled-in config. An email step's to = "{{ input.userEmail }}" and an LLM message's content = "Summarize: {{ steps.fetch.body }}" are both reading the context this way.

  3. Every step's output is recorded. Whatever a step produces (always JSON) is stored on the run as steps.<id>. Give the step saveAs = "name" and the same value is also available as outputs.name — a stable alias later steps can use without depending on the step's id. The engine also stamps each object entry with a verdict — ok, the execution state ("succeeded", "failed" or "skipped") with its matching succeeded / failed / skipped booleans, plus errored when relevant — that later steps can branch on; arrays and primitives pass through unstamped.

  4. The run's final output. When the last step finishes, the workflow's result is outputs.output — the value saved by a step with saveAs = "output" — or the whole outputs map if no step used that name. The standard pattern is to end with a transform step that sets saveAs = "output" and explicitly shapes the return value. The full step-by-step record (each step's input and output) stays on the run for inspection.

Template syntax, filters, and built-in helpers are covered in the Template Reference at the end of this page.

Conditional Execution ​

Skip a step when a CEL expression evaluates falsy. runIf is parsed as CEL directly — do not wrap it in {{ }}:

toml
[[steps]]
id = "premium-feature"
kind = "llm.chat"
runIf = "input.isPremium && steps.lookup.ok"
model = "gpt-4o-mini"

[[steps.messages]]
role = "user"
content = "Generate premium content for {{ input.topic }}."

A condition reads the same run state a template does — input, selected, steps, outputs, meta, secrets and vars, plus iteration and the loop's binding names inside a forEach. vars is your app's full set of config vars, the same values {{ vars.KEY }} renders in step config, so a guard and a template read one shared snapshot — loaded once when the run starts, or once per batch for a forEach with concurrency above 1, where a var edited mid-run can reach one batch and not another. Reading a key your app doesn't have throws No such key: KEY — write 'KEY' in vars (or vars.?KEY) when the var may not be set yet.

Every object step output carries an engine-managed verdict: ok, the execution state — "succeeded", "failed" or "skipped" — and the succeeded / failed / skipped booleans that mirror it (plus errored: true when a failure was captured by continueOnError). The booleans are always present, so downstream runIf expressions can branch reliably on steps.fetch.succeeded, steps.fetch.failed or !steps.fetch.skipped without knowing whether the step ran. An array or primitive output passes through unstamped.

CEL optional types are enabled in every workflow context, so you can collapse multi-conjunct null guards: steps.fetch.?data.?items.orValue([]).size() > 0. One caution: comparing a .? path to a value with != is true when the path is absent — input.metadata.?userId != '' passes for input with no userId at all. For strings, lists, and maps, write "present and non-empty" as size(input.metadata.?userId) > 0 — size() is 0 for an absent path and for a present-but-null value; for numbers and booleans, use .hasValue().

When a step reads a value from an upstream step that can itself be skipped, guard the read with that step's verdict — a skipped step has no output key, so an unguarded read throws:

toml
[[steps]]
id = "summarize"
kind = "llm.chat"
runIf = "steps.fetch.succeeded && steps.fetch.output.count > 0"   # `succeeded` is false (never absent) when fetch skipped

Or, when the dependent has nothing to do at all without that upstream, list it in skipWhenSkipped so the dependent skips too:

toml
[[steps]]
id = "summarize"
kind = "llm.chat"
skipWhenSkipped = ["fetch"]   # if "fetch" was skipped, skip this step without evaluating runIf

The skip cascades — a step skipped this way will in turn skip its own skipWhenSkipped dependents. List only earlier step ids. A step that errored under continueOnError does not trigger the skip; only a genuinely skipped upstream does.

Reusable named guards ​

When the same condition appears in several runIf expressions — or a guard grows long enough that you'd rather name it than repeat it — define it once in a top-level [expr.cel] table and reference it by name as expr.<name>:

toml
[expr.cel]
isPremium = "input.plan == 'premium' && steps.account.ok"
withinQuota = "steps.usage.count < input.limit"

[[steps]]
id = "premium-feature"
kind = "llm.chat"
runIf = "expr.isPremium && expr.withinQuota"
model = "gpt-4o-mini"

A named guard is usable anywhere a step condition is — a step's runIf or a switch case's when — and the bracket form expr['isPremium'] works too. Definitions may reference each other (eligible = "expr.isPremium && expr.withinQuota") as long as the references form no cycle.

Each guard evaluates against the run's fixed state — input, steps, outputs, meta, secrets, and vars — so expr.isPremium means the same thing at every place it's referenced. It does not see a reference site's local bindings: a forEach item variable or iteration counter is out of scope inside a named guard. When a guard fails to evaluate, the error is reported under its name (expr.isPremium), not the expression text.

primitive config push validates the table before it uploads, and the server rejects the same problems with a 400: a reference to a name you never declared, a definition with an empty body, or a reference cycle. primitive config pull writes the [expr.cel] table back out, so definitions round-trip.

The Run Lifecycle ​

Every invocation creates a persistent workflow run. A run moves through queued → running → a terminal state (completed, failed, terminated, or skipped), and a run whose execution can no longer be resolved reports missing. Workflows that apply their results into local-first documents add two more states — apply_pending and apply_claimed — between the last step and completion (see Applying Results to Local Data). A run reads skipped only when it declared a run-scoped lock with onContention = "ignore" and lost the race — see Locks.

Each step's input and output is recorded on the run, so you can always reconstruct what happened — from the CLI, from your app, or in the Admin Console's run detail view. Runs look the same whether a user, a cron trigger, or a webhook started them.

The run record also carries executionStartedAt — when the run actually began executing, as distinct from startedAt (when it was requested) — plus queueDelayMs, the gap between the two. Both stay null while a run is still queued.

Invoking Workflows ​

Four ways to start a run, all hitting the same workflow definition:

InvocationUse for
Client call (async)User-initiated jobs your UI tracks: imports, report generation, enrichment
Client call (sync)Short, latency-sensitive calls: validation, lookups, webhook-style responses
Cron triggerAnything on a clock: digests, cleanup, periodic syncs

From Your App (Asynchronous) ​

Start a run, then track it by polling or by listening for status events:

ts
// Start a workflow; it runs in the background
const { runId, runKey } = await client.workflows.start({
  workflowKey: "welcome-email",
  input: { userName: "Alice", userEmail: "alice@example.com" },
});

// Check status
const status = await client.workflows.getStatus({ workflowKey: "welcome-email", runKey });

// List recent runs
const { items } = await client.workflows.listRuns({ workflowKey: "welcome-email", limit: 50 });
swift
// Start a workflow; it runs in the background
let started = try await client.workflows.start(
  workflowKey: "welcome-email",
  input: ["userName": "Alice", "userEmail": "alice@example.com"]
)
let runKey = started.runKey

// Check status
let status = try await client.workflows.getStatus(
  workflowKey: "welcome-email", runKey: runKey
)

// List recent runs
let runs = try await client.workflows.listRuns(
  options: ListWorkflowRunsOptions(workflowKey: "welcome-email", limit: 50)
)

getStatus returns status and, when complete, output. The status is always one of nine values, the same set everywhere the platform reports a run — getStatus, listRuns, terminate, the status events, and the CLI:

StatusMeaning
queuedAccepted, waiting to start executing.
runningExecuting.
apply_pendingServer-side work finished; waiting for your app's apply handler.
apply_claimedAn apply handler has claimed the run and is running it.
completedFinished successfully — terminal.
failedFinished with an error — terminal.
terminatedStopped before finishing (terminate, a sync-call timeout, or a disabled user) — terminal.
missingThe run's execution can no longer be resolved.
skippedDid not run: its declarative lock was held and the workflow declared onContention = "ignore" — terminal, and not a failure. skipReason says why (LOCK_CONTENTION).

Compare against these values directly: the server reconciles the run's state before answering, so there is nothing to normalize client-side. Reading a status never changes the run's recorded state, and a terminated run never later reads as completed.

One detail worth knowing when you poll: a run whose execution has just ended can briefly report running while the platform publishes its output, so status and output never contradict each other. Treat a non-terminal read as "not finished yet, keep polling" rather than proof the run is still executing — run.status on the same response already carries the recorded terminal status, and waitFor handles the window for you.

For live updates without polling, subscribe to status events:

typescript
client.on("workflowStatus", (event) => {
  if (event.status === "completed") console.log("Result:", event.output);
});
swift
// In a SwiftUI `.task`. The payload type names the event, so nothing else is
// needed to resolve the subscription; leaving the loop unsubscribes.
for await event in client.stream(for: WorkflowStatusEvent.self) {
  if event.status == "completed" { print("Result:", event.output ?? "") }
}

A third option: workflows.waitFor(runId) wraps the same status event in a single awaitable call, resolving once the run reaches a terminal state:

typescript
const { status, output, error } = await client.workflows.waitFor(runId);
if (status === "completed") {
  console.log("Result:", output);
} else if (status === "failed") {
  console.log("Run failed:", error);
}
swift
let result = try await client.workflows.waitFor(runId: runId)
if result.status == "completed" {
  print("Result:", result.output ?? "")
} else if result.status == "failed" {
  print("Run failed:", result.error ?? "")
}

It's event-driven, not polling, and resolves on every terminal outcome — including "failed" — rather than throwing. It fails only if the wait times out (default 15 minutes; a timeout of 0 disables it) or if runId doesn't resolve to a run.

From Your App (Synchronous) ​

For short, latency-sensitive workflows, opt the workflow into synchronous invocation by setting syncCallable = true in the workflow TOML and pushing it. Clients can then await the final result in one round-trip:

ts
const result = await client.workflows.runSync({
  workflowKey: "validate-coupon",
  input: { code },
  timeoutMs: 5000, // default 5000; server caps at 30000
});
// → { runId, runKey, status, output?, error?, run?, existing? }
// status: "completed" | "failed" | "terminated" | "timeout" | "apply_pending"
// Resolves for every terminal outcome — only transport errors reject.
if (result.status === "completed") {
  console.log(result.output);
}
swift
let result = try await client.workflows.runSync(
  workflowKey: "validate-coupon",
  input: ["code": code],
  timeout: 5 // seconds; default 5, server caps at 30
)
// RunSyncWorkflowResult: runId, runKey, status, output?, error?, run?, existing?
// status: "completed" | "failed" | "terminated" | "timeout" | "apply_pending"
// Resolves for every terminal outcome — only transport errors throw.
if result.status == "completed" {
  print(result.output ?? "")
}

The promise resolves for every terminal outcome; only network errors reject. Long-running workflows should use asynchronous start() instead.

A call that exceeds its timeout (default 5 seconds, capped at 30 by the server) resolves with status: "timeout" — and that ends the call, not necessarily the work. Execution isn't interrupted at the boundary, so writes from steps already in flight can still land; but the run's record is finalized as terminated before the envelope returns, and it never later becomes completed — so don't poll for it to finish. (getStatus tracks runs started with start(); a synchronous run's final state comes back in the envelope's run.) Treat the run as incomplete: check the state it was supposed to produce, and recover with idempotent writes so cleanup is safe even if a late step landed. To try again, call runSync with a new runKey — reusing the old one returns the terminated run instead of executing again. When knowing the final outcome matters more than latency, prefer start(): its run record reaches a real terminal status you can poll with getStatus.

A syncCallable workflow may declare a run-scoped lock: the lock is honored under run-sync and through workflow.call, just as it is on the durable path. Because every path shares one lock namespace, a durable run and a synchronous run of the same key serialize against each other — but a run never serializes against itself, so concurrent branches inside one run need concurrency = 1 or per-branch keys (see Locks).

Typed Invocations (Codegen) ​

Generated invoker factories are the default way application code invokes a workflow — reach for raw client.workflows calls with a string-literal key only when a workflow declares no schema to generate from. When a workflow declares an inputSchema / outputSchema, the CLI generates typed invocation wrappers from the workflow TOML in your config directory:

bash
primitive workflows codegen
bash
primitive workflows codegen --lang swift

Apps scaffolded from the starter templates run this automatically — the web template as part of pnpm codegen (which dev, build, and test all run), the iOS template from its build scripts — so generated invokers stay current with every build.

The command writes one generated file per workflow — <key>.generated.ts (default) or <key>.generated.swift (--lang swift) — to <config-dir>/workflows/generated/ by default (-o <dir> overrides). Each file declares the workflow's input and output types plus a factory that pins the workflow key, so the key can't drift from the types it was generated with:

ts
import { createCheckoutSession } from "./generated/create-checkout-session.generated";

const checkout = createCheckoutSession(client);
const res = await checkout.runSync({ input: { priceId: "price_123" } }); // input compile-checked
console.log(res.output?.checkoutUrl);                                    // output typed

const status = await checkout.getStatus({ runKey: "run-1" });            // status.output typed too
const ended = await checkout.terminate({ runKey: "run-1" });             // ended.output typed too

await checkout.cronTriggers.create({                                     // trigger's rootInput typed from the input schema
  triggerKey: "nightly-checkout",
  displayName: "Nightly Checkout",
  cron: "0 3 * * *",
  rootInput: { priceId: "price_123" },
});
swift
import JsBaoClient

let checkout = createCheckoutSession(client)
let res = try await checkout.runSync(input: CreateCheckoutSessionInput(priceId: "price_123")) // input type-checked
print(res.output?.checkoutUrl ?? "")                                                          // output typed

let status = try await checkout.getStatus(runKey: "run-1")  // status.output typed too
let ended = try await checkout.terminate(runKey: "run-1")   // ended.output typed too

try await checkout.cronTriggers.create(                     // trigger's workflow key pinned
    triggerKey: "nightly-checkout",
    displayName: "Nightly Checkout",
    cron: "0 3 * * *",
    rootInput: ["priceId": "price_123"]
)

Every workflow's factory exposes a typed start and getStatus, each bound to the workflow's output type; runSync is generated only for workflows with syncCallable = true. The input is required whenever the schema requires fields, optional otherwise. Run with --check in CI to fail when the generated files are out of date, the same way primitive databases codegen --check guards database types. For a workflow with no schema — where there is nothing to generate from — the client.workflows methods take the same type parameters directly: runSync<Input, Output>(...), start<Input>(...), getStatus<Output>(...).

Both languages' factories also carry a typed terminate; cronTriggers.create / cronTriggers.update, which pin the workflow key so a trigger can't be redirected at another workflow; and — for apply-mode workflows — define, which registers your apply handler. Two payloads are typed further in JavaScript than in Swift, because the Swift client models them more loosely: a cron trigger's rootInput is typed from the input schema in JavaScript (Partial of it for object-shaped inputs, since an inputMapping can supply the rest) while Swift takes a JSONValue there — Swift has no Partial, and a partial root input has to stay open — except for a non-object input schema, which Swift binds to the full input type; and the JavaScript apply handler's output is bound to the workflow's output type, while the Swift handler receives the client's untyped WorkflowApplyContext. On update, all three states JavaScript's rootInput carries are available in Swift too: omit it to leave the stored root input alone, or clear it with JSONValue.null where the parameter is open and .clear (an Updatable) where it is bound to the input type.

An outputSchema can express a discriminated union with oneOf, when every member is an object and shares exactly one property declared as a distinct single-value enum — the discriminant is auto-detected, not named explicitly:

toml
[[workflow.outputSchema.oneOf]]
type = "object"
required = [ "status", "checkoutUrl" ]
[workflow.outputSchema.oneOf.properties.status]
type = "string"
enum = [ "ok" ]
[workflow.outputSchema.oneOf.properties.checkoutUrl]
type = "string"

[[workflow.outputSchema.oneOf]]
type = "object"
required = [ "status", "message" ]
[workflow.outputSchema.oneOf.properties.status]
type = "string"
enum = [ "error" ]
[workflow.outputSchema.oneOf.properties.message]
type = "string"

Codegen renders the union in each language's idiom. Give the checkout workflow the schema above and its caller narrows on the discriminant:

ts
const res = await checkout.runSync({ input: { priceId: "price_123" } });
if (res.output?.status === "ok") {
  console.log(res.output.checkoutUrl);   // narrowed to the "ok" member
} else if (res.output?.status === "error") {
  console.log(res.output.message);       // narrowed to the "error" member
}
swift
let res = try await checkout.runSync(input: CreateCheckoutSessionInput(priceId: "price_123"))
if let output = res.output {
  switch output {
  case .ok(let ok):
    print(ok.checkoutUrl)   // narrowed to the "ok" member
  case .error(let err):
    print(err.message)      // narrowed to the "error" member
  }
}

Applying Results to Local Data (Client Apply) ​

A workflow runs on the server, but its result often belongs in a document — local-first data only clients write. A workflow with requiresClientApply = true (the default) doesn't finish at the last step: the run transitions to apply_pending, and a connected client claims it, writes the output into the document, and confirms:

  1. The client registers an apply handler for the workflow with workflows.define(workflowKey, { onApply }).
  2. When a run reaches apply_pending, a client calls claimApply() (an exclusive, time-limited claim), runs the handler, then confirmApply() — or releaseApply() on failure so another client can retry.
  3. define(...) wraps this loop for you — when the status event arrives, the client claims the lease, runs your handler, and confirms (or releases on a thrown error). Most apps never call claim/confirm directly.

If a workflow's output doesn't need to land in a document — it writes to databases, sends email, returns a value — set requiresClientApply = false. Because the default is true, server-only workflows (cron- and webhook-fired jobs especially) need the explicit false; otherwise runs sit in apply_pending waiting for a client that never comes:

bash
primitive config set workflow/send-digest workflow.requiresClientApply=false
primitive config push --only workflow/send-digest

On a Schedule (Cron Triggers) ​

A cron trigger fires a workflow on a schedule. Define it as TOML, synced with the rest of your config:

toml
# config/cron-triggers/nightly-digest.toml
[cronTrigger]
key = "nightly-digest"
displayName = "Nightly digest email"
workflowKey = "send-digest"
cron = "0 9 * * *"
timezone = "America/Los_Angeles"
overlapPolicy = "skip"

[rootInput]
digestType = "daily"
bash
primitive config create cron-trigger nightly-digest   # scaffold the file from the defaults
primitive config push --only cron-trigger/nightly-digest

[rootInput] is a literal JSON payload sent on every firing; use [inputMapping] instead to project values from the firing context (e.g. runId = "$triggerId", at = "$firedAt").

Schedules are standard 5-field cron (minute, hour, day-of-month, month, day-of-week): 0 * * * * is hourly, 0 9 * * 1 is Mondays at 9:00, 0 0 1 * * is the first of the month. Timezone accepts any IANA name and handles DST correctly — 0 9 * * * in America/Los_Angeles fires at 9:00 local year-round; omitted means UTC. Overlap policy decides what happens if a firing arrives while the previous run is still going: "skip" (default — right for idempotent jobs) or "allow" (parallel runs).

Manage triggers from the CLI or your app:

bash
primitive cron-triggers list
primitive cron-triggers get <trigger-id>      # includes recent runs
primitive cron-triggers disable <trigger-id>
primitive cron-triggers enable <trigger-id>
primitive cron-triggers test <trigger-id>     # fire manually
primitive cron-triggers archive <trigger-id>  # retire it (soft delete)

Retiring a trigger has two spellings, and they cost different things. primitive cron-triggers archive <trigger-id> is the soft one: the schedule is cancelled and the row is kept, still holding its triggerKey and its slot against the 50-trigger cap — archiving frees neither, enable refuses an archived trigger, and there is no un-archive. Deleting its TOML file and running primitive config push --prune is the hard one: the row is destroyed outright, and the key and the slot come back. Recovery from an archive is therefore the hard delete followed by a re-push, not a second push. disable and enable are operational rather than configuration: they write the server-owned status, which the TOML does not carry, so a later push cannot put a disabled trigger back in service. enable also clears an automatic pause — when a firing fails hard the platform sets status to inactive and records why in lastError.

ts
const { items } = await client.cronTriggers.list();
const trigger = await client.cronTriggers.get(triggerId);
await client.cronTriggers.test(triggerId); // fire once, now
swift
let list = try await client.cronTriggers.list()
let items = list.items
let trigger = try await client.cronTriggers.get(triggerId: triggerId)
_ = try await client.cronTriggers.test(triggerId: triggerId) // fire once, now

Two limits: 50 cron triggers per app (consolidate with a single trigger that fans out — iterate-users, or a forEach over workflow.call), and 1-minute minimum granularity.

Cron-fired runs are persistent workflow runs like any other — meta.triggerId identifies the trigger that fired them. Remember requiresClientApply = false for cron workflows (above).

Via Inbound Webhooks ​

Inbound webhooks let external services (Stripe, GitHub, Slack, etc.) trigger workflows automatically: each webhook has a public receive URL (POST /app/{appId}/webhook/{webhookKey}), signature verification, and a target workflow it starts with the event payload as input. A webhook-triggered workflow must be a system workflow (runAs = "system") — that identity is what keeps members from invoking it directly with a crafted payload.

Inbound Webhooks covers the whole surface: defining webhooks in TOML, the verification schemes and signing-secret rules, secret rotation, deduplication and replay protection, limits and deletion, and the webhooks test / webhooks verify tools.

Controlling Access to Workflows ​

Every workflow can carry an accessRule — a CEL expression in the [workflow] block that decides who may start a run:

toml
[workflow]
key = "generate-report"
name = "Generate Report"
accessRule = "hasRole('admin') || isMemberOf('team', 'ops')"

A workflow with no rule denies every caller but app admins and owners — the same fail-closed posture prompts, integrations and database operations take. Write accessRule = "true" for a workflow any signed-in app member may start. Admins and owners always pass regardless of the rule. The rule is evaluated on every client invocation — asynchronous or synchronous — and when another workflow invokes this one through a workflow.call step. Cron triggers and inbound webhooks skip it entirely (they have their own controls). Because those triggers run system workflows — which members can't start at all — a system workflow takes no accessRule at all: a non-empty rule on a runAs = "system" workflow is rejected when you save or push it (runAs:"system" workflows do not evaluate accessRule — remove the accessRule). accessRule gates only caller workflows, deciding who may start a run.

A refused start answers 403 with errorCode: "WORKFLOW_ACCESS_DENIED" — on start(), on runSync(), and on a workflow.call step alike. The response is identical whether the rule evaluated false or no rule is stored; the worker log distinguishes the two ([workflow-access] denied versus [workflow-access] no access rule — denying).

Find workflows that have no rule

A caller workflow with no accessRule denies every non-admin start. Find them with primitive workflows get <id> (which prints (none — all non-admin starts are denied; set one to allow callers)) and with the per-file warnings primitive config push prints. Set accessRule = "true" to allow any signed-in member.

Every surface that creates a caller workflow now requires the decision up front: a create with no accessRule is refused with accessRule is required (use "true" for a workflow any app member may start). runAs = "system" workflows are exempt — they reject any rule and members cannot start them.

Letting one workflow call another ​

A child workflow that only ever runs as a step of a known parent should say so rather than open itself to every member. Name the parent in the child's rule, the same way a prompt or an integration does:

toml
[workflow]
key = "rebuild-index"
# Only the digest workflow may call this; no member can start it directly.
accessRule = "fromWorkflow('daily-digest')"

fromWorkflow() with no argument admits any calling workflow; fromWorkflow('<key>') admits one. The calling workflow is bound in process by the workflow.call step, so a client cannot claim to be a workflow — on start() and runSync() nothing is bound and fromWorkflow() is false.

One exemption applies in the other direction: a workflow.call from a system workflow skips the child's accessRule entirely. A system run's reach is bounded by its declared capabilities rather than by start rules, and no member can start one, so the child's rule has no caller to judge.

Push the rule with primitive config push like any other workflow config. For the rule language and the identity context available to it (hasRole, isMemberOf, memberGroups), see Access Control.

System Workflows ​

By default a workflow runs as the user who started it (runAs = "caller"): every step acts with that member's own permissions — it touches only documents they can access, its group and data operations are checked against their roles, and its blob steps are checked against the bucket's access policy. This is the safe default, and most workflows want it.

Set runAs = "system" to run a workflow as the app itself instead of as any one user:

toml
[workflow]
key = "nightly-digest"
name = "Nightly Digest"
runAs = "system"

A system run executes with the app's own privileges — which is what lets a scheduled job read and write across every user's data. Because it acts on no one's behalf, who may start one is tightly held:

  • Only admins and owners can start a system workflow. A regular member who tries is refused with a 403 — never silently downgraded to a caller run.
  • Cron triggers and inbound webhooks can only fire system workflows. A trigger has no human principal to borrow, so it refuses to start a caller workflow. (Member-initiated runs are what caller workflows are for.)

Runs are attributed to the app's system principal, and every system run records who set it off — the admin who started it, or the trigger that fired it — for the audit trail.

A registered operation's access rule still applies. The app-privileged baseline covers raw reads and writes — the documents and records a run touches directly, skipping the per-caller permission checks a caller run is bound by. It does not override a registered database operation's own access rule: a database.query or database.mutate step evaluates that operation's CEL whether the run is caller or system, and an operation whose access is "false" fails with 403 Access denied even from a system workflow. To reserve an operation for server-side automation, authorize it by workflow identity rather than disabling access:

toml
access = "fromWorkflow('billing-webhook')"   # not "false"

Sensitive capabilities ​

A system run can always read and write the app's documents and data. Anything beyond that baseline is opt-in: declare it in capabilities so a privileged workflow does only what you intend.

toml
[workflow]
key = "sync-team-roster"
name = "Sync Team Roster"
runAs = "system"
capabilities = ["membership"]

membership lets the workflow change group membership — the group.addMember, group.removeMember, and group.removeAll steps. Without the grant, those steps in a system workflow are refused. Read-only group checks never need it.

Three more capabilities gate the resource lifecycle steps and the collection membership steps in a system run: resource-provision (database.create, group.create, collection.create, document.create), resource-teardown (database.delete, group.delete, collection.delete), and resource-grant (collection.grantGroupPermission, collection.addDocument, collection.removeDocument). Each is deny-by-default — a system-mode step whose capability isn't declared fails non-retryably. A system-mode create attributes the new resource to the app's system principal (createdBy: "sys:<appId>"); a system-mode delete may only remove a resource with that same attribution, unless the workflow also holds the escalated resource-teardown:any capability, which extends teardown to resources a member created.

Grant or revoke capabilities by editing the capabilities array and pushing — on a new workflow and an existing one alike. An empty array revokes all of them.

iterate-users is system-only — it fans out across the entire user roster, which no single caller has the standing to do. A workflow that uses it must set runAs = "system", or the server rejects it when you push.

Acting on Behalf of a User ​

A system run acts as the app, not as any one member — but a per-user job often needs to work about a specific user: read the documents they can see, run a database operation under their access rules, or attribute an event to them. The *ForUser step variants do exactly that. Each takes an explicit userId subject and operates as if it were checking that user, while the run's actor stays the system principal for the audit trail — the workflow acts about the user, never as them.

These steps are system-only — a runAs = "caller" workflow that calls one is rejected — and the subject must be a member of the app, or the step fails. The subject is the step's userId when set, otherwise input.userId — an empty or whitespace-only userId falls back to input.userId rather than shadowing it, so a child workflow fanned out by iterate-users gets the iterated user as its subject with no wiring. A subject that resolves to empty fails the step with a remediation error naming input.userId and the iterate-users subject:

toml
[[steps]]
id = "ensure-profile"
kind = "document.getOrCreateWithAliasForUser"
userId = "{{ input.userId }}"
aliasKey = "profile"
title = "Profile"
# permission = "write"   # the subject's grant on a freshly created doc; default "write"

[[steps]]
id = "assignments"
kind = "database.queryForUser"
userId = "{{ input.userId }}"
databaseId = "{{ input.classroomDbId }}"
operationName = "listAssignments"
saveAs = "assignments"

[[steps]]
id = "track"
kind = "analytics.writeForUser"
userId = "{{ input.userId }}"
action = "profile.processed"
feature = "onboarding"

A database.*ForUser step evaluates the operation's CEL access rules and database triggers as the subject — user.userId, hasRole(...), and isMemberOf(...) all refer to that user — even though the actor recorded on the run stays the system principal.

The subject-user steps:

KindReturns
user.getThe subject's profile: { userId, email, name, appRole, rootDocId, disabled }
user.resolveResolve a subject by userId or email; { userId: null } when no app member matches, else { userId, user }
document.resolveAliasForUserResolve the subject's user-scoped alias (app-privileged); { documentId: null } on miss
document.listForUserDocuments visible to the subject — direct and root-document grants — as { items, cursor }
document.getForUserOne document as the subject sees it: { document, permission }, or { document: null } when they have no effective access. Pass systemBypass = true for an app-privileged read by id
document.getOrCreateWithAliasForUserEnsure a per-subject document exists (created by the system actor, with the alias and a default write grant to the subject): { documentId, aliasKey, userId, created }
database.*ForUserqueryForUser / mutateForUser / countForUser / aggregateForUser / pipelineForUser / applyToQueryForUser — the matching database.* step, run under the subject's access rules and trigger context

Once a subject method hands back a concrete documentId, the ordinary document.query / save / patch / delete steps read and write it app-privileged — there are no separate *ForUser write kinds. Those CRUD steps also accept an inline subject alias, documentAlias = { scope = "user", aliasKey = "...", userId = "..." }, which resolves the subject's alias in place and fails the step if it doesn't exist.

Testing and Debugging Workflows ​

Test cases live alongside the workflow — workflows/<key>.tests/<case>.toml, authored in TOML and applied by config push — and run against the real engine. The file's name is the case's identity: config pull writes it back under that name, and renaming the file renames the case rather than creating a second one.

toml
# workflows/send-digest.tests/basic-test.toml
[test]
name = "Basic test"
inputVariables = '{"input":"hello"}'
bash
primitive config push --only workflow/send-digest
primitive workflows tests run-all <workflow-id>

primitive config fields workflow lists the sidecar's keys; deleting a case is removing its file and running primitive config push --prune.

Manual firing for cron-driven workflows: primitive cron-triggers test <trigger-id>.

Run inspection — every step's input and output is persisted and reachable from the CLI, your app, or the Admin Console's run detail view:

bash
primitive workflows runs list <workflow-id>
primitive workflows runs status <workflow-id> <run-id>
primitive workflows runs steps <workflow-id> <run-id>

runs list includes a DELAY column, and runs status includes "Execution started", "Queue delay", and "Create call" lines — surfacing executionStartedAt, queueDelayMs, and createCallDurationMs (the wall-clock time of the run's underlying create call) from the run record.

Step results are recorded as the run goes, not once it finishes: runs steps and runs status on an in-flight run return the steps that have finished so far plus a running row for the step executing right now, so you can watch a long run progress — and see which step is stuck — without waiting for a terminal state. The row is finalized in place when the step completes, and a run that ends while a step is still marked running (aborted mid-step) closes that row as failed, so no finished run reports a step as still executing.

The <workflow-id> argument to the management and runs commands (get, preview, disable, enable, runs ...) accepts either the workflow's id or its key — primitive workflows runs list send-digest works as well as the ULID form. When both exist, the id wins; key lookup is scoped to the app and case-insensitive.

ts
// Fetch the per-step run records for a run (debugging / admin views)
const { items: stepRuns } = await client.workflows.listStepRuns({ runId });

for (const step of stepRuns) {
  // step.stepId, step.stepKind, step.status, step.input, step.output, step.error
  console.log(step.stepId, step.stepKind, step.status);
}
swift
// Fetch the per-step run records for a run (debugging / admin views)
let stepRuns = try await client.workflows.listStepRuns(runId: runId).items

for step in stepRuns {
  // step.stepId, step.stepKind, step.status, step.input, step.output, step.error

Syncing Workflow Config ​

Workflow files ride the standard config loop — Configuring Primitive Services covers it; this section adds the workflow-specific semantics:

bash
# Initialize config (sync dir auto-resolves to .primitive/sync/<env>/<appId>/)
primitive config init

# Pull current server config
primitive config pull

# Edit TOML files locally...

# See what changed
primitive config diff

# Push changes
primitive config push

Every [workflow] field round-trips through config push, on a new workflow and an existing one alike — including syncCallable and capabilities. The file is the whole picture: what it declares is what the workflow has after the push.

That cuts both ways — deleting a line converges the server, it does not preserve the old value. On the next config push of an existing workflow:

  • removing description, accessRule, runAs, capabilities, inputSchema, outputSchema, [workflow.lock] or syncCallable clears it;
  • removing perUserMaxRunning, perUserMaxQueued, perAppMaxRunning, perAppMaxQueued, queueTtlSeconds, dequeueOrder or requiresClientApply resets it to the default (4, 100, 25, 10000, 43200, fifo, true);
  • status is not on either list: availability is server-owned, so a push neither sends nor converges it, and a file that still carries the key fails the push;
  • name is required: the push refuses a [workflow] table with no non-empty name and names the file, rather than sending a clear the server would reject.

So a hand-trimmed file is a config change, not a partial update — pull before editing a workflow you didn't author locally. Edits made in web-admin since your last sync are detected and reported as push conflicts, with --force as the override; that check compares the workflow's modified timestamp, so it catches an edit that landed before the push started, not one landing during it. It also rides the update request, so it only fires for a workflow the push actually sends: a file unchanged since your last sync is skipped without a request, and its server-side drift shows up in primitive config diff rather than as a push conflict.

For reusable step blocks, lift them into <workflowDir>/../workflow-fragments/<name>.toml and reference them from a workflow via include = ["<name>"]. The CLI flattens fragment references before push; primitive workflows expand <workflow.toml> prints the expanded result for debugging.

Included steps are placed ahead of the workflow's own [[steps]], in the order the fragments are listed, wherever the include appears in the file. To run something before an included fragment, lift that work into a fragment of its own and list it first.

The [[include]] table form parameterizes a fragment and can gate all of its steps behind one condition:

toml
# config/workflows/onboard.toml
[[include]]
fragment = "lifecycle-email"
runIf = "input.plan == 'pro'"
[include.with]
id = "welcome"
subject = "Welcome aboard"

The fragment's steps read those values as {{ params.id }} and {{ params.subject }}, which the CLI substitutes at expand time; the include's runIf is combined with each step's own runIf. Every other {{ ... }} template in the fragment is left for the server to render when the run executes, so the same fragment can be included several times with different parameters.

primitive config pull keeps the fragment form. A file whose includes already expand to what the server is running is left untouched, comments and all. When the server has drifted — steps added in the console, say — pull keeps the include blocks and writes the extra steps into the workflow's own [[steps]]. The one case it can't preserve is a running workflow that no longer starts with the steps a fragment expands to (someone edited or removed a fragment's steps server-side): there is no fragment-based file that reproduces it, so pull writes the fully expanded steps and prints the reason.

System workflows add subject-user variants — user.get / user.resolve, document.*ForUser, database.*ForUser, and analytics.writeForUser — for acting about a specific user; see Acting on Behalf of a User.

Any step can fan out with forEach, whose value names an array in the run context — forEach = "steps.fetch.items". Unlike the step's other fields, this one is a bare path, not a template. Wrapping that path in a single template expression (forEach = "{{ steps.fetch.items }}") resolves to the same array, but any other use of {{ }} there — a partial template, several expressions in one value, or an expression that is not a bare path (operators and filters work in the step's other fields, not in the source) — is rejected when you push the workflow. Kebab-case step ids are ordinary paths (forEach = "{{ steps.list-securities.items }}" works); a path segment with other punctuation needs the bracket form (forEach = "{{ steps['odd.key'].items }}").

A forEach step is bounded by maxItems — 500 iterations by default, which clears the native page size of the providers you're likely to iterate (Plaid hands back 250 rows per page). Raise it per step (maxItems = 1000) when a list is genuinely longer, and pair a raised cap with concurrency so the iterations fan out instead of running one after another. A list over the cap fails the step before any iteration runs, and that failure is not retried — the list is already the length it is, so a retry would only re-do the work that produced it.

Steps that reach across the network — llm.chat, gemini.generate, the database.* steps, and email.send — are bounded by a timeout: 120 seconds for the LLM and Gemini steps, 30 seconds for database and email. Override it per step with a timeout field (in milliseconds). A step that exceeds its timeout fails without retrying, recording a failed step-run rather than hanging the run.

transform ​

Returns its templated output table — the workhorse for shaping a final result or restructuring data between steps. Given run input { "name": "Ada" } and a prior step fetch whose output is { "items": ["alpha", "beta"] }:

toml
[[steps]]
id = "final"
kind = "transform"
saveAs = "output"
[steps.output]
greeting = "Hello {{ input.name }}"
items = "{{ steps.fetch.items }}"     # single-expression mode preserves arrays

The step's result is the templated table itself — steps.final (and outputs.output, via saveAs) becomes:

json
{ "greeting": "Hello Ada", "items": ["alpha", "beta"], "ok": true }

(The ok field is the engine's verdict stamp — it's added to every object result, so don't use ok as a data field of your own.)

script ​

For data shaping that's more involved than a templated transform step — reshaping nested JSON, computing derived fields, filtering and mapping arrays — a script step runs a sandboxed Rhai script over its JSON input and returns JSON. Scripts are side-effect-free (no network, no storage) and deterministic, so they're safe to retry and easy to test — with one deliberate exception: the ulid() builtin mints a fresh, sortable unique id on each call (for pre-minting record ids ahead of a document.bulkUpdate write), so a script that calls it returns different ids run to run, while a script that doesn't stays fully reproducible.

A script body lives in your config directory as transforms/<name>.rhai and is pushed with primitive config push:

// transforms/normalize-order.rhai
let items = input.raw.items.filter(|i| i.qty > 0);
let total = 0.0;
for i in items { total += i.qty * i.price; }
#{
  currency: input.currency,
  itemCount: items.len(),
  total: total,
}

The step names the script with ref and feeds it input through the with table — inside the script, with is read as input.* (not bare variables):

toml
[[steps]]
id = "normalize"
kind = "script"
ref = "normalize-order"     # the script's name: transforms/normalize-order.rhai
saveAs = "order"
# configId = "..."          # optional — pin a specific ScriptConfig for determinism
[steps.with]
raw = "{{ steps.fetch.body }}"
currency = "{{ input.currency }}"

configId is optional. Without it, the runner resolves the script's active config body at execution time, so pushing a new .rhai body reaches all referencing workflows on their next run with no re-publish step. Set configId to pin a specific version when determinism is required.

limits is also optional and lowers the per-run sandbox ceilings for this step (maxOperations, wallMsHint, maxOutputBytes, maxArrayLength, maxObjectKeys, maxNestingDepth, maxStringSize, maxCallDepth, maxLogBytes). Requested values are clamped at the app ceiling; they can only lower, never raise it.

Given steps.fetch.body of { "items": [ { "sku": "a1", "qty": 2, "price": 5.0 }, { "sku": "b2", "qty": 0, "price": 9.0 } ] } and input { "currency": "USD" }, the script returns:

json
{ "currency": "USD", "itemCount": 1, "total": 10.0 }

One wiring detail: a script's output is wrapped in an envelope, steps.<id>.output = { result: <return value>, ok: <bool> }. The return value lives under result, so later steps read {{ steps.normalize.output.result.total }} — not {{ steps.normalize.output.total }} or {{ steps.normalize.total }} (unlike transform, whose result is the table directly). The success verdict is at {{ steps.normalize.output.ok }}.

Pushing a changed .rhai file (primitive config push) creates a new script version and activates it — every workflow that references the script by name picks up the new body on its next run, with no re-publish step needed.

iterate-users ​

Fans another workflow out across every user in the app, once per user, as a restartable singleton — built for big per-user batch jobs (backfills, digests) that must survive restarts without re-processing completed users. It's a system-only step: the workflow must set runAs = "system".

toml
[[steps]]
id = "backfill"
kind = "iterate-users"
iterationName = "2026-06-prefs-backfill"   # stable name; identifies this iteration
pageSize = 100
concurrency = 25
[steps.source]
mode = "app"                 # iterate the app's user roster
[steps.perUser]
workflowKey = "process-one-user"   # the workflow to run once per user
[steps.perUser.input]
reason = "preferences backfill"    # static input merged into each child run

source selects which users to iterate — mode = "app" walks the app's full user roster, fetched in pages of pageSize. For each user, the step starts a child run of the workflow named by perUser.workflowKey (a separate workflow you define), with up to concurrency child runs in flight per page. Prefer this over a hand-rolled forEach when the fan-out is app-wide and long-running.

An iterate-users step can't itself carry a forEach — it already fans out over the whole roster, so nesting it in a loop would multiply the entire user base by the loop's length. Pushing a workflow that does is rejected ('iterate-users' cannot be used with forEach). If you really need a per-item app-wide pass, put the iterate-users step in a child workflow and forEach over workflow.call instead.

Each child run receives the iterated user's id as input.userId automatically — a child that needs nothing else can read {{ input.userId }} with no perUser.input block at all. When you do supply perUser.input, its values are rendered per user against a user binding — the iterated user's row, with user.userId and user.role — and full template syntax works, including fallbacks and filters:

toml
[steps.perUser.input]
greetingName = "{{ user.userId | upper }}"
tier = "{{ user.role || 'member' }}"
reason = "preferences backfill"        # static values pass through unchanged

A key you set in perUser.input wins over the injected default, so userId = "{{ user.userId }}" is redundant but harmless.

Filtering by a metadata value ​

Add a metadataFilter block to fan out over only the users whose resource metadata matches. The roster is still walked in full, but a non-matching user is skipped before dispatch — no child run, no per-child cost — so you no longer need the "start a child for everyone and have it bail" pattern:

toml
[[steps]]
id = "summaries"
kind = "iterate-users"
iterationName = "nightly-portfolio-summary"
[steps.metadataFilter]
category = "billing"                      # a category defined for resource type "user"
key = "status"                            # a key declared in that category's schema
in = ["trialing", "active", "past_due"]   # exactly one of: eq | in | exists
[steps.perUser]
workflowKey = "portfolio-summary-one-user"
  • The filter reads the iterated user's own metadata for resource type user. category and key are static — no {{ }} templates, no #.
  • Use exactly one operator: eq = <value> (strict equality — 1 never matches "1"), in = [<values>] (a non-empty list), or exists = true / exists = false.
  • eq and in values may be templates (eq = "{{ input.status }}"). They render once, when the iteration starts, so every page is filtered by the same value; an unresolved reference fails the run before any child is started.
  • A user with no metadata for the category, no such key, or a null value never matches eq/in — and is exactly who exists = false matches.
  • stringset and date fields support only exists: a stringset value is an array no scalar can equal, and a date may be stored as epoch milliseconds or as an ISO string, so equality would silently miss half your users.
  • The step's result gains filteredOutCount — how many enumerated rows the filter rejected — present (even as 0) exactly when metadataFilter is set. totalProcessed still counts only dispatched users.
  • Naming a category that isn't defined for user, a key the category's schema doesn't declare, or an operand the field's type can never hold fails the run with that name in the message, rather than quietly matching nobody. Structural mistakes (no operator, two operators, an empty in, a misspelled option) are rejected when you push the workflow.
  • The filter does not evaluate the category's readRule. Unlike the metadata steps, it is a direct, system-only read: iterate-users acts about users, never as one (the same rule metadata.resolve follows). A restrictive readRule does not hide a category from this filter, so don't treat one as a guard against it.

iterationName is itself templated: a plain string keys a single restartable singleton, while a date template like "digest-{{ today }}" makes each day's run its own iteration, and {{ now }} or {{ uuid }} makes every fire unique (turning off the resume-a-singleton behavior). Inspect and clear iterations from the CLI — primitive workflows iterations list shows each iteration's status and progress, ... get <name> shows one in detail (including the failed-user sample), and ... reset <name> clears a finished (completed or failed) iteration so its next trigger runs fresh. A still-running iteration can't be reset.

prompt.execute ​

Runs a managed prompt — versioned, testable, and configured outside the workflow:

toml
[[steps]]
id = "summarize"
kind = "prompt.execute"
promptKey = "summarizer"      # must be active
saveAs = "summary"
# expect = "text"             # the default — content is the model's text

[steps.variables]
text = "{{ input.content }}"

The step's output is { content, metrics, promptKey, configName, model, renderedSystemPrompt, renderedUserPrompt }.

The step declares the type of content. expect is the only thing that decides it — the prompt config's outputFormat shapes the provider request and the execute endpoint's response, so activating a different config never retypes what your downstream steps and scripts receive:

expectcontent
omitted or "text"The model's output text exactly as the provider returned it — never parsed, never fence-stripped.
"json"The parsed JSON value (object, array or primitive). Markdown code fences are stripped first; output that will not parse fails the step with a non-retryable error naming the prompt key and config.

expect must be the literal "json" or "text" — it is never templated, and any other value is rejected when you save the workflow.

toml
[[steps]]
id = "sentiment"
kind = "prompt.execute"
promptKey = "sentiment-extractor"   # its config constrains the model to JSON
expect = "json"
saveAs = "sentiment"

[steps.variables]
text = "{{ input.content }}"

[[steps]]
id = "record"
kind = "transform"

[steps.output]
mood = "{{ steps.sentiment.content.mood }}"

Pair expect = "json" with a config that constrains the provider, which is what makes the parse reliable: on openrouter that is outputFormat = "json" (provider JSON mode), on gemini it is the config's outputSchema — gemini uses outputFormat only to normalize the execute endpoint's response, not to constrain the request. The step parses whatever it gets either way (it strips fences itself), so an unconstrained config just leaves the model free to answer with prose, which fails the step.

Reading a field off a text-typed content — {{ steps.summarize.content.title }} — is an unresolved reference and fails the step that references it. Declare expect = "json" on the prompt step, or rescue the reference with {{ steps.summarize.content.title | default: "" }}. Migrating a workflow that relied on the old auto-parsing behavior is one line: add expect = "json". The step output has no raw field — the completion is stored once, in content.

Calls an external API through a configured integration, with credentials resolved server-side. The integration's own accessRule decides whether the step may call it — a common pattern is accessRule = "fromWorkflow()", which lets your workflows through while refusing direct client calls. An integration with no rule refuses the step too, in both run modes.

toml
[[steps]]

saveAs = "weather"

method = "GET"
path = "/current"

[steps.request.query]

toml

integrationKey = "oauth-provider"
saveAs = "token"

[steps.request]
method = "POST"
path = "/oauth/token"

[steps.params]

[steps.params]

To write a set of records — a page of an external sync, an imported list — use database.batch: it runs one registered mutation operation over an array of parameter objects in a single call, and records a single step run:

toml

Document Steps ​

document.query, document.queryOne, document.count, document.save, document.patch, and document.delete read and write records in a document's models. Every document step takes a documentId and a modelName; queries take an optional filter (the same operator syntax as client-side model queries) and options (sort, limit, cursor pagination), and writes target a recordId:

toml
[[steps]]
id = "overdue"
kind = "document.query"
documentId = "{{ input.docId }}"
modelName = "Invoice"
saveAs = "invoices"
[steps.filter]
status = "overdue"
[steps.options]
sort = { dueDate = 1 }
limit = 50

[[steps]]
id = "mark-paid"
kind = "document.patch"
documentId = "{{ input.docId }}"
modelName = "Invoice"
recordId = "{{ input.invoiceId }}"
[steps.data]
status = "paid"

document.save creates or replaces the record at recordId; document.patch merges its data fields into it. Step results: document.query returns { data, hasMore, nextCursor } (pageable with collect), document.queryOne returns { record } (null when nothing matches), document.count returns { count }, the writes return { record }, and document.delete returns { deleted, id }.

Writes are durable when the step completes and reach connected clients like any other document change — use document steps when the workflow owns the write. When the result should instead land in data only clients write, leave the writing to client apply.

Writes obey the model's field types. Every document write — document.save and document.patch, single and batch, plus document.bulkUpdate — checks each value against the model's declared field types before anything is persisted. A value that converts safely is converted: the 1/0 a database read yields for a boolean column (SQLite has no boolean type) is stored as true/false, a numeric string in a number field becomes a number, a number in a string field is stringified. A value that can't be converted — "maybe" or 2 in a boolean field, an object in a number field — fails the step with a type error naming the model, field and declared type (the failure is non-retryable: a mistyped record never succeeds on a retry). The rejection rolls back the transaction it happened in, so a single write and a bulkUpdate write nothing at all; a batch records write runs one transaction per 100-record chunk, so a type error in a later chunk leaves the earlier chunks committed, like any other batch failure. date fields accept either an ISO-8601 date string ("2026-08-14", optionally with a time — the space-separated "2026-08-14 12:30:00" a SQL read yields included) or an epoch number and nothing else — an unparseable string fails like any other mistyped value, and so does one only a locale parser understands ("08/14/2026") or a day the calendar doesn't have ("2026-02-30"); null, fields the model doesn't declare, and stringset payloads are left alone. The contract reads the model schema embedded in the document, so a model no client has ever saved has nothing to enforce. The same check covers the other server-side write surfaces — the document-records REST API and the primitive documents records commands built on it, which now answer 400 for a mistyped value instead of storing it. Writes your clients make over their live connection are unaffected: they sync document changes directly and never go through this path.

Caller-mode access. In a caller workflow (the default), document steps act with the starting user's own document permissions, checked per operation: the reads (query, queryOne, count) need reader on the target document, and save, patch, and delete all need read-write. A step that reaches past what the caller may do fails the run — so a templated or user-supplied documentId can't be used to touch a document the caller couldn't open themselves. A system workflow runs with the app's privileges and skips these per-caller checks.

Targeting a document by alias. Instead of a fixed documentId, a step can name a document by its alias — convenient for the one-document-per-user pattern, where each caller has their own:

toml
[[steps]]
id = "load"
kind = "document.query"
modelName = "Habit"
saveAs = "habits"
[steps.documentAlias]
scope = "user"
aliasKey = "tracker"

Give a step either documentId or documentAlias, not both. A user-scoped alias always resolves to the caller's own document. If the alias doesn't resolve, the step fails the same way a missing documentId would.

Branching on whether an alias exists. When you'd rather check than fail — "has this user set up their tracker yet?" — use document.resolveAlias. It returns { documentId }, or { documentId: null } when there's nothing to resolve, so a later step can runIf on the result instead of erroring:

toml
[[steps]]
id = "find-tracker"
kind = "document.resolveAlias"
scope = "user"
aliasKey = "tracker"
saveAs = "tracker"

Writing many records in one step. document.save and document.patch accept records (an array) instead of recordId + data; document.delete accepts recordIds (an array of strings) instead of recordId. A step takes one form or the other, never both — supplying recordId alongside records/recordIds fails the step. Batch mode collapses a forEach fan-out into a single step that resolves the document's ACL once and applies every record in one transaction per chunk (chunked at 100 records; a batch over 100 records makes several sequential chunk round-trips, each atomic on its own but not atomic with the others — a failure partway through leaves earlier chunks committed):

toml
[[steps]]
id = "upsert-holdings"
kind = "document.save"
documentId = "{{ input.docId }}"
modelName = "Holding"
records = "{{ steps.rows.output.result.rows }}"   # each { id?, ...fields } — id is optional; omitted ids are minted server-side

document.save returns { saved, savedIds } and document.patch returns { patched, patchedIds } (each element of records needs an id for patch); document.delete returns { deleted } (a non-existent id is a no-op, not an error). Re-running a batch save whose records had no id mints fresh ids each time rather than upserting the same ones — give records an explicit id if the workflow might retry.

Writing across models atomically. Batch mode works on one model at a time, and a batch over 100 records commits chunk by chunk. When a write spans models and must land whole — create an account, adjust a ledger, retire a stale position, all or nothing — document.bulkUpdate applies an ordered list of operations across any of the document's models in a single transaction with a single change broadcast:

toml
[[steps]]
id = "apply-rebalance"
kind = "document.bulkUpdate"
documentId = "{{ outputs.doc.documentId }}"
saveAs = "applied"
operations = [
  { model = "Account",  action = "create", id = "{{ input.newAccountId }}", data = { name = "Growth", balance = 0 } },
  { model = "Ledger",   action = "patch",  id = "{{ input.ledgerId }}", data = { rebalancedAt = "{{ now }}" } },
  { model = "Position", action = "delete", id = "{{ input.staleId }}" },
]

Each operation names its model, an action (create, patch, or delete — that exact vocabulary), and an id; create and patch carry the record fields in data, the same key the single-record writes use. data is required and must be non-empty on those two actions, delete takes none, and any other key in an operation is rejected before anything is written. A create never mints its id server-side: the caller supplies a ULID (26 uppercase characters), typically from the {{ ulid }} template helper or a script's ulid() builtin — which also lets one operation reference the id another operation in the same list just created. Up to 500 operations apply in listed order, all-or-nothing: a create whose id already exists or a patch whose id doesn't fails the whole blob and nothing commits. The step returns { applied, added, updated, deleted }, where added and updated list { model, id } per committed create and patch. Like the other document writes, caller-mode runs need read-write on the document, and documentAlias targeting works here too.

Conditional writes (compare-and-set). A single-record document.save, document.patch, or document.delete accepts a writeOptions block that guards the write against the record's current state — the workflow-side compare-and-set. Two runs racing on the same record converge without a queue: the guard is checked against the live record as the write commits, so exactly one applies and the other fails cleanly.

toml
[[steps]]
id = "cas-balance"
kind = "document.patch"
documentId = "{{ input.docId }}"
modelName = "Account"
recordId = "{{ input.accountId }}"
data = { balance = "{{ steps.calc.output.next }}" }
saveAs = "updated"
[steps.writeOptions.precondition]
version = "{{ steps.read.output.record.version }}"   # apply only if version still matches

precondition is a field-equality map — the write applies only when every named field on the live record still equals the given value; a mismatch, or a record that no longer exists, fails the write and changes nothing. On document.delete it's a conditional delete. ifNotExists (on save) applies only when no record exists at recordId. A failed guard fails the step with CONDITION_NOT_MET and is not retried — the workflow reads the record, computes the next value, and re-attempts the conditional write itself, so a stale write can never overwrite a newer one. To branch on that outcome, capture the attempt with continueOnError = true: the code is on steps.<id>.code for a plain step, and on steps.<id>.errors[0].code / steps.<id>.items[0].code for an attempt made inside a forEach. Preconditions compare scalar values only; for richer conditions, read first and compare in a transform or script, then gate the write on a plain field. document.bulkUpdate accepts a precondition on each operation too — a failed one rolls back the whole blob.

Creating a document mid-run. The document document.bulkUpdate writes into is often one the same run just minted. document.create makes a brand-new document and returns { documentId, created: true } — mint the document only once the run has decided it's needed (for example, after a diff shows a real change), then write into the returned id:

toml
[[steps]]
id = "make-doc"
kind = "document.create"
title = "Holdings — {{ input.importDate }}"
tags = ["import"]
saveAs = "doc"
[steps.metadata]
source = "csv"
accountId = "{{ input.accountId }}"

title is required; optional tags and metadata are set at creation time, so an import's provenance (source, date, account) rides on the document and a collection listing can serve as the history index without opening old documents. In a caller workflow the starting user becomes the document's owner, exactly as the client documents.create call would. In a system workflow the step instead requires an explicit subject userId (the user the document is for) and the resource-provision capability; the document is created under the app's system principal (createdBy: "sys:<appId>") and the subject is granted owner by default (override with permission = "read" | "write" | "owner"). A single run is capped at about 1000 documents — a looping run that exceeds the cap fails non-retryably, and documents minted before the cap persist. Lower the ceiling for a run with input.maxDocumentCreates (it can only tighten, never raise). The cap is a durable per-run counter on a fixed time window, so it is an abuse guardrail rather than an exact quota: a long run that straddles a window boundary can mint up to twice the cap. Validation failures (missing title, too many tags, oversized metadata) are non-retryable; transient errors retry.

group.addMember, group.removeMember, group.removeAll, group.checkMembership, group.listMembers, and group.listUserMemberships manage groups from a workflow:

toml
[[steps]]
id = "add"
kind = "group.addMember"
groupType = "team"
groupId = "{{ input.teamId }}"
userId = "{{ input.userId }}"   # or email = "...", not both

group.removeAll clears every membership a user holds within one group type — the building block for a "clear then set" pattern, such as resetting a user's subscription tier before adding exactly one:

toml
[[steps]]
id = "clear-tiers"
kind = "group.removeAll"
groupType = "subscription"
userId = "{{ input.userId }}"

It takes a groupType and a userId (no groupId — it removes the user from every group of that type) and returns { removed, groupIds }. It is strictly type-scoped, so clearing sub never touches subscription, and it removes at most 1000 memberships per run. In a caller run the group type's member.delete rule is checked for every affected group before anything is removed, so authorization is all-or-nothing.

Group steps evaluate the group type's rule sets like any other caller; rules can match workflow-issued operations with fromWorkflow("workflowKey") — see Access Control. In a system run, addMember and removeMember record the app's system principal as the member's addedBy — not the admin or trigger that started the run.

Collection Steps ​

collection.addDocument and collection.removeDocument manage a document's membership in a collection — the workflow counterpart to the client's add/remove calls, useful when a run produces or processes a document that belongs in a shared set:

toml
[[steps]]
id = "publish"
kind = "collection.addDocument"
collectionId = "{{ input.collectionId }}"
documentId = "{{ steps.create.documentId }}"

Both take a collectionId and a documentId, and both converge on retry: adding a document that's already a member succeeds with { added: false, alreadyPresent: true } (a real add returns { added: true, alreadyPresent: false }), and removing one that isn't a member succeeds with { removed: false, alreadyAbsent: true }. In a caller run, authorization matches the client calls exactly — addDocument checks the collection type's document.add rule plus the caller's write access to the document; removeDocument checks document.remove. In a system run, both steps instead require the resource-grant capability (see Sensitive capabilities).

Resource Lifecycle Steps ​

database.create / database.delete, group.create / group.delete, collection.create / collection.delete, and collection.grantGroupPermission provision and tear down resources from inside a run — so one durable workflow can set up a whole constellation (a database, its groups, its collections, and the grants wiring them together) instead of the client sequencing each call itself:

toml
[[steps]]
id = "db"
kind = "database.create"
title = "{{ input.className }}"
databaseType = "classroom"

[[steps]]
id = "teachers"
kind = "group.create"
groupType = "class-teachers"
groupId = "class-{{ input.classCode }}-teachers"   # optional; a caller-supplied id makes re-runs idempotent
name = "{{ input.className }} Teachers"

[[steps]]
id = "posts"
kind = "collection.create"
name = "{{ input.className }} Posts"
collectionType = "class-posts"

[[steps]]
id = "grant"
kind = "collection.grantGroupPermission"
collectionId = "{{ steps.posts.collectionId }}"
groupType = "class-teachers"
groupId = "{{ steps.teachers.groupId }}"
permission = "read-write"   # or "reader"

These steps run in both caller and system workflows. In a caller workflow (the default), each step acts as the starting user under exactly the rules the equivalent client call enforces, creating and tearing down resources just as if that user had done it from the app. In a runAs = "system" workflow, each step instead needs the matching capability declared in capabilities: resource-provision for the create steps, resource-teardown for the delete steps, and resource-grant for collection.grantGroupPermission — without the grant, the step fails non-retryably before anything is written:

toml
[workflow]
key = "provision-classroom"
name = "Provision Classroom"
runAs = "system"
capabilities = ["resource-provision", "resource-grant"]

[[steps]]
id = "makeDb"
kind = "database.create"
title = "{{ input.className }}"
databaseType = "classroom"

A resource a system-mode create step produces is attributed to the app's system principal (createdBy: "sys:<appId>"). A system-mode delete may only remove a resource with that same attribution — deleting a resource a member created needs the escalated resource-teardown:any capability alongside resource-teardown. See Sensitive capabilities for the full capability list.

The create steps return the created resource, so later steps can wire it up ({{ steps.db.databaseId }}, {{ steps.posts.collectionId }}). database.create takes a title and databaseType plus optional metadata (validated against the type's declared metadata); collection.create takes a name plus optional description, collectionType, and contextId. Both also accept optional initialMetadata — a { category: { field: value } } map that stamps resource metadata categories atomically as the resource is created, exactly as the equivalent client create call does: every category is validated before the resource is created (an invalid one fails the whole step, leaving nothing behind), the category's write rule is waived for this create-time stamp, and at most 10 categories may be stamped. Stamping at create closes the window where an md.self.* rule on the new resource would otherwise deny until a later write lands. Their ids are minted server-side, so a retried run can create a duplicate — put creates early and make later steps the fallible ones. group.create avoids this by accepting a caller-supplied groupId: re-creating an existing group succeeds with { created: false, alreadyExists: true }.

The delete steps (database.delete by databaseId, group.delete by groupType + groupId, collection.delete by collectionId) cascade exactly like their client counterparts and treat an already-gone resource as a no-op ({ deleted: false, alreadyAbsent: true }) — an ordered teardown workflow re-run over a partially torn-down set converges instead of failing.

Metadata Steps ​

metadata.write, metadata.read, and metadata.delete write, read, and delete a resource metadata category, going through the same category writeRule / readRule gate as the client and CLI:

toml
[[steps]]
id = "record-billing"
kind = "metadata.write"
resourceType = "user"
resourceId = "{{ input.userId }}"
category = "billing"
saveAs = "output"
[steps.data]
stripeCustomerId = "{{ input.customerId }}"
status = "active"

metadata.write fully replaces the category and returns { data, schemaVersion, size }; metadata.read returns { data, schemaVersion, exists }; metadata.delete clears the category and returns { deleted } (saveAs puts any of them under outputs.<name>). Delete is gated by the writeRule and is idempotent — deleting an absent category returns deleted: false rather than failing, so a teardown workflow can clean up a resource's metadata in the same run that deletes it. A category's writeRule/readRule can name fromWorkflow('workflowKey') to authorize only that workflow's step — a REST call or a different workflow to the same category is denied.

metadata.resolve looks a resource up by a category's unique field value — for example, turning a stored Stripe cus_… id back into the user it belongs to. It's a system step (runAs = "system") and returns { resourceId, resourceType } on a hit or { resourceId: null } on a miss:

toml
[[steps]]
id = "find-user"
kind = "metadata.resolve"
resourceType = "user"
category = "billing"
key = "stripeCustomerId"
value = "{{ input.customerId }}"
saveAs = "output"

collect ​

Auto-paginates any step that returns { items, cursor } (or { data, nextCursor }), merging all pages into one result:

toml
[[steps]]
id = "all-users"
kind = "collect"
itemsField = "data"
cursorField = "nextCursor"

[steps.step]

workflow.call ​

Runs a child workflow synchronously, inline. The child gets its own isolated input — it does not see the parent's steps or outputs:

toml
[[steps]]
id = "onboard"
kind = "workflow.call"
workflowKey = "onboard-user"
[steps.input]
userId = "{{ input.userId }}"

Add forEach to fan out — the child runs once per item, and the step returns the array of child results. For app-wide, restartable fan-out over your entire user roster, use iterate-users instead.

Each call is recorded as its own run of the child workflow: primitive workflows runs list <child-key> shows it (running while it executes, then its terminal status), with its own step runs to inspect and the calling run in meta.parentRunId. Debug a failing child from its own run record rather than from the parent's one-line step error.

block.call ​

Invokes a prompt, integration, script, or workflow by key through one uniform step shape — useful when the block to run is chosen by configuration rather than hard-coded as a typed step. blockType selects the kind, blockKey names the block, and input carries the payload:

toml
[[steps]]
id = "summarize"
kind = "block.call"
blockType = "prompt"        # "prompt" | "integration" | "script" | "workflow"
blockKey = "summarize-order"
[steps.input]
orderId = "{{ input.orderId }}"

At run time the step becomes the matching typed step — prompt.execute, integration.call, script, or workflow.call — so its result shape, ok verdict, and retry behavior are identical to writing that step directly. input maps to the typed step's payload field (variables, request, with, and input respectively), and each type's own fields are also accepted (variables, modelOverride, and expect for prompts; request, attachments, bodyMode, and multipartFields for integrations; with and limits for scripts).

For prompts, integrations, and scripts, pin a specific configuration with configId, or version (version = "active" is the default: run whatever configuration is active).

email.send ​

Sends an email from inside a workflow. It has two modes.

Template Mode ​

Use a registered email template — either a built-in type or a custom one you registered:

toml
[[steps]]
id = "order-confirmation"
kind = "email.send"
templateType = "order-confirmation"
to = "{{ input.customerEmail }}"

[steps.variables]
orderId = "{{ input.orderId }}"
total = "{{ input.total }}"

Register custom template types with any kebab-case name — a template is a file in email-templates/, applied with config push:

toml
# config/email-templates/order-confirmation.toml
[template]
emailType = "order-confirmation"
subject = "Your order #{{orderId}}"
htmlBody = "<p>Thanks! Your order total is {{total}}.</p>"
bash
primitive config push --only email-template/order-confirmation

For the full list of built-in types, the template variables each exposes, and how to override or revert them, see Email Templates.

Inline Mode ​

For one-off or dynamically constructed emails, specify subject and body directly in the step:

toml
[[steps]]
id = "report-ready"
kind = "email.send"
to = "{{ input.email }}"
subject = "Your report is ready"
htmlBody = "<p>Download: <a href=\"{{ outputs.upload.signedUrl }}\">link</a></p>"
textBody = "Download: {{ outputs.upload.signedUrl }}"

to is a single address. To fan out to many recipients, use forEach:

toml
[[steps]]
id = "blast"
kind = "email.send"
forEach = "input.recipients"
as = "addr"
to = "{{ addr }}"
templateType = "announcement"

notification.send ​

Sends a notification to a user — the server-side equivalent of client.notifications.send():

toml
[[steps]]
id = "notify"
kind = "notification.send"
toUserId = "{{ input.userId }}"
title = "Your report is ready"
body = "Tap to view this week's summary."
channels = ["in-app", "ios"]
deepLink = "myapp://reports/latest"

channels defaults to ["in-app"]; add "ios" / "android" to also push to the recipient's registered devices. The step succeeds (ok: true) only when at least one requested channel actually delivered — a send that reaches nobody (every channel failed, was rate-limited, or the recipient had no registered device) reports ok: false even though the step ran. Set idempotencyKey to make a retried step re-send only the channels that still need it. See Notifications for the full concept, client SDK, and dedupe/rate-limit reference.

Blob Steps ​

blob.upload, blob.download, blob.signedUrl, and blob.delete write, read, sign URLs for, and delete files in blob buckets — the standard way to hand a generated file (a PDF report, an export) to users, and to clean one up when a flow is done with it:

toml
[[steps]]
id = "save"
kind = "blob.upload"
bucketKey = "reports"
filename = "{{ meta.workflowRunId }}.pdf"
contentType = "application/pdf"
contentBase64 = "{{ steps.gen.bytesBase64 }}"

[[steps]]
id = "url"
kind = "blob.signedUrl"
bucketKey = "reports"
blobId = "{{ steps.save.blobId }}"
expiresInSeconds = 3600

blob.upload returns the blobId; blob.signedUrl mints a time-limited URL you can email or return to the client. blob.delete removes a blob by blobId and returns { deleted: true, blobId, bucketId } — it reports success even when the blob is already gone, so a retried run doesn't fail on cleanup it already did.

Deleting many blobs in one step. blob.delete accepts blobIds (an array of up to 500 ids) instead of blobId — one form or the other, never both. An empty array is a valid no-op, so a templated list that resolves to nothing doesn't fail the step:

toml
[[steps]]
id = "cleanup"
kind = "blob.delete"
bucketKey = "reports"
blobIds = "{{ steps.expired.output.result | pluck:blobId }}"

Every id is validated, and in a caller run screened against the bucket's delete policy, before anything is deleted — one denial fails the whole step with nothing removed. The batch form returns { deleted: N, blobIds, bucketId }, where deleted counts the ids processed.

Two things about these steps are properties of the bucket rather than the step: how a run is authorized against the bucket's access policy, and the requirement that a blob a run reads as input outlive the run's retry window. See Using Buckets in Workflows.

Analytics Steps ​

analytics.write emits analytics events from a workflow; analytics.query reads server-side aggregates — the simplest way to ship a recurring digest, an admin email, or a Slack post that summarizes activity:

toml
[[steps]]
id = "log"
kind = "analytics.write"
action = "report.generated"
feature = "reports"

[[steps]]
id = "top-users-weekly"
kind = "analytics.query"
queryType = "users.top"
windowDays = 7
limit = 25
saveAs = "topUsers"

Query types are dotted strings — overview.dau, daily-active, cohort-retention, users.top, events.grouped, errors.groups (failures grouped by fingerprint with per-day counts), workflows.top, and friends. The query runner is default-deny: non-admin callers are rejected, so keep analytics workflows locked down with accessRule = "hasRole('admin')" (or fire them via cron). Each run is capped at 50 analytics queries.

A query step records { queryType, data, ok }, so later steps read the payload under data — {{ outputs.topUsers.data.results }}, not {{ outputs.topUsers.results }}. What data holds is the query's own response body, identical to what the same query returns over REST or the CLI. Reading query results covers the shapes and the arithmetic traps in them.

For the full picture — what events are emitted, the client-side logEvent API, and how to read metrics back — see Analytics.

noop ​

toml

Template Reference ​

Templates are how steps read the run context (see How Data Flows Through a Run). Expressions use double braces:

{{ input.fieldName }}             # Workflow input
{{ steps.<id>.field }}            # Output from a previous step (by step id)
{{ outputs.<saveAs>.field }}      # Output from a step that used saveAs
{{ secrets.API_KEY }}             # App secret (read-only)
{{ vars.ACCOUNT_ID }}             # App config var (non-secret, read-only)
{{ meta.startedAt }}              # The run's stable start timestamp
{{ user.userId }}                 # The invoking user (caller runs)
{{ input.name | default:"Anonymous" }}   # Filters with single |
{{ input.title || "Untitled" }}            # Fallback with double || (or)

When the entire string is one expression ("{{ steps.fetch.items }}"), the raw array or object is returned. Otherwise expressions are coerced to strings and interpolated.

meta holds whatever you passed to start(), plus meta.startedAt — the run's stable start timestamp (ISO 8601), filled in automatically and identical across every step and retry. Use it when several steps need one shared "generated at" value; use now when you want a fresh per-reference clock read.

In a runAs = "caller" run, user is the invoking user (user.userId), available in step params and in a forEach step's source expression and body. Inside an iterate-users step's perUser.input block, user is instead the iterated user's row (user.userId, user.role). A runAs = "system" run has no caller, so user is unbound outside that iterate-users case.

secrets.* reads from your app's server-side secret store — see App Secrets for managing values and where they're safe to reference. vars.* reads your app's non-secret config vars the same way.

Built-In Helpers ​

Four zero-argument helpers are always available. They re-evaluate on every reference — {{ now }} {{ now }} produces two different timestamps:

NameReturns
nowCurrent ISO 8601 timestamp
todayCurrent UTC date as YYYY-MM-DD
uuidFresh random UUID v4
ulidFresh random ULID (lexicographically sortable)
toml
[[steps]]
id = "name-report"
kind = "transform"
[steps.output]
filename = "report-{{ today }}-{{ ulid }}.pdf"
generatedAt = "{{ now }}"

Fallbacks and Filters ​

Use || for fallbacks and a single | to chain filters:

{{ input.title || 'Untitled' }}
{{ input.flag || false }}                # typed false, not the string "false"
{{ input.count || 0 }}                   # typed 0, not an empty string
{{ input.data | json }}                  # pretty JSON
{{ input.tags | join: ', ' }}
{{ input.users | pluck: 'email' | uniq }}
{{ input.list | sort: 'name' | first }}
{{ input.text | upper | truncate: '100' }}
{{ input.amount | toFixed: '2' }}
{{ input.id | expect: 'string' }}        # throws on type mismatch

A fallback variant is a quoted string, a number, or true / false — anything else is read as a context path. A terminal falsy literal resolves to its typed value rather than falling through, so {{ steps.maybe.output.flag || false }} is how you say "defaults to false" and {{ steps.maybe.output.n || 0 }} is how you say "defaults to zero" (the same field then renders 0 whether the upstream step ran or was skipped). A falsy literal anywhere earlier in the chain falls through to the next variant. The boolean filter reads a string the same way, so 'false' and '0' become false (only | default: 'false' alone leaves you with the truthy string).

A number is a literal only in the spelling the engine round-trips — 0, 7, -5, 1.5. Padded or exponent forms (0.0, -0, 1e3) are read as context paths, and the push rejects them rather than accepting a fallback that can never render.

Filters cover type handling (json, string, number, boolean, default, expect), strings (upper, lower, trim, split, replace, truncate, startsWith, endsWith, contains), arrays (length, first, last, keys, values, join, pluck, where, sort, reverse, flatten, uniq, compact, slice, concat), numbers (round, floor, ceil, abs, toFixed), and dates (toISOString).

Templates have no arithmetic — {{ a + b }} won't resolve. Do math in a script step or a filter chain.

Unresolved Paths ​

An unresolved reference fails the step. If {{ input.custmerName }} names a path that isn't in the run context, the step fails non-retryably and the error names the expression, the step param it came from, and the keys that were available:

Step "notify-customer" failed: 1 unresolved template expression(s):
  - {{ input.custmerName }} (param "message"): Path "input.custmerName" not found in context
    Available: input.customerName, input.orderId

The failure arrives through the surfaces you already use: the step is recorded as failed, the run fails, and it appears in run history and error analytics like any other step failure. Nothing is substituted into the output.

When a template names a root that doesn't exist, the error lists the valid ones (input, steps, outputs, meta, secrets, vars) — which catches typos like {{ inputs.userId }}.

Caught at push time ​

The mistakes that are decidable without running anything are rejected by primitive config push (and by the API that saves a definition), so you see them in the push output instead of in a failed run:

  • an unknown root — {{ inputs.userId }}, {{ iteration.index }} on a step that has no forEach. The error names the expression, the step, and the valid roots.
  • a reference to a step or output the file doesn't declare — {{ steps.lookpu.output }} when the workflow declares lookup, or {{ outputs.profile.name }} when no step has saveAs = "profile". The error lists the ids the file does declare.
  • a fallback that can never resolve — {{ input.a || inputs.b }}. The variant after || is what runs when everything before it is missing, so a dead one is rejected even though the expression's first variant is fine. A variant a truthy literal makes unreachable ({{ true || inputs.b }}) is not flagged — that expression always resolves before it gets there.

Which roots are valid depends on where the expression sits:

RootWhere it resolves
input, steps, outputs, meta, secrets, varsevery step
selected, user, md, now, today, uuid, ulidevery step
iteration, loop, and the loop's binding names (as — one name, or one per array in the { zip, as } form — or item when as is omitted)inside a forEach step's other fields only — not in the forEach source itself, which is resolved before any item is bound

An expression marked optional is never rejected: a | default (or | now) anywhere in the filter chain, or a fallback chain ending in '', 0 or false ({{ input.maybe || '' }}), tells the push it is meant to be absent. So does anything the push can't decide — a dynamic bracket key like {{ steps[input.branch].output }} is left to the run-time check.

Because the check is about what a definition says, a workflow you pushed before this check existed can be rejected on its next push even if you didn't touch the offending step. Such an expression was already failing its step at run time; the push just tells you sooner.

Marking a reference optional ​

Say so at the expression, with | default or ||:

{{ steps.x.output.result | default: '' }}   # renders '' when x was skipped
{{ input.nickname | default: 'friend' }}
{{ input.title || 'Untitled' }}
{{ input.tag | upper | default: 'none' }}   # position in the chain doesn't matter
{{ input.note | default }}                  # bare `default` renders ''
{{ steps.x.output.flag || false }}          # typed false when x was skipped
{{ steps.x.output.count || 0 }}             # typed 0 when x was skipped

This is the only escape hatch, and it is per-expression: there is no workflow-level or step-level setting that makes unresolved references tolerated. A reference to an optionally-skipped step's output needs | default: or a fallback — without it the step fails when that upstream step was skipped. Use || false (not | default: 'false') when the consumer wants a boolean, and || 0 (not | default: '0') when it wants a number: the filter's argument is a string, and a non-empty string is truthy everywhere downstream.

A path that resolves is never a failure, whatever its value: a resolved null renders as typed null in single-expression mode and the string "null" in interpolation; a resolved "" renders empty in both.

The engine's own path fields ​

forEach sources, selector paths and runs counts are bare paths, not templates, and they follow the same rule: the path must resolve, and there is no fallback syntax for them. A forEach source that resolves to an empty list iterates zero times, as always — but one that doesn't resolve at all, or that resolves to something which isn't a list, fails the step. If a list is genuinely optional, make the step that produces it emit an empty one.

An unresolved forEach source yields to the step's own gate: when the step has a runIf the engine can evaluate at step level (it reads no loop variable) and it is false, the step is skipped rather than failed — so runIf: "steps.sync.ok" beside forEach: "steps.sync.body.added" skips when sync did.
