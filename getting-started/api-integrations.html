API Integrations ​

Primitive lets you securely proxy requests to external APIs. You configure integrations with the CLI — Primitive stores your API keys server-side so your client code never sees credentials.

Defining an Integration ​

Create a TOML config file for each external API:

toml
# config/integrations/weather-api.toml
[integration]
key = "weather-api"
displayName = "Weather API"
accessRule = "true"

[requestConfig]
baseUrl = "https://api.weather.com/v1"
allowedMethods = ["GET"]
allowedPaths = ["/forecast/*", "/current"]

[requestConfig.defaultHeaders]
X-API-Key = "{{secrets.WEATHER_API_KEY}}"

Key Configuration ​

  • integration.key — Unique identifier your app uses to call the integration
  • Availability — not a TOML key. Every integration you push is callable straight away; take one out of service with primitive integrations disable and put it back with primitive integrations enable. Retiring one for good is a third verb, primitive integrations archive — see Retiring an integration
  • integration.accessRule — Required. An expression deciding who may call this integration; see Who Can Call It
  • integration.timeoutMs — Request timeout in milliseconds
  • requestConfig.baseUrl — The external API's base URL
  • requestConfig.allowedMethods / requestConfig.allowedPaths — Whitelist of HTTP methods and paths your app can call (trailing-* wildcards supported)
  • requestConfig.defaultHeaders — Headers sent on every request; use {{ secrets.KEY }} for credentials or {{ vars.KEY }} for non-secret values
  • requestConfig.staticQuery — Query parameters appended to every request

Who Can Call It ​

An integration forwards requests upstream with your API key attached, so every integration states who may invoke it. accessRule is a CEL expression, evaluated on every call, in the same language and identity context as a workflow's access rule:

toml
[integration]
key = "stripe"
displayName = "Stripe"
# Only your own workflows may call this one — no client can.
accessRule = "fromWorkflow('create-checkout-session') || fromWorkflow('create-portal-session')"

What you can write:

ExpressionAllows
"true"Any signed-in app member
"fromWorkflow()"Any workflow's integration.call step, and no direct client call
"fromWorkflow('daily-digest')"Only that one workflow
"isMemberOf('staff', 'core')"Members of that group
"user.userId == 'usr_123'"One specific user
"md.self.access.clientCallable == true"Whatever the integration's own metadata says

App admins and owners always pass, as they do for every other rule in Primitive. A workflow running as system carries no user identity, so only fromWorkflow(...) (or the integration's own metadata) can authorize it — a user.userId rule is false there.

A caller the rule turns down gets a 403 with errorCode: "INTEGRATION_ACCESS_DENIED" before any request goes upstream, and the integration does not appear in that caller's integration list at all.

An integration with no rule denies everyone but admins and owners. Clearing accessRule (removing the key from the TOML, or setting it to "") locks the integration down rather than opening it up.

Existing integrations need a rule

Integrations created before this rule existed have none stored, so after upgrading, member calls and workflow steps against them are refused with INTEGRATION_ACCESS_DENIED. For each one:

bash
primitive config pull                  # writes integrations/<key>.toml
# add accessRule to [integration] — "true" restores the previous open behavior
primitive config push

primitive integrations get <key> tells you which of your integrations still have no rule.

Referencing Secrets and Vars ​

Credentials live in your app's secrets store; non-secret config values live in its vars store. Reference either from the integration config the same way — {{ secrets.KEY }} or {{ vars.KEY }} — for example, an API key in a default header and a non-secret account ID in a query param:

toml
[requestConfig.defaultHeaders]
Authorization = "Bearer {{secrets.WEATHER_API_KEY}}"

[requestConfig.staticQuery]
account = "{{vars.ACCOUNT_ID}}"

Both resolve server-side when the request is proxied and are never exposed to your client code. They diverge in two ways worth knowing: a {{ secrets.KEY }} reference is checked when you save the integration — naming a secret that doesn't exist fails the save — while a {{ vars.KEY }} reference isn't validated at save time, so a nonexistent var just leaves the literal placeholder unresolved at call time. And request previews and logs redact any value that resolved from a secret, but never one that resolved from a var — vars aren't secret, so they stay visible. Set a secret with primitive secrets set; a var is a key in vars.toml, applied with primitive config push. See App Secrets for the full management workflow.

Syncing Configuration ​

Integration files ride the same config loop as every other service — Configuring Primitive Services covers it in full:

bash
# Initialize config directory
primitive config init

# Push integration config to server
primitive config push

# Test the integration
primitive integrations test weather-api

Calling from Your App ​

ts
const response = await client.integrations.call({
  integrationKey: "weather-api",
  method: "GET",
  path: "/forecast/san-francisco",
  query: { units: "metric" },
});
console.log(response.status, response.body);
swift
let response = try await client.integrations.call(IntegrationCallRequest(
  integrationKey: "weather-api",
  method: "GET",
  path: "/forecast/san-francisco",
  query: ["units": "metric"]
))
print(response.status, response.body ?? "")

Error Handling ​

Failed calls throw a typed error — branch on its code:

ts
try {
  await client.integrations.call({
    integrationKey: "crm",
    method: "POST",
    path: "/contacts",
    body: { email: "user@example.com" },
  });
} catch (error) {
  if (isJsBaoError(error)) {
    switch (error.code) {
      case "INTEGRATION_NOT_FOUND":
        break; // 404, also fires for status != active
      case "INTEGRATION_REQUEST_INVALID":
        break; // 400/413/422 (method/path/body)
      case "INTEGRATION_PROXY_FAILED":
        break; // upstream timeout/network/malformed
      case "ACCESS_DENIED":
        break; // 401/403 (client auth)
      case "INVALID_ARGUMENT":
        break; // missing integrationKey
      case "OFFLINE":
        break; // SDK in offline mode
    }
  }
}
swift
do {
  _ = try await client.integrations.call(IntegrationCallRequest(
    integrationKey: "crm",
    method: "POST",
    path: "/contacts",
    body: ["email": "user@example.com"]
  ))
} catch let error as JsBaoError {
  switch error.code {
  case .integrationNotFound:
    break // 404, also fires for status != active
  case .integrationRequestInvalid:
    break // 400/413/422 (method/path/body)
  case .integrationProxyFailed:
    break // upstream timeout/network/malformed
  case .accessDenied:
    break // 401/403 (client auth)
  case .invalidArgument:
    break // missing integrationKey
  case .offline:
    break // SDK in offline mode
  default:
    break
  }
}

CLI Reference ​

An integration is defined in integrations/<key>.toml and applied with config push; the integrations commands read and test what is there.

bash
primitive config create integration my-api       # Scaffold integrations/my-api.toml
primitive config push --only integration/my-api  # Create or update it on the server
primitive integrations list                      # List all integrations
primitive integrations get my-api                # View integration details
primitive integrations test my-api               # Test the integration
primitive integrations logs my-api               # View recent call logs
primitive integrations disable my-api            # stop serving the proxy now
primitive integrations enable my-api
primitive integrations archive <integration-id>  # retire it (soft delete; ID from list)

An integration's availability is server-owned: it is not a TOML key, and disable/enable are its only writers, so config push cannot put an integration you took out of service back into it. A file that still carries a status line fails the push with a message naming the verbs.

Retiring an integration ​

An integration is active, inactive or archived, and the three words mean three different things:

StateHow you get thereWhat it means
activecreate, config push, primitive integrations enableserving the proxy
inactiveprimitive integrations disabletemporarily out of service; enable puts it back
archivedprimitive integrations archive (or a plain admin-API DELETE)retired — the delete lifecycle, not availability
bash
primitive integrations list                            # the ID column is the argument
primitive integrations archive <integration-id>        # confirms first; -y skips the prompt
primitive integrations archive <integration-id> --json # the server's envelope on stdout

archive addresses an integration by its ID — the ID column of primitive integrations list — not by the key its TOML file is named for.

archive is the soft delete: the row is kept so its history still resolves, and it goes on holding its integrationKey — so a later config push cannot re-create an integration under that key. primitive integrations enable refuses an archived row, and there is no un-archive. To reclaim the key, hard-delete the row: remove integrations/<key>.toml and run a confirmed primitive config push --prune (or hard-delete it in the console), then add the file back and push.

The confirmation is the repo default: it prompts before the call, --yes/-y skips it, and on a pipe or in CI without --yes it exits 1 telling you to re-run with --yes rather than acting unasked.

An integration can carry a regression suite the same way prompts and workflows do: test cases are TOML files in a sidecar directory beside the integration — integrations/<key>.tests/<case>.toml — applied by config push like the rest of the config tree. primitive config fields integration lists the case file's keys; deleting a case is removing its file and running primitive config push --prune. The file's name is the case's identity — config pull writes it back under that name, and renaming the file renames the case rather than creating a second one.

A case's inputVariables is the request the run issues, at the top level with no wrapper key: method, path, headers, query, and the body — body, or form for form-urlencoded, or bodyMode plus multipartFields for multipart. A key the case omits falls back to the integration's own configuration, exactly as a live call does (defaultMethod for the method, / for the path, defaultHeaders/staticQuery merged either way), so a case against a POST-only integration can name just its path and body. There is no configured body: a case that authors no body or form sends none.

toml
# integrations/plaid.tests/mints-a-link-token.toml
[test]
name = "mints a link token"
inputVariables = '''
{
  "method": "POST",
  "path": "/link/token/create",
  "body": { "client_name": "Acme", "products": ["transactions"] }
}
'''
expectedOutputPattern = "link-production-"

Delete an integration by removing its file and running primitive config push --prune.

The Inbound Half: Webhooks ​

An integration is the outbound half — your app calling a third-party API. Most real integrations also need the inbound half: a webhook the provider calls when something happens on their side (a payment succeeds, a repo is pushed), which triggers a workflow. The two are configured separately — the outbound call here, the inbound webhook as a webhook trigger on a workflow, with signature verification. Integrating a service like Stripe or GitHub usually means setting up both.
