Primitive CLI ​

The Primitive CLI (primitive) is a command-line tool for managing your Primitive applications. It handles authentication, app configuration, user management, and provides access to guides and documentation.

Why Use the CLI? ​

Use the CLI to manage app configuration, invite users, inspect data, and automate deployments. Coding agents can read feature guides with primitive guides get <topic>.

Installation ​

Install the CLI globally:

bash
pnpm add -g primitive-admin

This installs the primitive command globally on your system. pnpm is the recommended package manager; npm install -g primitive-admin works too. Install with one manager only — installing with both leaves two global copies and whichever comes first on your PATH wins.

Updating ​

When a newer release is available, the CLI prints an update notice with the command for the package manager that owns the copy you are running — for example pnpm add -g primitive-admin@latest for a pnpm install and npm i -g primitive-admin@latest for an npm one. If it finds a second global copy installed by the other manager, it names that copy's path so you can remove it.

Authentication ​

Before using most commands, you need to authenticate:

bash
primitive login

This opens your browser. After you sign in with Google, the console shows what the login asks for: the apps it reaches, what it can do and how long it lasts. Nothing is granted until you press Approve; Deny ends the command with an error. One login covers every environment on the server you sign in to, and an environment on another server keeps a login of its own — see Project Configuration and Environments below for where it is stored.

Inside a project a login is pinned to the project's apps, and a command on any other app is refused with APP_NOT_PINNED; when that app is one of the project's environments, the error names the primitive -e <env> login that covers it. Admin Tokens explains the default scope, pins, protection levels and CI sessions.

To sign in to every app you are an admin of, ask for it explicitly. The approval page warns that the login reaches all of your apps, including protected ones:

bash
primitive login --app all

After you approve, login prints the scope, the apps by name, every environment it signed in to and the environments on other servers that need their own login. Outside a project there is no list of apps to pin a login to, so primitive login needs --app all or --app <ids>. Some commands need a step-up — see Scoped logins and step-ups. If a command stops with Your login predates scoped sessions and can no longer be refreshed. Run 'primitive login' to sign in again., run primitive login.

login authenticates against the active environment's server. Inside a project it uses the selected environment's apiUrl — pick the environment with -e <env>. Outside a project it uses the default server, which you can point at a local or custom server with the PRIMITIVE_SERVER_URL environment variable:

bash
primitive -e prod login                                       # a named environment's server
PRIMITIVE_SERVER_URL=http://localhost:8787 primitive login    # a custom server, no project config

To check your current authentication status:

bash
primitive whoami

whoami shows who a command run from this directory acts as, and where it goes: the environment, the server and where that server came from, and the app. It also shows the session's kind, scope (full when unrestricted) and pinned apps, and while you hold a step-up, the step-up's scope and apps and when it ends. Add --json for the same fields as an object.

To log out:

bash
primitive logout

logout ends the session on the server, not only on this machine: the refresh token it held is refused from then on, and the local credentials are cleared. An access token the session already issued keeps working until it expires (at most an hour). A step-up ends with it, at once. If the server can't be reached, logout keeps the local credentials and exits with an error, so running it again retries the revocation.

Every environment on the login's server — committed or a child app — uses the one login, so login and logout in any of them act on all of them, and say which:

text
✓ Signed out of: dev, staging, feature-x

Gotchas:

  • A server older than the CLI ignores a login's pins and signs you in to every app. The CLI then stores nothing and exits with an error naming the apps it asked for; run primitive login --app all against such a server.

Scoped logins and step-ups ​

A login can be limited to some scopes and pinned to other apps, so the token on this machine can do less:

bash
primitive login --scope read,write --app <app-id>

The scopes are read, write, admin, data:read and data:write; --scope <list> and --app <ids> take comma-separated lists. Without --app, a scoped login in a project is pinned to the project's apps, like a plain one. The approval page names the apps you asked for, marks a protected one and says what the scopes allow.

A write to a protected app and the operations that need admin take a step-up, a short session stored beside your login; Stepping up says which operations and how long it lasts. A refused command prints the step-up it needs:

bash
primitive login --step-up --scope write --app <app-id>
primitive login --step-up --scope admin

--step-up needs --scope and a login to build on. The step-up is pinned to the environment's app unless --app <ids> names others, or --app all asks for an unpinned step-up for platform routes. Google asks you to sign in again only for a step-up holding admin, and the approval page marks the request as a step-up. Your login keeps working beside it: a command refused for lacking admin, or refused by a protected app, retries once with the step-up. It cannot be refreshed; ask for a new one when it ends. primitive token --step-up --scope <list> --app <ids> prints a step-up instead of storing it, always after approval in the browser.

Project Configuration and Environments ​

Primitive CLI config is project-scoped. When you run primitive init or any CLI command inside a directory containing primitive/config.json (the CLI walks up from the current working directory looking for it), the CLI operates against the named environments declared in that file.

my-app/
├── primitive/
│   └── config.json         # committed — environment definitions
├── .primitive/
│   └── credentials.json    # gitignored — one login per server
├── src/
└── package.json

Two files, two purposes:

  • primitive/config.json is committable. It defines named environments and an optional default. Your whole team targets the same apps because the file is checked in.
  • .primitive/credentials.json is gitignored. It holds the logins primitive login writes, one per server, each kept under the URL of the server that issued it. Never check it in.

primitive init scaffolds both files for a new project: it writes a dev environment bound to the app it just created, and stores the session you logged in with as that server's login — so a freshly scaffolded project is already in project mode and signed in. Init signs in before the app exists, so that login covers all of your apps; run primitive login inside the project to limit it to the project's apps.

Because the lookup walks up, one project config can serve several clients. primitive init my-app --platform web,ios scaffolds a web client and a native client of the same app into web/ and ios/, with the config — including the shared database schemas — and the git repository at the root; running init inside such a repository adds another client to that same app. See One App, Several Clients.

Run app commands from your project directory. See Outside a Project for commands that work before setup.

Git Worktrees ​

A linked git worktree of a signed-in project is signed in too. Commands there use the main checkout's .primitive/credentials.json for the same project, so a worktree you create with git worktree add runs commands straight away:

bash
git worktree add ../my-app-feature -b feature
cd ../my-app-feature && primitive whoami    # the main checkout's login

The rest of .primitive/ stays per worktree, so each worktree keeps its own environment selection and child apps. primitive login in any worktree signs them all in, and primitive logout in any worktree signs out every worktree of the repository that holds the project.

Gotchas:

  • Sharing the login needs git 2.31 or newer. With an older git, a worktree has a login of its own and needs primitive login.
  • A worktree of a bare repository, or one whose main checkout does not contain the project, keeps a login of its own.
  • A .primitive/credentials.json copied into a linked worktree is not used. login and logout name it; delete it.

Named Environments ​

A single project usually targets multiple backends — a development app for day-to-day coding, a staging app for QA, a production app for your customers. Each environment in primitive/config.json binds an apiUrl and an appId together so "which server" and "which app" always travel as one unit:

json
{
  "version": 1,
  "defaultEnvironment": "dev",
  "environments": {
    "dev":  { "apiUrl": "http://localhost:8787",       "appId": "app_..." },
    "prod": { "apiUrl": "https://primitiveapi.com",    "appId": "app_..." }
  }
}

The file also holds settings every environment shares. functionSources lists directories outside the config tree that server functions may import from, such as code your web client already runs:

json
{
  "version": 1,
  "functionSources": ["web/src/engine", "../shared/src"],
  "environments": { "dev": { "apiUrl": "http://localhost:8787", "appId": "app_..." } }
}

Entries are relative to the project root and may climb with .. up to the git repository root. See Sharing code with your app.

Manage environments with the env subcommands:

bash
# Add an environment to an existing project (primitive init creates the project)
primitive env add dev  --api-url http://localhost:8787      --app-id app_dev123
primitive env add prod --api-url https://primitiveapi.com   --app-id app_prod456

# List all environments and inspect one
primitive env list
primitive env show prod

# Point THIS machine at an environment (writes .primitive/local.json, which is
# gitignored — switching backends never dirties a tracked file)
primitive env use dev

# Delete an environment (also clears its credential slot, so re-adding the
# same name later cannot reuse stale tokens)
primitive env remove staging

--app-id is required: every environment names exactly one app, which is what lets selecting an environment select its app with nothing else to keep in step.

primitive env use <name> also attaches a child app: a name that is neither a committed environment nor already registered on this machine is looked up among the current environment's children, and a match is registered and selected in one step.

After adding an environment, sign in to it with primitive -e <name> login, which signs in every environment of the project on that server. An environment added to a server you are already signed in to uses that login, but the login is pinned to the apps the project named when you signed in, so a command on the new environment's app is refused with APP_NOT_PINNED naming that same primitive -e <name> login. primitive init signs in the initial dev environment during setup. For automation, see API Tokens for CI and Servers.

A login is only sent to the server that issued it. When an environment's apiUrl changes — on another branch, for example — the environment uses the login of its new server, or needs primitive -e <name> login there.

How the Active Environment Is Resolved ​

Every command resolves an active environment in this order — the first match wins:

  1. --env <name> flag on the command itself
  2. PRIMITIVE_ENV environment variable (handy for CI)
  3. This machine's selection in .primitive/local.json, written by primitive env use
  4. defaultEnvironment in primitive/config.json — the committed team default
  5. The only environment defined — if there is exactly one, it's used automatically
  6. Otherwise the CLI errors and asks you to choose

primitive env use changes this machine’s selection in gitignored .primitive/local.json. The committed defaultEnvironment is the team default for a fresh clone.

A broken selection is never papered over. If .primitive/local.json is corrupt, or names an environment that no longer exists, env list and env show say so instead of quietly falling back to the default — the fix is to delete the file or re-run primitive env use <name>.

Name environment entries after the backend/app pair they bind (prod, prod-test, alpha), not after a build stage. A build stage is a separate axis: which front end you are building is chosen at build time, and the two cross more often than you would expect.

So in CI you can do:

bash
PRIMITIVE_ENV=prod primitive config push

…or override per-command without changing the default:

bash
primitive functions list --env staging
primitive config push --env prod

Using the Active Environment in a Web Build ​

A web app built with Vite resolves the same environment, in the same order, through the primitiveEnv() plugin that primitive-admin exports. (An iOS app resolves it in its Xcode build phase.)

ts
// vite.config.ts
import { defineConfig } from "vite";
import vue from "@vitejs/plugin-vue";
import { primitiveEnv } from "primitive-admin/vite";

export default defineConfig({
  plugins: [primitiveEnv(), vue()],
});

The plugin runs at config time for vite dev, vite build and vitest alike:

  • It defines VITE_APP_ID, VITE_API_URL, VITE_WS_URL, VITE_APP_NAME and VITE_PRIMITIVE_ENV on import.meta.env, and sets the same keys in process.env so tests read them too.
  • PRIMITIVE_ENV selects the environment for one run, as with any command; primitiveEnv({ primitiveEnv: "prod" }) fixes it in the config.
  • An explicit VITE_* value in a .env file or your shell wins, with a warning naming the key.
  • VITE_EXPECTED_PRIMITIVE_ENV pins a Vite mode to one environment.

Scripts get the same answer from resolvePrimitiveEnv({ root }), which throws a PrimitiveEnvError whose kind names the problem (missing-config, unknown-environment, …). vite is an optional peer dependency of primitive-admin, so installing the CLI never pulls Vite in.

The scaffolded template's vite.config.ts imports the same plugin from primitive-app/vite. It needs no edit.

Switching Apps Inside a Project ​

There is no "currently active app" anywhere but the environment. The active app is whatever the resolved environment's appId says it is, and every environment has one. To point an environment at a different app, edit its "appId" in primitive/config.json. primitive whoami and primitive env show report the app the next command will act on.

Outside a Project ​

With no project config anywhere up the directory tree there is no environment, so there is nothing for an app-scoped command to target. Only the commands that run before a project exists work there:

  • primitive init creates a project — the app, primitive/config.json with a dev environment bound to it, and that environment's credentials.
  • primitive login --app all signs in against the default server (or PRIMITIVE_SERVER_URL); primitive logout clears that session.
  • primitive apps delete <app-id> deletes an app with that login and its step-up, against the same server: the default server, or PRIMITIVE_SERVER_URL when it is set. A login another server issued is refused and never sent.
  • primitive whoami shows the user and server those commands use: the server PRIMITIVE_SERVER_URL names or the default server, the login that server issued or PRIMITIVE_TOKEN, and no current app. With no login it says so and names the server to sign in to.
  • primitive guides, primitive skill, help and --version work anywhere; outside a project primitive guides serves the guides for the default server.

Everything else — apps list, apps get, users list, env add, config pull, … — exits non-zero with an error that names the missing primitive/config.json and points at primitive init. --env outside a project fails the same way, --app and PRIMITIVE_SERVER_URL do not create an environment, and no flag redirects a command at another project's tree or app: to work on an app, run the command from inside the project whose environment names it.

bash
primitive apps list
# No primitive/config.json found in /tmp/scratch or any parent directory. … Run 'primitive init' to create one.

cd ~/code/my-app && primitive apps list    # the project's environment names the server and app

To delete an app you are not working on — a stale prototype, say — sign in and step up outside any project, then delete it by id. The confirmation names the server:

bash
export PRIMITIVE_SERVER_URL=https://my-server.example.com    # omit for the default server
primitive login --app all
primitive login --step-up --scope admin --app 01HXY...
primitive apps delete 01HXY... --confirm "Old Prototype"

Inside a project, app-scoped commands accept --app <id> to act on another app on the environment's server instead of the environment's own app.

# View app details

App settings — access mode, auth providers, CORS, member invitations, and more — live in app.toml and change by editing that file and pushing it. There is no command that sets an app setting directly; see TOML Is the Only Write Path.

bash
# Show the current server-effective settings
primitive apps get

# Fetch settings into app.toml, edit one, then apply just the app settings
primitive config pull --only app
primitive config set app app.mode=invite-only
primitive config push --only app

Child Apps ​

A child app is a throwaway copy of the current environment's app for one branch. Child apps covers when to use one, the branch loop and what starts empty; this section is the command reference.

bash
# Create a child app for a feature branch, register it on this machine and
# select it
primitive apps children create feature-x

# Push the current tree into it (create selected it)
primitive config push --yes

# List the current environment's app's children (slug, owner, branch,
# created, last activity, expiry)
primitive apps children list

# Show one child, and how it relates to this machine
primitive apps children get feature-x

# Delete a child and its local state (prompts unless --yes)
primitive apps children delete feature-x --yes

create accepts --branch <name> (default: the checkout's current git branch), --idle-days <n> (7–30, default 30), --no-secrets (skip copying secrets), --no-use (create without selecting it on this machine), and --json. create pushes nothing: it ends with the push to run next, so you can set the child's own config var values (below) before its first push. delete needs no step-up, because every child app is internal.

The exit code tells a script whether a child now exists, and --json prints one document whose nextStep is the command to run next:

Exit codeMeaning
0The child is created and registered on this machine.
1No child was created.
2The child was created but couldn't be registered on this machine. Run primitive env use <slug> to attach it.

The Vue and Swift app templates wrap this in child:up and child:down — see Child apps for parallel work.

With a child selected, config pull/push/diff act on the child itself — reading and writing the parent's shared tree, as above — but every apps children command acts on its parent: running apps children create with a child selected makes a sibling of that child, not a grandchild.

A child starts without the parent's users and databases, and an invite-only parent's child admits nobody until you add accounts directly — see Child apps. A database created on the child has its own id, so anything that names a parent database's id (a var, a record) needs the child's id instead.

A child uses its server's login and step-up, which reach it through the parent's pin; it has no login of its own. primitive -e feature-x login signs in every environment on that server, and primitive logout in any of them signs them all out.

A child's own config var values ​

The shared tree's vars.toml holds the parent's values. Vars whose value belongs to one app — its database ids, a webhook URL containing its app id, the origin its OAuth flow returns to — go in the child's own file beside it, vars.<slug>.override.toml, in the same flat KEY = "value" form:

toml
# primitive/dev/vars.feature-x.override.toml
REFERENCE_DB_ID = "01M4VFW6B2WANJXA58FG810HDX"
WEB_ORIGIN = "https://feature-x.example.com"
bash
# With the new child selected, give it its values before its first push
primitive config set vars WEB_ORIGIN="https://feature-x.example.com"
primitive config push --yes

With the child selected, config push sends vars.toml with the override's keys replacing or adding to it, config diff compares against those same values, and config pull writes the child's differing values into the override, never into vars.toml. The parent and every other child never read the file. It is machine-local: primitive init and the app templates git-ignore primitive/*/*.override.toml, and apps children delete removes it with the child's other local state.

Gotchas

  • The override can replace or add a var, not remove one: every key in vars.toml is pushed to the child too.
  • Functions cache the config vars they read for their current version. If you add an override to a child whose functions are already pushed, they keep the old values until you push a new version of each function that reads them (any change to its code or TOML) or its running instance is recycled; config push prints a note when this applies. Set a new child's values with config set vars before its first push, so it gets them before its functions. See Referencing Vars.

A teammate reaches a child another admin created by attaching it:

bash
primitive env use feature-x

A name that's already a committed environment or an existing local entry is just selected, as usual. Otherwise env use looks the name up as a child slug of the current environment's app: if found, it registers the child on this machine and selects it, in one step; the child uses the current environment's login. It refuses an unknown slug, and refuses a known one only when that child's app id is already registered here under a different name.

primitive apps list shows parent apps only; add --all to include children:

bash
primitive apps list --all

Deleting a parent app with children is refused, naming them; delete the children first, or delete them together:

bash
primitive apps delete <app-id> --confirm "My App" --with-children

--with-children deletes each child, then the parent, stopping before the parent on the first child it can't delete — rerun the same command to finish. A plain login deletes the children; the parent needs an admin step-up unless it is internal.

Managing Databases ​

On the CLI a database is a db3. Create, read and operate databases from the command line — for seeding, scripts and support. Add --json to any of them for scripting:

bash
# Create a database, typed from the start; sync off and held by the app
primitive db3 create "Q3 launch" --type workspace
primitive db3 create "Gradebook" --type classroom --sync off --custodian app

# Show one database; list the databases a custodian holds
primitive db3 get <db3-id>
primitive db3 list --custodian user:<user-id>
primitive db3 list --custodian app
primitive db3 list --limit 50 --cursor <cursor>   # page a long list

# Record, model and file counts and a size
primitive db3 stats <db3-id>

# Delete a database with its records and files
primitive db3 delete <db3-id>

--type names a type from your db3-types/ directory, --sync off makes the database server-only, and --custodian (app or user:<user-id>, admins only) says who holds it. See Sharing and Access.

Give a database a type, and read the schema it has:

bash
# Attach a type to an untyped database, and show the type it has
primitive db3 type attach <db3-id> workspace
primitive db3 type get <db3-id>

# Each model's fields as declared and as written; or export them as a type file
primitive db3 schema <db3-id>
primitive db3 schema <db3-id> --toml --output primitive/dev/db3-types/imported.toml

type attach installs the type whole or not at all, and a database's type never changes once set. schema --json prints the answer as JSON, and --output <file> (with --toml) writes the file instead of printing it. See Schemas and Codegen.

Follow a type's push to every database of it:

bash
primitive db3-types list                  # the app's types and their revisions
primitive db3-types get workspace
primitive db3-types push-status workspace # each database's outcome in the latest push
primitive db3-types push workspace --retry <run-id>   # push again to the databases that push refused or failed

Change who can reach a database:

bash
# Turn sync off (server-only) or back on
primitive db3 sync set <db3-id> off
primitive db3 sync get <db3-id>

# Share it with every member of the app: reader, read-write, or none
primitive db3 app-access set <db3-id> reader
primitive db3 app-access get <db3-id>

# Hand it to the app, or to a user
primitive db3 transfer <db3-id> app

See Sharing and Access for what each one changes.

Records ​

Read and repair records directly. Writes go through the same path as every client's, so subscribed devices see the change live, and the type's rules run on every write:

bash
# What models a database holds, and one model's fields and indexes
primitive db3 records models <db3-id>
primitive db3 records describe <db3-id> <model-name>

# Query, count and aggregate records in a model
primitive db3 records query <db3-id> <model-name> --filter '{"status":"open"}' --limit 50
primitive db3 records query <db3-id> <model-name> --sort '{"createdAt":-1}' --limit 50
primitive db3 records query <db3-id> <model-name> --include '[{"model":"users","type":"refersTo","sourceField":"assigneeId","as":"assignee"}]'
primitive db3 records count <db3-id> <model-name> --filter '{"status":"open"}'
primitive db3 records aggregate <db3-id> <model-name> --op sum --field qty --group-by symbol

--sort orders query results by one or more fields: 1 ascending, -1 descending, with key order as precedence. Use --limit (100 records by default, up to 10,000 per page) and --cursor to page through query results; a cursor continues only the sort it came from, so repeat the same --sort with it. --filter-file reads a filter from JSON or TOML.

aggregate --op takes count, sum, avg, min or max. Supply --field except for count, and repeat --group-by for grouped results.

--include loads related records (refersTo, hasMany, refersToMany) under _related on each row, and includes nest up to 3 levels. A hasMany leg reads at most 1,000 related rows per request, and a page whose _related would pass 8 MiB is refused with DB3_PAGE_TOO_LARGE rather than ending early. See Loading related records.

bash
# Create or replace a record (--id is optional — a ULID is generated when omitted)
primitive db3 records save <db3-id> <model-name> --data '{"name":"gear","qty":5}'

# Update the record whose unique field matches instead of creating one
primitive db3 records save <db3-id> <model-name> --upsert-on sku --data '{"sku":"G-1","qty":5}'

# Merge fields into a record that must already exist
primitive db3 records patch <db3-id> <model-name> <record-id> --data '{"qty":6}'

# Add to numeric fields atomically
primitive db3 records increment <db3-id> <model-name> <record-id> --data '{"qty":2}'

# Delete a record (prompts unless -y)
primitive db3 records delete <db3-id> <model-name> <record-id> -y

# Apply several operations in one atomic batch from a file
primitive db3 records bulk <db3-id> --data-file ops.json -y

save creates or replaces a record; patch changes only the fields you pass and fails when the record doesn't exist, so it never creates one by accident. Pass --data-file <path> instead of --data to read the fields from a file. A write that breaks the type is refused with an error naming the model and field.

Each operation in ops.json names its model and action (create, patch, delete or upsert), and a validation failure writes nothing. An upsert addresses a record by a unique constraint the model declares rather than by id: the record holding the constraint's values gets data merged in, or is created when none does. The summary reports the upserted count, and --json lists each upsert's record id and whether it was created:

json
{
  "operations": [
    { "model": "transaction", "action": "create", "id": "01JQZ8M2V5K3H9T4N6R7B1C0DE", "data": { "amount": 5 } },
    {
      "model": "transaction",
      "action": "upsert",
      "constraint": "transaction_plaid_identity",
      "data": { "plaidItemId": "it_1", "plaidTransactionId": "tx_9", "amount": 12.5 }
    }
  ]
}

Failed commands exit nonzero and report a stable error code. See Reading and Writing Records for record semantics and Batches for the batch limits.

Indexes ​

bash
# List a database's indexes, register one for a field, and drop it
primitive db3 indexes list <db3-id>
primitive db3 indexes register <db3-id> --model contacts --field email
primitive db3 indexes drop <db3-id> <index-name> -y

# A composite index is a unique constraint: it needs --unique and a name
primitive db3 indexes register <db3-id> --model contacts --field accountId --field email --unique --name account_email

db3 indexes list prints each index's name, model, fields, whether it is unique, and its origins: declaration when the type declares the field indexed or unique, named when it was registered. Registering or dropping needs the database's owner, or an app owner or admin; an index the type still declares cannot be dropped. A refusal prints its code, and for DB3_INDEX_NOT_UNIQUE each key records share. See Indexes.

primitive db3 inspect <db3-id> reports a database's write progress and the writers it has seen — a starting point when a device's writes aren't arriving.

Bulk loads ​

bash
# Load a directory of <model>.ndjson[.gz] files, one record per line
primitive db3 ingest <db3-id> --input ./records -y
primitive db3 ingest <db3-id> --input ./records --no-wait   # start it and return; --timeout <seconds> bounds the wait
primitive db3 ingest <db3-id> --input ./records --mode refresh -y

# Follow or stop a load
primitive db3 ingests get <db3-id> <session-id>
primitive db3 ingests abort <db3-id> <session-id>
primitive db3 ingests list <db3-id>

--mode merge (the default) changes only the records the input names; --mode refresh also deletes every record of those models the input doesn't name. Rows the database refuses are skipped and counted; primitive db3 inspect <db3-id> --refused <session-id> lists them with their reasons. Omit -y to keep the confirmation prompt — a load can't be undone. See Bulk loading.

Export and import ​

bash
# Write a database's records, declaration and blobs to a directory
primitive db3 export <db3-id> --output ./orders-export
primitive db3 export <db3-id> --output <dir> --no-blobs   # records only

# Create a new database from it (in this app or another), or load it into an existing one
primitive db3 import ./orders-export
primitive db3 import ./orders-export --into <db3-id> -y

# Keep the database's id, so anything that stored it still finds it
primitive db3 import ./orders-export --keep-id
primitive db3 import ./orders-export --title <title> --type <type>   # or --untyped; --no-blobs skips the files

An import creates a database of the export's type with its records and blobs, under a new id. --keep-id creates it under the exported id instead, which must be free in the target app: import into another app, or delete the original first. Every check runs before anything is written.

Managing Collections ​

Collections group databases and carry shared access — see Collections for the concept. The CLI manages them end to end:

bash
primitive collections create "Q1 Reports" --description "Quarterly reports"
primitive collections create "Q1 Reports" --owner user@example.com   # admin token: that user is custodian and owner
primitive collections list                       # collections you belong to (--all: every one, admin only)
primitive collections get <collection-id>
primitive collections documents add <collection-id> <db3-id>     # add a database; also: remove, list
primitive collections for-document <db3-id>      # collections a database belongs to

# Members: users, and groups as group:<group-id>, each at a role
# (owner, manager, editor, contributor, viewer)
primitive collections members add <collection-id> <user-id> --role editor
primitive collections members add <collection-id> group:engineering --role viewer
primitive collections members set-role <collection-id> <user-id> manager
primitive collections members list <collection-id>     # principals with their roles
primitive collections members remove <collection-id> <user-id>

primitive collections delete <collection-id>     # its databases are preserved

# Scripted removal: -y skips the prompt, --json reports what was removed
primitive collections documents remove <collection-id> <db3-id> -y --json
primitive collections members remove <collection-id> group:engineering -y --json
primitive collections delete <collection-id> -y --json

An app-user token creates a collection for its caller; an assigned console admin can set --owner to create one for another member. Default collection rules give the creator management access.

Removal commands ask for confirmation. Pass -y in automation; --json changes output formatting but does not confirm deletion. Deleting a collection preserves its databases.

Inspecting Live Connections ​

Answer the most common sync question — "does the server think this user is connected, and to what?" — by listing the live connections it believes exist. Pass exactly one selector: a database or a user.

bash

primitive connections list --document <db3-id>

# Every live connection for a user (databases, channels, and the user's

Each row is a connection’s subscription to a database or channel. One connection may appear in several rows. Abruptly disconnected clients may remain listed briefly until their entries expire.

Configuration ​

primitive config round-trips your app's configuration between the server and a directory of TOML files. It is the only way the CLI writes configuration — Configuring Primitive Services states that rule and covers the loop, the directory layout, and the app.toml settings in full. This is the command reference.

bash
primitive config init                          # create the directory (auto-resolves primitive/<env>/)
primitive config pull                          # download current server config as TOML
primitive config fields <type>                 # a type's TOML keys, types, required flag, and defaults
primitive config create <type> <key>           # scaffold that object's file from the defaults
primitive config set <object> <path>=<value>   # set a scalar in a file, comments preserved
primitive config diff                          # preview entities that would be created, changed, or removed
primitive config push                          # apply local changes
primitive config push --only <selector>[,...]  # apply just these objects
primitive config push --dry-run                # walk the full push, reported but not applied
primitive config push --prune                  # also delete managed entities whose local TOML you removed
primitive config revert                        # restore the config directory from a pre-pull snapshot

fields, create, and set are local — they read and write files and call no API. <object> on set is <type>/<key>, app, or vars; --only selectors are <type>/<key>, app, or var/<key>. So the scripted form of a one-field change is two commands:

bash
primitive config set function/order-intake function.description="Order intake"
primitive config push --only function/order-intake

All of these read and write the selected environment's directory, and only that one. config revert --list enumerates snapshots and --snapshot <id> restores a specific one.

A plain config push only creates and updates. --prune also deletes managed entities (ones a prior pull recorded in sync state) whose local TOML you removed, confirming each with a fresh read; --force skips that drift check, --yes skips the one confirmation prompt, and --dry-run previews the deletions. See The Sync Loop for how prune decides what's eligible.

Push replaces each configured object with the contents of its file. Review deletions before pushing. Server changes appear as DRIFT or CONFLICT; pull to incorporate them, or use --force deliberately to overwrite them. See The Sync Loop.

primitive apps get is the read view of the app-settings half of the loop — the [app], [auth], [cors], and [invitations] tables in app.toml — as the server is running them, alongside the app's id and name. Fetching, comparing and applying that file are config commands scoped to it:

bash
primitive apps get                # render current server-effective settings
primitive config pull --only app  # write server settings to app.toml
primitive config diff --only app  # per-field differences between app.toml and the server
primitive config push --only app  # apply the edited file

The config commands read the selected environment's committed tree; apps get reads the server.

Validation, preview fidelity, and push convergence (re-running a failed push adopts entities missing from sync state by key) are covered in The Sync Loop.

CLI diagnostics (success/warning/info messages) are written to stderr; only structured data (--json output) goes to stdout, so primitive config diff --json | jq works without any extra redirects.

Advanced Features ​

Admin sessions ​

Every sign-in — a CLI login, a web-admin login, an admin step-up, a CI session — is a session on the server. List yours:

bash
primitive auth sessions list
primitive auth sessions list --json

The list shows each session's kind (cli, web, step-up or ci), its name (a CI session's; — for the others), its scope (full when unrestricted), the apps it is pinned to (— for none), its status (active, pending while an approved login waits for the CLI to collect it, revoked or expired), when it was created, last refreshed and expires, and which one is this login's (CURRENT). It is paginated with --limit (25 sessions a page by default, at most 100) and --cursor.

Revoke one — for example a login on a machine you no longer use:

bash
primitive auth sessions revoke 01J9ZK3M4N5P6Q7R8S9T0V1W2X

The revoked session's refresh fails from then on, and a revoked CI session's token fails on its next request; your other sessions are unaffected. revoke asks for confirmation (pass --yes to skip it — required when not running in a terminal). Revoking this login's own session also clears its local credentials.

App Secrets ​

Store app-level secrets server-side and reference them from integrations and webhook triggers as {{secrets.KEY_NAME}}, or read them in a server function with ctx.secret — your client code and repo never see the values:

bash
primitive secrets set OPENAI_API_KEY --value sk-...
primitive secrets list
primitive secrets delete OPENAI_API_KEY

Resource Metadata ​

Read and write resource metadata category values — category definitions (schema, readRule, writeRule) are managed through primitive config, not this command:

bash
primitive metadata set user 01HXY... profile --data '{"tier":"pro"}'
primitive metadata get user 01HXY... profile --json
primitive metadata get-batch --resource user:01HXY...:profile,billing
primitive metadata list user 01HXY...                # every stored category on a resource
primitive metadata delete user 01HXY... profile      # idempotent
primitive metadata resolve user billing stripeCustomerId cus_ABC   # reverse lookup by unique value; a miss exits 0

Category definitions have their own read-only noun:

bash
primitive metadata-category-configs list             # every definition: schema, rules, version
primitive metadata-category-configs get user profile # adds the full schema JSON

Definitions are authored in metadata-category-configs/<resourceType>.<category>.toml and applied with primitive config push. Delete one by removing its file and running primitive config push --prune — stored values are not deleted and become unreachable, so delete them first (primitive metadata delete) if you need them gone.

bash
primitive config create integration my-api    # then edit and push
primitive integrations list

Prompts ​

LLM prompts are defined in prompts/*.toml and run from a server function; these commands read and trial them:

bash
primitive config create prompt my-prompt  # then edit and push
primitive prompts list
primitive prompts get <prompt-id>         # IDs from the list
primitive prompts execute <prompt-id>     # a diagnostic: runs even when inactive
primitive prompts disable <prompt-id>     # take it out of service now
primitive prompts enable <prompt-id>
primitive prompts archive <prompt-id>     # retire it (soft delete; ID from list)

Availability is not part of the file — see Availability is server-owned. disable takes a prompt out of service — ctx.prompts.run refuses it with PROMPT_NOT_EXECUTABLE — and enable puts it back. prompts execute is an admin diagnostic and runs an inactive prompt on purpose, which is how you trial one before enabling it. archive is the third verb and a different act — see Retiring an object: archive vs prune.

Who may reach a prompt is decided by the access gate of the server function that runs it.

Server Functions ​

Operate the server functions a config tree pushes as functions/<key>.toml; the code itself is authored and shipped through primitive config push. The primitive functions verbs:

  • Read — list (filter with --status active|inactive|archived), get, configs, and activate to point a function at an earlier version
  • Run — invoke <key> inside the request, start <key> as a task run (--wait to wait for it, --run-key so a repeat replays the existing run)
  • Runs and logs — runs, runs steps, runs wait, runs terminate, logs
  • Authorize — authorize <key> runs only a function's authorize method and prints the decision; --cases/--cases --all runs its case file(s) — see Testing authorize From the CLI
  • Generated types — codegen (--check for CI, --lang swift for Swift invokers)
  • Availability — disable, enable, archive (see Availability is server-owned)

Operating a function covers each verb — which take the key and which the function id, who a run executes as, timeouts and exit codes — and Debugging a failing function walks through a failure.

Function Triggers ​

A function's webhook and cron triggers are declared in its TOML and shown by primitive functions get <function-id>. primitive functions triggers operates them by the function's key, and a cron entry also by its name:

bash
primitive functions triggers events <key>       # recent webhook deliveries (accepted/rejected/duplicate)
primitive functions triggers rotate-secret <key> --secret "{{secrets.STRIPE_WEBHOOK_SECRET_NEXT}}"
primitive functions triggers test <key> --payload '{"type":"charge.succeeded","data":{"id":"ch_1"}}'
primitive functions triggers test <key> --payload '{…}' --deliver   # post it for real
primitive functions triggers verify <key> --header 'Stripe-Signature: t=…,v1=…' --body-file captured.json
primitive functions triggers fire <key> <name>        # start the cron entry's task run now
primitive functions triggers disable <key> <name>     # take the entry out of service
primitive functions triggers enable <key> <name>      # put it back, or resume an error pause

triggers test previews a signed request without sending it. See Previewing Deliveries.

Add --deliver to send the request and run the function. --json reports dispatched, refused, or unconfirmed.

Use triggers verify to check a captured delivery’s signature. Pass its headers and original body; see Checking a captured delivery.

A cron entry whose fire fails hard is paused; triggers enable resumes it. primitive functions runs lists the task runs its fires started.

Retiring an object: archive vs prune ​

Archive removes an object from active use without deleting it permanently. Remove its TOML file and use config push --prune for permanent deletion. See Archive vs prune.

Email Templates ​

Manage overrides for the emails Primitive sends. See Email Templates for the built-in types, template variables, the override file's [template] shape, and the override/revert model.

bash
primitive config create email-template email-sign-in  # scaffold the file
primitive config push --only email-template/email-sign-in

# List all email types and their override status
primitive email-templates list

# View the current template for an email type
primitive email-templates get email-sign-in

# See available template variables for an email type
primitive email-templates variables email-sign-in

# Send a test email using the current template
primitive email-templates test email-sign-in

Revert to the built-in default by deleting the file and running primitive config push --prune. Each command takes an email type — a built-in or a custom kebab-case type you registered — and primitive email-templates variables <type> lists the variables that type substitutes at send time.

Scripting ​

For automation and scripting, most commands support --json output:

bash
primitive apps list --json
primitive users list --json

List commands return the same JSON envelope:

json
{
  "items": [],
  "hasMore": true,
  "nextCursor": "01HXY..."
}

items holds the rows, hasMore says whether there is another page, and nextCursor is present only when there is. Read a list with jq '.items[]'.

Paginated commands accept --limit and --cursor and return one page per call. Other lists return all items with hasMore: false. Check primitive <noun> list --help for supported options.

bash
# The first page, then the next
primitive users list --json --limit 50
primitive users list --json --limit 50 --cursor 01HXY...

To get the current access token for use with other tools:

bash
primitive token

primitive token refreshes the active token when needed. Use it in scripts that call authenticated APIs.

To hand a script or an agent a token that can do less than your login, print a narrower one:

bash
primitive token --scope read --app <app-id> --ttl 15m

It shares your login's session and lives --ttl (at most 1 hour, and never longer than your login). When the request is no wider than your login, the token prints with no browser. A wider one — a scope your login lacks, or a pin carrying more than read — opens the approval page first, and the token it prints cannot be refreshed. Only the token goes to stdout, and nothing is stored.

API Tokens for CI and Servers ​

For a CI pipeline, a deploy script or a server-side job, create a CI session: a named admin token for that job, pinned to the apps it works on. Admin Tokens covers which scopes to give it. Create it from your own CLI login, inside the project:

bash
primitive auth sessions create --name deploys --scope read,write --app <app-id>

primitive auth sessions create opens the approval page in the browser and then prints the token once. --app takes one or more app ids, comma-separated; CI sessions covers how long the session lives and what it can't do.

Store the token in your CI's secret store, and run the CLI with it in PRIMITIVE_TOKEN from a checkout of the project. No credentials file is needed:

bash
PRIMITIVE_TOKEN=<token> primitive config push

The token works for the admin and app APIs and WebSocket connections, within its scope and pins. primitive auth sessions list shows CI sessions with their names; revoke one with primitive auth sessions revoke <session-id>.

Gotchas:

  • primitive auth sessions create needs your own primitive login and is refused while PRIMITIVE_TOKEN is set. Unset the variable in the shell you create sessions from.
  • While PRIMITIVE_TOKEN is set it takes precedence over your stored login, and primitive logout is refused. End a CI session with primitive auth sessions revoke <session-id>.

You can also sign in as yourself without a browser: pipe a refresh token into login --token-stdin. Select the environment with -e <env> so login targets the right server (or, without a project config, point it at one with PRIMITIVE_SERVER_URL):

bash
primitive token --refresh | primitive -e <env> login --token-stdin

primitive tokens create --name <name> --user <userId> mints an app access token that signs the JavaScript client in as that one user with no browser — see Headless sign-in with an access token. It isn't a CI credential; for a CI pipeline use primitive auth sessions create above (see CI sessions).

Non-Interactive primitive init ​

primitive init (the command behind npx create-primitive-app) prompts for anything it needs — app name, target platforms, access mode. For scripted setups, put the answers in a .primitive-init.toml file in the directory where you run it (or point at one elsewhere with --config <path>), and init skips every prompt:

toml
action = "create"            # or "use-existing" (then set app_id instead of app_name)
app_name = "My App"
platform = "web"             # "web", "ios", "web,ios", or ["web", "ios"] (defaults to web)
dir = "my-app"
access_mode = "invite-only"  # "public", "domain", or "invite-only"
dev_port = 5173              # optional; dev server port for a web project
skip_install = false         # optional; same effect as --skip-install
server = "https://primitiveapi.com"  # optional; same effect as -s/--server

platform names one client or several: a list scaffolds each client into its own directory under one project root. -p/--platform takes the same list on the command line (--platform web,ios), and the interactive prompt is a multi-select.

Adding a client to an app that already exists is its own action, valid inside a directory whose primitive/config.json is found by the walk-up above:

toml
action = "add-client"        # the app comes from the selected environment
platform = "ios"
dir = "ios"                  # optional: one platform defaults to its own name

An add-client run names no app of its own — no app_name, app_id, access_mode, invite_emails or allowed_domains — and it writes no nested .primitive/, no nested .git/ and no commit. See One App, Several Clients.

dev_port sets the web project's dev server port without the port prompt: init pins it in vite.config.ts and .env, and adds http://localhost:<port> to the app's CORS allowed origins and redirect URIs. skip_install skips the dependency install; --skip-install requests the same thing, and passing the flag always skips even if the config says otherwise.

server selects the backend for initialization; -s/--server takes precedence. Before an unattended run, sign in to that server. Inside a project, select a matching environment with -e <name>.

For unattended runs, log in ahead of time.

Run primitive init --help for the full key list (dev port, invite emails, allowed domains, overwrite behavior).
