Tasks and Requests ​

Every server function runs under one of two runtimes: the request runtime, which answers inside the call, or the task runtime, which starts a run that can sleep for hours or days. This page covers the two runtimes and how a task run behaves — steps, resets, budgets, run status and run error codes. How a caller picks one is on Invoking and Triggers.

Runtimes ​

The invocation method selects the runtime. The function’s TOML does not set it:

DoorRuntime
functions.invoke / POST functions/{key}request
A webhook deliveryrequest
functions.start / POST functions/{key}/starttask
ctx.functions.start from inside a functiontask
A cron firetask

Cron schedules start tasks. Webhook deliveries run within a request; use ctx.functions.start to hand longer work to a task.

  • the request runtime runs the code inside the call and hands back its result. It has to finish inside a request.
  • the task runtime starts a run, hands back a run id immediately, and lets the code sleep for hours or days in between.

The same function can be invoked or started as a task:

toml
# primitive/dev/functions/order-sync.toml
[function]
key = "order-sync"
entry = "functions/order-sync/index.ts"
access = "true"

ctx.runtime ​

Every invocation carries the runtime it is running under, beside the trigger that fired it:

ts
export default defineFunction(async (input, ctx) => {
  // "request" | "task" — set by the platform from the runner in use.
  console.log(ctx.runtime, ctx.trigger.kind);
});

ctx.trigger.kind identifies what started the function. ctx.runtime identifies whether it runs in a request or as a task.

assertRuntime ​

Some code only makes sense one way round. A function that sleeps for a day is not something anyone should be calling with invoke and waiting on. Say so in the code, and the platform refuses the call:

ts
import { assertRuntime, defineFunction } from "primitive-functions";

// At MODULE SCOPE: every invocation under the wrong runtime is refused before
// a line of the handler runs.
assertRuntime("task");

export default defineFunction(async (input: { since: string }, ctx, step) => {
  await step.sleep("cooling-off", "24 hours");
  return { sweptAt: Date.now() };
});

It works inside the handler too, and inside a step.do body, if only part of the code needs the guarantee:

ts
export default defineFunction(async (input, ctx, step) => {
  if (input.slow) assertRuntime("task");
  // …
});

A mismatch throws a typed FunctionRuntimeError (name is "FUNCTION_RUNTIME_REFUSED", with runtime and required on it) and the platform settles the invocation as status: "failed" with errorCode: "FUNCTION_RUNTIME_REFUSED" and a message naming both runtimes and the verb that takes the one it needs:

json
{
  "status": "failed",
  "errorCode": "FUNCTION_RUNTIME_REFUSED",
  "error": "FUNCTION_RUNTIME_REFUSED: this function is running under the request runtime and requires the task runtime. Start it as a task: functions.start(...) from a client, or POST .../functions/{key}/start."
}

The same settlement on a task run: the run ends failed, its errorCode is FUNCTION_RUNTIME_REFUSED, and status.error.message leads with the code. Either way the invocation log records it.

Use assertRuntime to require a runtime; no TOML setting selects it.

step under each runtime ​

The handler receives step as its third argument under both runtimes:

Task runtimeRequest runtime
step.doRuns once and the result is memoized; a replayed slice does not re-run it.Runs the body inline. Nothing is persisted and nothing is replayed.
step.sleep / step.sleepUntilHibernates. Nothing runs and nothing is billed while it waits; hours and days are fine.Really waits, when the remaining request budget covers it. When it does not, the invocation fails with errorCode: "FUNCTION_RUNTIME_REFUSED", naming the step, the duration and the budget left.
step.waitForEventWaits for the event.Fails with FUNCTION_RUNTIME_REFUSED: nothing can deliver an event to an invocation that has to return now.

A step unavailable in the selected runtime fails with FUNCTION_RUNTIME_REFUSED. Use a task for work that needs long waits or events.

These rules also apply to webhook handlers, which use the request runtime.

The handler with step:

ts
import { defineFunction } from "primitive-functions";

export default defineFunction(async (input: { orderId: string }, ctx, step) => {
  const charged = await step.do("charge", async () => {
    return ctx.api.documents.get({ documentId: input.orderId });
  });

  // Hibernate. Nothing is running — and nothing is billed — while it waits.
  await step.sleep("cooling-off", "24 hours");

  return { orderId: charged.documentId, confirmedAt: Date.now() };
});

Task runs ​

A task run is a sequence of slices: the engine runs the handler, hibernates it at a sleep, and wakes it again. The sections below cover starting one from code, keeping its steps safe to replay, what it may spend, and reading what it did.

Step discipline ​

The engine re-executes your handler from the top on every resume and replays each completed step.do from its stored result instead of running it again. Two rules follow, and both matter:

  • Put every side effect inside step.do. A charge, an email, a write made outside a step runs again on every resume. Completed step results are reused on resume. Interrupted or retried steps may run again, so make their side effects idempotent.
  • Do not branch on anything nondeterministic between steps. Date.now(), Math.random() or a fresh read at the top level can take a different path after a resume, and the engine then looks for steps that are not there. Read such values inside a step, so the value is stored with it.

Starting a task run from a function ​

ctx.functions.start starts another function as a task run from inside a running one — from an invocation, from a task run's slice, and from a webhook- or cron-fired run alike:

ts
const started = await ctx.functions.start("digest-page", { userIds }, {
  runKey: `digest-${date}-${page}`,
});
// { runId, runKey, instanceId, status: "running" }

The response includes the run ID. Reusing a runKey returns the existing run, including a failed one, with existing: true. To retry failed work, use a new key and the same input.

Share synchronous logic through ordinary TypeScript imports. Use ctx.functions.start when the work should run as a separate task.

The callee's access expression is not evaluated. Your own gate was the authorization, and your code chose the callee, so a function can start one the invoking member could not call themselves. Decide who may reach the tree in the access expression of the function at the top of it.

Run ownership follows the original caller. That member can inspect and terminate child runs. A trigger-started task and its children run as the app and are inspected by admins.

Which document the run is keyed under. A task run is addressed by a context document plus its run key, so a nested run always has one, resolved in this order:

  1. the contextDocId you pass;
  2. else the parent run's context — so a whole tree shares one;
  3. else the root caller's root document, which is the default a member's own start uses;
  4. else fn:<the root function's id> — a synthetic context, the same shape a cron-fired run's cron:<triggerId> has. This is what a trigger-rooted tree gets, and it is why a run key there is a singleton per root function across fires rather than per member.

If the parent context is unavailable, resolution continues with the remaining choices. The resolved context appears in the run status.

Both runKey and contextDocId are bounded at 100 characters.

Inside the child, ctx.trigger.kind is "function" and carries the parent function's key and its run id (null when the parent was a request invocation, which writes no run row). ctx.user names the tree's root caller, and ctx.user is null when a trigger rooted the tree — nobody called it.

Nesting is bounded at 4 levels below the root. A fifth nested start fails with 409 FUNCTION_NEST_DEPTH_EXCEEDED.

Each run is listed under its own function — primitive functions runs <digest-page-id> — with FIRED BY function and a PARENT column naming the function that started it.

Process users in pages ​

This example processes one page. Read it inside step.do, then start a child task with a unique run key:

ts
const page = await step.do("load-users", () =>
  ctx.users.list({ limit: 50, cursor: input.cursor })
);
await step.do("start-page", () =>
  ctx.functions.start("digest-page", {
    userIds: page.items.map((user) => user.userId),
  }, { runKey: `digest-${input.date}-${input.page}` })
);

To process every user, repeat with page.nextCursor until no next cursor is returned. Give each page its own step names and run key. Keep page reads and child starts inside steps so a resume reuses their results. Bound concurrency within each child with pMap.

A failed child does not fail its siblings. Retry that page with the same input and a new run key.

Reporting back ​

Choose how the task exposes its result:

  • Return output. Read it with getStatus, waitFor, or primitive functions runs wait. Results remain on the run for 45 days.
  • Save state. Write records or notifications inside a step for results the app should retain. Return what the step wrote — { wrote: true, recordId } or { wrote: false, reason } — so a caller reading the run's output learns the outcome without a second lookup.
  • Send a live message. Use ctx.users.send for connected clients. Pair it with saved state when offline clients need the result later.

Task completion does not automatically send a WebSocket message. There is no feature that pushes a run's settlement to the client; the three options above are how a task reports back.

Learning that a task's writes have arrived. A client with the context document open does not need the run status for this: it already holds a subscription on the model the task writes, and that subscription's callback fires when the task's write syncs in, the same as any other write to an open document. Use the run status only to learn whether the task finished and how — not to learn whether a particular write landed.

Telling the starter the run is done. Call ctx.users.send to ctx.user.userId as the run's last step, after the work it reports on has committed. A client connected right now gets it immediately. Because ctx.users.send never runs for a platform failure — ENGINE_*, FUNCTION_STALLED, a reset that exhausts retries — treat it as a push that arrives on the common path, and keep waitFor (or a getStatus poll) as the fallback that still answers when it does not.

Locks from a function ​

A function waits for a named lock with ctx.locks.withLock: it acquires the key, runs your closure while holding it, and releases it on the way out — on a normal return and on a throw alike.

ts
import { defineFunction } from "primitive-functions";

export default defineFunction(async (input: { itemId: string }, ctx, step) => {
  return ctx.locks.withLock(`ingest:${input.itemId}`, {
    ttlMs: 600_000,
    timeoutMs: 360_000, // a task can wait this long; a request must fit its budget
  }, async () => {
    await step.do("ingest", async () => {
      // …the work that must not overlap…
    });
    return { ingested: true };
  });
});

When the key is not free within timeoutMs, withLock throws an error named LOCK_TIMEOUT (its code is the same, and its details carry the holder's owner, holderKind, leaseExpiresAt and whether the acquire rate limit refused the last attempt) and never runs the closure. The closure's own error reaches your code unchanged after the release.

To branch on contention instead of failing, use ctx.locks.acquire and ctx.locks.release. acquire never throws for "not acquired": it answers { acquired: true, handle }, or { acquired: false, timedOut: true, … } with the last holder it saw.

ts
import { defineFunction } from "primitive-functions";

export default defineFunction(async (input: { itemId: string }, ctx, step) => {
  const lock = await ctx.locks.acquire(`ingest:${input.itemId}`, {
    ttlMs: 600_000,
    timeoutMs: 360_000,
  });
  if (!lock.acquired) return { skipped: true, heldBy: lock.owner };
  try {
    await step.do("ingest", async () => {
      // …the work that must not overlap…
    });
  } finally {
    await ctx.locks.release(lock.handle);
  }
  return { ingested: true };
});

The owner is the run. Unless you pass owner, both name ctx.runId, so a run never waits on its own hold: a later slice of the same run, or a second call on a key the run already holds, re-takes it at once with a fresh handle. When several triggers are coalesced into one run by a run key, pass the work that key stands for (owner: ctx.trigger.runKey ?? ctx.runId). Never a static string: two unrelated runs presenting one would re-enter each other's hold. For the same reason a withLock nested inside another on the same key re-enters, and its release frees the hold the outer closure is still inside — use distinct keys, or one wrapper. See Re-taking Your Own Lease for the full rule.

What a wait costs. The waiting happens on the platform: each attempt asks the server to hold the request for up to 30 seconds and answers the moment the key frees. A wait therefore uses no CPU and costs one platform call and one acquire attempt per half-minute. timeoutMs is at most 1 hour.

  • Under the task runtime each attempt is a step of its own, so the wait survives a reset or a deploy, the slice's clock is refreshed at every attempt and the wait never shortens the run. It is not a hibernation: the engine does not suspend a wait shorter than five minutes, so a waiting slice stays open. For coordination longer than an hour, put a step.sleep between ctx.locks.acquire calls.
  • Under the request runtime the whole wait has to fit what is left of the invocation's budget. A timeoutMs it cannot cover fails at once with FUNCTION_RUNTIME_REFUSED, before any attempt, naming the key and the budget left. A webhook delivery has 5 seconds in all, so a wait longer than that belongs in a task: hand the work over with ctx.functions.start.

The one-shot calls are there as well. ctx.api.locks.tryAcquire is a single attempt, and it takes waitMs too — the same route, waiting server-side for up to 30 seconds or the invocation's remaining budget, whichever is less. Under the task runtime make those calls live, outside step.do: a memoized acquire would hand a resumed slice the handle a previous slice was given, and that handle no longer works. ctx.locks takes care of this for you.

What resets a running task ​

A running task keeps the function version it started with. Pushing or activating another version does not change that run.

The platform can interrupt a task during maintenance or a runtime reset. It resumes the handler from the beginning, reusing completed step results. The interrupted step may run again and consume another retry attempt.

Make step bodies idempotent, and return values from steps instead of assigning them to outer variables. Cleanup in a catch must also be safe to repeat: an interruption does not necessarily mean the run has failed permanently.

Read the run’s final status to determine its outcome. Use functions runs steps to see progress; slice.resets, lastResetAt, and lastResetCause report interruptions.

Budgets in a task run ​

A task executes in slices. After a pause, the handler resumes from the beginning and reuses completed step results.

  • A slice begins with 10 minutes of wall-clock time. The platform refreshes that budget at step boundaries so each step begins with at least 5 minutes. A sequence of steps can continue for up to 12 hours before a pause.
  • If refresh is unavailable, the task pauses for a little over 5 minutes and resumes with a fresh slice.
  • Each slice allows subRequests of up to 10 000 and 5 minutes of active CPU. These budgets do not refresh. The platform pauses at a step boundary after half the subrequest allowance is used; exceeding CPU fails the run.
  • Keep individual steps within their budgets. A single long operation outside step.do receives no wall-clock refresh.

Use steps to divide work and step.sleep when the task needs to wait. For CPU-heavy work, a sleep longer than five minutes starts a fresh slice after hibernation. Output limits and outputSchema apply to the final result.

The run status includes a slice block with timing, refresh counts and progress: lastProgressAt is when the run last did something, such as starting or finishing a step; openStep and openStepStartedAt name the step it is inside (charge#0 is the first step.do("charge", …)); parkedAt is set while it waits. functions runs shows REFRESHES and LAST PROGRESS.

When a run's status settles ​

The platform records a task’s status and output when it finishes. Polling is not required to save the result.

running means the run is active or its final outcome is not yet known. It includes sleeping, retrying, and resuming after an interruption. You don't need a staleness timeout of your own: the platform ends a run that stops making progress.

A run that shows no progress for 30 minutes is ended failed with FUNCTION_STALLED. Starting or finishing a step, a failed attempt, a sleep and a new slice all count as progress. The 30 minutes start only once the open step's own timeout and the delay before its next retry have passed, so a step with a long timeout or retries.delay is waited for, not ended. Sleeping, waiting for an event and waiting out a retry delay never count as a stall. Once ended, the run reads failed on every read.

When a run fails ​

getStatus and waitFor resolve with status: "failed" for a failed run. Check the status and then read:

  • error.code: the failure category listed below.
  • error.message: the diagnostic.
  • error.name and error.details: optional additional information.

Use the code for programmatic handling. A failure before the handler could record logs may have a run error without an invocation log.

Run error codes ​

A failed run carries a code beside its message: run.errorCode on the run row, and error.code on the function run status both clients read. It is a closed set the platform owns, so you can branch on it rather than matching prose. It has no room for an outcome your own code expects.

For that, return a typed result instead of throwing: { ok: false, code, message } (shape it however suits the app) is a normal return value, read from output like any other result. Reserve throwing for what the handler did not expect — an uncaught throw settles the run FUNCTION_THREW. Inside step.do, throw only when the failure should spend one of the step's retries; a returned failure result is never retried.

For a terminal ENGINE_* failure, start a new run with a new runKey if the work should be retried. Keep side effects idempotent because the failed run may have completed some work. Report repeated platform failures.

ctx.runId, ctx.sliceId and ctx.trigger.runKey ​

A function can read which run it is, and which slice of that run it is running in:

ts
export default defineFunction(async (input, ctx, step) => {
  // The run this invocation belongs to — `null` for an `invoke`, which writes
  // no run row at all.
  ctx.runId;
  // The slice of that run. A task run is a sequence of slices: it changes when
  // the run hibernates and wakes, so it is how you tell a resume from a first
  // pass. `null` under the request runtime — a request invocation is not a
  // slice.
  ctx.sliceId;
});

Reading a task run step by step ​

functions runs answers at the level of the run: status, the runtime it used, start, end, the failure code. For a task run that is rarely enough — the handler's work is in its named steps, and what you want to know is which one it is on, which ones already finished, and where the time went.

bash
primitive functions runs steps <function-id> <run-id>

Each step comes back with its name, its kind (function.step for a step.do, function.sleep for a step.sleep or step.sleepUntil, function.event for a step.waitForEvent), its status, the idle GAP before it, and its duration. A step that is still executing reads running with the time it has been running so far — including a run that is asleep, whose function.sleep step stays running until it wakes. A step that threw reads failed with its message.

The rows are written as the run goes, so they are readable while it is still in flight, and they survive the hibernation of a step.sleep. A resumed run replays its completed steps from the engine's memo rather than re-running them: each step keeps one row, with the timing of the slice that actually executed it. A step that a platform deploy reset keeps that same one row too — it stays running, not failed, until the replay finishes it, and its duration then spans the reset rather than stopping at it. --json emits the same rows as JSON.

Ending a run that will not settle ​

bash
primitive functions runs terminate <function-id> <run-id>

The command stops the task and records terminated. If stopping fails, the run stays unchanged and the command reports an error; retry it. A run that already finished keeps its actual outcome. Open step records are closed when the run ends.

Ceilings ​

Every function runs under fixed platform ceilings. [function.limits] may lower any of them and can never raise one — a config asking for more simply gets the platform value.

A task run's output is held to the same 1 MiB and is kept on the run row for its life, so it outlives the engine's instance. Over roughly 10 000 characters it is stored by reference and still answered whole; a runs page holding many large outputs may be shorter than the limit you asked for and continue with a cursor.

A burst past the rate ceiling answers 429 with errorCode: "FUNCTION_RATE_LIMITED" and a Retry-After header. Buckets are per app and per function, so one function's traffic never consumes another's. A slot is taken only once a call is going to run: a caller your access rule rejects, or a request your inputSchema refuses, consumes none of the budget. When the limiter itself cannot be reached the call is refused with 503FUNCTION_RATE_UNAVAILABLE rather than run unmetered.

cpuMs is not a precise short timer: the runtime adds roughly two seconds of allowance. Use request timeoutMs when you need a strict wall-clock bound.

Outputs must fit within 1 MiB. Larger results fail with OUTPUT_TOO_LARGE; page results or save them and return an ID.

The wall-clock budget starts when the platform accepts the invocation, so loading a function's code the first time comes out of it — and the credential the sandbox carries expires on that same clock, never later than the answer the caller sees.

Timeouts stop further platform calls

After a timeout, the caller receives status: "timeout" and further platform calls from that invocation are denied. Already-started work may still have side effects, so do not assume a timeout undoes an operation.

Integration and prompt requests are bounded by the invocation’s remaining time. Their timeout codes are UPSTREAM_TIMEOUT and PROMPT_UPSTREAM_TIMEOUT. Use a task for work that exceeds a request budget.
