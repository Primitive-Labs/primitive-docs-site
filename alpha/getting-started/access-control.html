Access Control ​

Primitive uses CEL expressions for most access rules — rule sets, metadata rules, and the other resource gates covered below. A server function's call gate works differently: every version pushed today defines an authorize method that decides in code (see The authorize Method); a CEL access rule is its frozen predecessor, still evaluated for an already-deployed legacy version, but no longer available to a new or changed one (see Porting from access).

CEL in Sixty Seconds ​

A CEL expression is a one-line condition that evaluates to true or false:

toml
access = "user.userId != ''"                                  # any authenticated user
access = "hasRole('admin') || hasRole('owner')"               # app admins
access = "isMemberOf('01JD7E8V3K9Q2N6R4T5W0X1Y2Z')"                 # members of one group, by its id
access = "hasGroupRole('01JD7E8V3K9Q2N6R4T5W0X1Y2Z', 'manager')"    # the group's owner and managers
access = "size(memberGroups()) > 0"                           # member of any group
delete = "record.blobCreatedBy == user.userId"                 # a rule-set rule: the uploader

Standard operators work as you'd expect: ==, !=, <, &&, ||, !, in, plus functions like size(...). String literals use single quotes inside TOML double-quoted strings.

The Identity Context ​

Every access rule — a legacy function's access, a rule set, a metadata rule — sees the authenticated caller:

Variable / functionMeaning
user.userIdThe caller's user ID (empty string when unauthenticated)
user.roleThe caller's app role
isAnonymous()True when the caller has no account at all (an unauthenticated request). Write !isAnonymous() to require any signed-in member; relevant where anonymous access is possible, such as a public blob bucket
hasRole(role)True if the caller's app role is "owner", "admin", or "member" as given (app-level role — distinct from a database's owner permission)
isMemberOf(groupId)True if the caller holds any role on the group
hasGroupRole(groupId, role)True if the caller's role on the group is role or higher. Group roles rank owner, then manager, then member; a role name outside those three is refused when the rule is saved
memberGroups()The list of group IDs the caller holds a role on
isMemberOf(groupType, groupId)Deprecated: use isMemberOf(groupId). True if the caller belongs to that exact group
memberGroups(groupType)Deprecated: use memberGroups(). The list of group IDs of that type the caller belongs to

Use group membership for access rules: model teams, roles, and relationships as groups, then write rules against membership instead of hard-coding user IDs. isMemberOf('01JD7E8V3K9Q2N6R4T5W0X1Y2Z') stays correct as people join and leave; user.userId == '01ABC...' doesn't.

A legacy function's access rule uses this identity context, and so does every rule set below. Resource rules add values such as a blob bucket's record.blobCreatedBy. Feature pages describe those values. Groups and collections have no rule set — see Rule Sets: Governing Management Operations below.

A webhook's handshake when is the exception: it is CEL, but it is not an access rule — it matches the shape of a provider's request, not a caller, so none of this identity context is available there. See Provider Handshakes.

Rules can also read resource metadata. Secrets and config variables must be explicitly declared by the owning configuration before a rule can read them: a metadata category config lists them in secrets = ["KEY"] and vars = ["KEY"], and its rules read secrets.KEY and vars.KEY. A function's access gate has neither; see App Secrets. Missing values deny access, so use 'KEY' in vars or vars.?KEY for optional variables.

A Rule Sees Identity, Not Stored Data ​

Every function above answers a question about the caller — their role, their group memberships. A rule has no way to read a database record. So an entitlement you want the server to enforce — a paid feature, a role gate — can't live as a flag on a row: storing isSubscribed = true and checking it in a rule doesn't work, because the rule can't read the row.

Model the entitlement as group membership instead, which a rule can check, and admit it with requireMember in the function's authorize:

toml
# primitive/dev/functions/export-report.toml
[function]
key = "export-report"
entry = "functions/export-report/index.ts"
ts
// functions/export-report/index.ts
import { defineFunction, requireMember } from "primitive-functions";

export default defineFunction("export-report", {
  authorize: requireMember(() => "01JD7EB2C8H4K6M9P3R5S7T1V0"), // the subscribers group
  handler: async (input, ctx) => {
    /* ... */
  },
});

Maintain that membership from your billing source — a function fired by the provider's webhook adds a member when a subscription starts and removes them when it lapses (ctx.api.groups.addMember, ctx.api.groups.removeMember) — and every paid feature becomes a one-line membership check. Give that webhook function authorize: allowCallers({ webhook: true }): admitting only the webhook door keeps members from calling it over HTTP to grant themselves the entitlement, while the provider's verified deliveries still run it.

A function that needs to read the record itself — not just describe the caller — can check it directly in authorize via auth.db3, instead of modeling the entitlement as group membership. See The authorize Method, below.

The authorize Method ​

Give a function an authorize method, as part of the object form of defineFunction, when the decision needs more than caller identity — the specific resource the input names, a group or collection the caller belongs to, a record that names them. It runs after the input passes inputSchema and before the handler, reads the input and a read-only auth context, and decides who may proceed:

ts
// primitive/dev/functions/get-order/index.ts
import { allow, defineFunction, deny } from "primitive-functions";

export default defineFunction("get-order", {
  authorize: async (input: { shopDb: string; orderId: string }, auth) => {
    if (!auth.user) return deny("FORBIDDEN");
    const order = await auth.db3(input.shopDb, "orders").model("orders").get(input.orderId);
    if (!order) return deny("NOT_FOUND");
    if (order.userId !== auth.user.userId && !(await auth.isMemberOf("support-team"))) {
      return deny("FORBIDDEN");
    }
    return allow({ order });
  },
  handler: async (input, ctx) => {
    return ctx.auth.order; // loaded and checked by authorize — never re-read input.orderId
  },
});
toml
# primitive/dev/functions/get-order.toml
[function]
key = "get-order"
entry = "functions/get-order/index.ts"

A function that defines authorize takes no access rule — omit it from the TOML entirely. allow(resolved) hands the handler whatever you pass as ctx.auth, typed from what authorize returns; call it with nothing to resolve null. deny(code, message?, { expose? }) takes one of three codes:

CodeUse it for
FORBIDDENThe caller may not do this
NOT_FOUNDThe resource doesn't exist, or the caller shouldn't learn that it does
INVALIDThe input doesn't name a resource authorize can check

A denied caller gets 403 with errorCode: "FUNCTION_ACCESS_DENIED", whatever the code — the same answer whether the function is disabled, the resource doesn't exist, or the caller simply isn't allowed to see it. Pass { expose: true } on a NOT_FOUND deny to answer 404 with that code and your message instead; expose has no effect on the other two codes. There is no implicit allow: a throw, a timeout, a return value other than allow()/deny(), or a resolved value that isn't JSON-serializable all deny the caller the same uniform way.

authorize runs on every way into the function: an invoke or task start, a --as system run, a ctx.functions.start from another function, an agent's tool, context or history call, a webhook delivery, a cron fire and a database change. A webhook delivery, a cron fire or a database change has no caller to answer, so a deny records the fire's run as denied before the handler runs, with the code at the start of its error message (FORBIDDEN: …). primitive functions runs <function-id> lists it, the provider still gets its normal answer, and a cron fire still counts.

Doors at a Glance ​

Doorauth.userA deny

function (a nested start)The chain's root caller, the same at every level however deep the chain nests, or null when a trigger rooted it; auth.trigger.functionKey names only the parent directly above, never an earlier oneSame as http. The auth Context ​

authorize only reads — there's no write, secret, integration, or start call on auth, and reaching one any other way is refused:

MemberReads
auth.userThe caller, as { userId, email, role }, or null when no user started the call. On an agent's tool, context or history call it is the user the turn runs for; on a nested start, the user who started the first function in the chain; on a --as system run, the admin who started it, with role "admin"
auth.hasRole(role)Whether the caller's app role is exactly role ("owner" | "admin" | "member")
auth.memberships()Every group the caller belongs to, as { groupType, groupId, role }[]
auth.isMemberOf(groupId), auth.memberGroups(), auth.hasGroupRole(groupId, role)Derived from the same membership list, with the same one-argument forms as a CEL rule
auth.collections.resolveRole(collectionId)The caller's role on a collection, or null
auth.db3(db3Id, type).permissions() / .model(name).get(id) / .query(...)The caller's level on a database (reader, read-write, owner or null), and its records on the app's authority, typed the way ctx.db3 is
auth.configVar(name)A declared app config variable
auth.triggerWhat started the call — see Invoking and Triggers

Each authorize call has its own read budget, separate from the handler's: 16 reads, raised with [function.limits] authorizeReads up to 64 — past it, the caller is denied. Its CPU time is measured against a 50 ms target (raise it with authorizeCpuMs) and logged; a true runaway is stopped by the function's own cpuMs ceiling, the one that bounds the handler. authorize runs under the same wall-clock timeout as the call itself — past it, the caller is denied — and the handler keeps its own full budget after an allow.

Helpers ​

The platform ships helpers that return an authorize function, so most functions need only one line:

HelperResolvesUse it as
allowAnyone()nullauthorize: allowAnyone() — admits every caller the function's routes already admit, with no check
requireSignedIn(){ userId }authorize: requireSignedIn() — admits any signed-in caller
requireRole(role){ userId, role }authorize: requireRole("admin") — admits role or above, ranked owner > admin > member
requireMember(groupIdOf, role?){ userId, groupId, role }authorize: requireMember((input) => input.teamId, "manager") — admits a member of the group the selector names, at role or above
requireCollectionRole(collectionIdOf, minRole){ userId, collectionId, role }authorize: requireCollectionRole((input) => input.collectionId, "editor") — admits minRole or above on the collection the selector names
allowCallers(rules)variesadmits by the caller's door — see below

A selector reads the resource id off the input; an input that names no id denies INVALID. For example, requireMember admits a manager of the team the input names, and hands the handler the role it found:

ts
import { defineFunction, requireMember } from "primitive-functions";

export default defineFunction("team-report", {
  authorize: requireMember((input: { teamId: string }) => input.teamId, "manager"),
  handler: async (input, ctx) => ({ team: ctx.auth.groupId, as: ctx.auth.role }),
});

allowCallers admits by the door the call came through, rather than by resource:

ts
import { allowCallers, defineFunction, requireRole } from "primitive-functions";

export default defineFunction("daily-sweep", {
  authorize: allowCallers({ cron: true, manual: true, users: requireRole("admin") }),
  handler: async () => ({ swept: true }),
});
KeyTypeAdmits
webhookbooleanA verified webhook delivery, when true
cronbooleanA cron fire, when true
manualbooleanAn admin-started manual run, when true
db3booleanA database change trigger's run, when true
functionsstring[]A nested start from one of these parent function keys
agentsboolean | AuthorizeFnThe agent tool/context/history doors — true applies users's own decision there too; a function runs its own check
usersAuthorizeFnAn HTTP call — users's own decision

A door with no rule, including one added later, is denied.

Give agents: true to run the users rule on the agent doors too, so one check covers a function whether a member calls it directly or an agent's tool invokes it on their behalf:

ts
import { allowCallers, defineFunction, requireRole } from "primitive-functions";

export default defineFunction("send-reminder", {
  authorize: allowCallers({ agents: true, users: requireRole("admin") }),
  handler: async (input: { householdId: string }) => {
    await sendReminder(input.householdId);
    return { sent: true };
  },
});

An admin's own call passes users; a tool call driven by an admin's turn passes it too, because agents: true applies the same rule there. A tool call driven by a member's turn is denied on either door — give agents a function of its own instead when the tool should admit a caller the users rule would refuse.

Checking Again in a Long Task ​

A task run keeps the ctx.auth it was started with: every step, and every resume after a step.sleep, reads the value authorize resolved at the start, even if the caller has since lost access. Call ctx.reauthorize() before work that should still require it. It runs authorize again for the same user, with the same input, against current data, and resolves the fresh value without changing ctx.auth; a deny throws the error fail throws, with the deny's code:

ts
import { defineFunction, requireMember } from "primitive-functions";

export default defineFunction("team-digest", {
  authorize: requireMember((input: { teamId: string }) => input.teamId),
  handler: async (input, ctx, step) => {
    await step.sleep("collect", "1 hour");
    await ctx.reauthorize(); // throws FORBIDDEN once the caller has left the team
    return step.do("send", async () => ({ team: ctx.auth.groupId }));
  },
});

Uncaught, the deny fails the run. ctx.reauthorize() runs under the same read budget as any authorize call, and it works the same way in a request handler.

Gotchas

  • No admin bypass. Unlike an access rule, an authorize method gives owners and admins no implicit pass. Admit them with a line of your own — if (auth.hasRole("admin")) return allow(); — or with requireRole("admin").
  • Agent calls answer their own way. A deny on an agent's tool call is the tool error AGENT_TOOL_ACCESS_DENIED, and on a context or history call it fails the turn.
  • Deep in a chain, ctx.user is still the root. Inside a nested start, ctx.user names the member who started the first function in the chain, never whoever called the function directly above you. Trusting it to mean "this call's caller" several levels down is the same trap as trusting an external identifier. Scope by what this function's own authorize resolved into ctx.auth instead.
  • A task run's ctx.auth has a size limit. A task start whose authorize resolves more than 64 KB fails with 500 and errorCode: "FUNCTION_AUTH_TOO_LARGE" (a cron fire records a failed run instead), and anything over 16 KB logs a warning on each step of the run. Resolve ids and the rows the handler needs, not whole collections.
  • Omit access. A function that defines authorize doesn't take it: a new version pushed with both is refused FUNCTION_ACCESS_AMBIGUOUS. Delete the line — see Porting from access, below.
  • allow's value must be JSON-serializable. Pass ids and the rows the handler needs, not a live object or a function.
  • Write authorize above handler. ctx.auth is typed from what authorize returns, and TypeScript reads the definition top to bottom. With the handler first and an authorize arrow whose parameters have no type annotations, a read such as ctx.auth.classId fails to compile with 'ctx.auth' is possibly 'null' and Property 'classId' does not exist on type 'WriteAuthorizeBeforeHandler'. Move authorize above the handler; you don't need to add annotations.
  • A flagged inputSchema defaults closed. A version with authorize defaults additionalProperties: false on an inputSchema that doesn't set it — a caller sending an undeclared property is refused even though you never wrote the keyword. A schema whose anyOf/oneOf members declare their own properties is left open instead, since closing the root would refuse their keys too; push warns when that happens (see Push Lints, below).
  • A module-scope assertRuntime hides behind a uniform deny. authorize shares the handler's module scope, so a throw while it loads — a task-only function's module-scope assertRuntime("task") included — fails the authorize call itself: an authorize-error, denied 403 like any other refusal, not the clear FUNCTION_RUNTIME_REFUSED message calling it the wrong way gives a legacy function. Call it the runtime the function expects, or check with primitive functions authorize <key> --runtime request while debugging.

Porting from access ​

A function already running a legacy version keeps working under its stored access rule, unchanged, for as long as that version stays active — access is frozen, and the function create and update endpoints refuse one in the request body with FUNCTION_ACCESS_FROZEN. The moment you push a changed version, though, it must define authorize: a version with no authorize is refused FUNCTION_AUTHORIZE_REQUIRED, naming the function and showing the object form, and a version that defines authorize while its TOML still carries access is refused FUNCTION_ACCESS_AMBIGUOUS. There's no migration tool — port the CEL by hand from this table, then delete the access line:

CEL accessPort to authorize
hasRole(role)requireRole(role)
isMemberOf(groupId)requireMember(() => groupId)
"true"requireSignedIn()
"false"allowCallers({})

A mechanical port falls into two traps:

  • "true" is not allowAnyone(). access = "true" reads as "any signed-in caller" by convention, but a function with code that assumes a real user — reads ctx.user.userId, writes a record under it — admits an anonymous-session caller no differently from a signed-in one if you port it to allowAnyone(). Port it to requireSignedIn() unless the function truly has no use for who's calling.
  • The admin bypass is gone. A rule that denied some callers but admitted an owner or admin only through the bypass — not because the CEL expression itself said so — needs that case back explicitly: if (auth.hasRole("admin")) return allow();, or a requireRole threshold that covers it (it ranks owner > admin > member, so requireRole("member") already readmits everyone above, unlike hasRole's exact match). The same loss reaches triggers: access = "false" on a cron- or webhook-only function worked because a trigger fire never consulted it, but authorize runs on every door, triggers included — port it to allowCallers({ webhook: true, cron: true }), naming the doors it actually uses, and add manual: true too if you still want to start it by hand with --as system, which bypassed access the same way.

Testing authorize From the CLI ​

primitive functions authorize <key> runs only a function's authorize — no handler — through an admin-only endpoint, and prints what it decided:

bash
primitive functions authorize add-member --user u-teacher-1 --input '{"classId":"c-1","role":"student"}'
# allow  11 ms  3 reads

primitive functions authorize add-member --user u-student-1 --input '{"classId":"c-1","role":"student"}'
# deny  FORBIDDEN  "not a teacher of this class"  9 ms  2 reads

primitive functions authorize plaid-sync-all-sf --trigger cron
# allow  4 ms  0 reads
Flag
--user <id>auth.user: an app user id, or an @fixture alias. Default: no user
--role <role>Replaces auth.user.role for the check; the user's memberships are unchanged
--trigger <door>http (default), webhook, cron, manual, context, history, db3, function:<key> (a nested start from the parent <key>), tool or tool:<name>
--runtime <runtime>request or task; defaults to the door's own
--input <json>The input, as JSON; @fixture aliases resolve inside it. Default {}
--jsonOutput as JSON

The check reaches auth the way the named door would: --trigger manual needs --user (the admin who'd start the run) and defaults --role to admin; --trigger function:<key> needs the parent's key; a bare --trigger tool defaults the tool name to the function's own key. It is admin-only, never runs the handler, and is refused for another app's admin or a disabled app user (except on manual, which accepts a disabled one, same as a real --as system start) — see primitive functions invoke --user for the same idea against the handler.

Exit codes: 0 allow, 1 deny (an authorize-error — a throw, a timeout, a bad return value — included), 2 when no check ran: a refusal, or a version with no authorize to run.

Case Files ​

A JSON array beside the function, functions/<key>.auth.json, lists the checks the function should pass:

json
[
  { "name": "teacher may add", "user": "@teacher", "input": { "classId": "@class", "role": "student" }, "expect": "allow" },
  { "name": "student may not", "user": "@student", "input": { "classId": "@class", "role": "student" }, "expect": "deny", "code": "FORBIDDEN" },
  { "name": "cron is not a door here", "trigger": "cron", "expect": "deny" }
]

Each case takes name (required, unique in the file), the same fields as the CLI flags above (user, role, trigger, runtime, input — same defaults, trigger defaulting to http), and expect: "allow" or "deny". code — one of FORBIDDEN, NOT_FOUND, INVALID — only applies to a "deny" case, and only when the case cares which code; an authorize-error never matches a named code.

bash
primitive functions authorize add-member --cases      # run this function's own case file
primitive functions authorize --cases --all           # run every functions/*.auth.json in the tree

Either prints a table (CASE EXPECT GOT CODE MS READS RESULT, with a FUNCTION column added for --all) and a N passed, M failed line, and exits non-zero on any failing case. A case file is not a push gate — config push never reads it — so wire --cases --all into your own CI step for that.

Fixture Aliases ​

A case, or --user/--input on the command line, can name a value by alias instead of a literal id: "user": "@teacher", resolved from a fixture map; "@@" escapes a literal @. The map is never uploaded — config push sends only a function's TOML and the files its build reads, and the bundler refuses a build that reads a fixture map or a case file:

  • A committed environment keeps its map at primitive/<env>/auth-fixtures.json, beside its app.toml. Commit it like any other config file.
  • A machine-local environment — a child app — keeps its own map beside its sync baseline under .primitive/, named <slug>.auth-fixtures.json. It is never read from the parent's file, not even as a fallback: a child shares the parent's tree but not its data, so the ids its @teacher or @class alias names are the child's own. primitive apps children delete removes it with the child's other local state.

Testing a New authorize in a Child App ​

Write and test authorize against a child app before you push the change to a shared environment, the same way you would any other config change:

bash
primitive apps children create add-member-authorize   # creates, registers and selects the child
# give the child's auth-fixtures.json its own user and resource ids
primitive config push --yes                            # push the branch into the child
primitive functions authorize add-member --cases       # run the function's own case file against it
primitive functions authorize --cases --all            # …or every case file in the tree

Iterate — edit authorize, re-push, re-run --cases --all — until every case passes, then merge the branch and push the merged tree to the parent as usual:

bash
primitive env use <parent>
primitive config push --yes
primitive apps children delete add-member-authorize --yes

The parent's own auth-fixtures.json (if it has one) is untouched by anything you did on the child — each environment's map, and each case file's aliases, resolve against the environment --env/the current selection names.

Push Lints ​

config push warns, but still pushes, when a flagged function's build looks like a mistake:

  • authorize reads neither auth.user nor auth.trigger — so it decides the same for every caller and door. If anyone may really call it, say so with allowAnyone(); otherwise check the caller.
  • a string property in inputSchema has no maxLength, or an array has no maxItems — named by its path, so a caller cannot send an unbounded value or list.
  • inputSchema's root is left open because an anyOf/oneOf member declares its own properties — the closed-schema default above can't apply there, so set additionalProperties explicitly yourself.

It refuses the push outright when authorize admits anyone — allowAnyone(), or an allowCallers arm that is — and the version can write: it writes or sends through a family the manifest records, or declares an integration: or high-blast capability. Confirm that's deliberate with [function] public = true:

toml
[function]
key = "broadcast-alert"
public = true   # anyone may call this, and it sends a notification on purpose

Without it, the push is refused FUNCTION_PUBLIC_WRITE_UNDECLARED, naming the function and why it looks write-capable; require a caller instead — requireSignedIn() or allowCallers({ ... }) — if that was the mistake.

Failing a Call with Your Own Code ​

From the handler, call fail(code, message?) to end the call with a code of your own choosing:

ts
import { defineFunction, fail, requireSignedIn } from "primitive-functions";

export default defineFunction({
  authorize: requireSignedIn(),
  handler: async (input: { quantity: number }) => {
    if (input.quantity > 100) fail("ORDER_TOO_LARGE", "orders are capped at 100 units");
    return { accepted: input.quantity };
  },
});

The caller gets errorCode: "ORDER_TOO_LARGE" and error: "orders are capped at 100 units". Any non-empty string is a valid code. Called from inside authorize, fail throws and denies the caller the same uniform way instead.

Where Rules Appear ​

Every surface a signed-in member can reach that runs app-defined server-side code, manages a platform resource, or spends the app's credentials, and what happens on each when no rule is set. App owners and admins bypass every rule below — except a function's own authorize method, which gives them no implicit pass.

Rule Sets: Governing Management Operations ​

A function's authorize method decides who may run its code. Rule sets answer a different question: who may manage a platform resource directly — read or write a bucket's blobs. Groups and collections don't use one: every group and collection has the same fixed, platform-enforced roles (groups: owner, manager, member — Users and Groups; collections: owner, manager, editor, contributor, viewer — Collections), and primitive config push refuses a group-type-configs/ or collection-type-configs/ file. A rule those roles don't express belongs in a server function whose authorize uses requireMember or requireCollectionRole.

A rule set is a named bundle of CEL rules per management operation:

toml
# primitive/dev/rule-sets/bucket-access.toml
[ruleSet]
name = "bucket-access"
resourceType = "blob_bucket"

[rules.blob]
read = "!isAnonymous()"
write = "!isAnonymous()"
delete = "record.blobCreatedBy == user.userId"
bash
primitive config push --only rule-set/bucket-access

A blob bucket attaches a rule set by naming it with ruleSetName in its TOML, where it governs member access per operation — see Blobs and Files.

Two behaviors to know:

  • App owners and admins bypass rule-set evaluation — rules govern regular members.
  • A blob bucket with no rule set bound falls back to its preset. To deny an operation for everyone except admins, attach a rule set with that operation set to "false".

Testing Rules ​

Rule sets are versioned and testable — evaluate rules against simulated requests before deploying:

bash
# Dry-run a rule set against a simulated scenario
primitive rule-sets test <rule-set-id> --scenario '{"user": {"userId": "u-1"}}'

The same is available from the client as client.ruleSets.test(). For a function's authorize, the fastest loop is primitive functions authorize <key>, or invoking it as a specific app user — primitive functions invoke <key> --user <user-id> — or signing in as different test users.

Test gated states as a plain member. App owners and admins bypass function access gates, rule sets, metadata read/write rules, and bucket presets, so you can't exercise a locked or entitlement-gated state while signed in as one: a paywalled feature reads as open to an admin even when the gate is correct. That includes primitive functions invoke without --user, which runs as your own admin app user. Verify that a gate actually denies using a member test user. An authorize method has no such bypass to work around — invoking as an admin exercises it exactly as any other caller would.

Rules That Follow a Loaded Subject's Own Memberships ​

The functions above answer questions about the caller. A metadata category rule can also ask about a loaded subject — not just the caller — with memberGroupsOf(<subjectId>, '<groupType>'), a deprecated alias kept for metadata rules (new code checks membership with isMemberOf/memberGroups, one argument). This lets a rule follow a relationship graph: for example, grant a teacher access when a resource's metadata links it to a class they teach.

toml
# in a metadata category's readRule, with md.self.classLink staged
readRule = "memberGroupsOf(md.self.classLink.classId, 'class-students').exists(c, isMemberOf(c))"

The subject (argument 1) must be a literal path such as md.self.<category>.<key>, and the group type (argument 2) must be a literal string, both checked when the rule is saved.

Trusting External Identifiers ​

When the server acts on an identifier — opening a billing portal from a payment customer_id, calling a provider API on a user's behalf — it must not trust a value the client supplied. A caller could substitute someone else's id and act on their account.

Keep the authoritative user-to-external-id mapping in a database only your functions write, and resolve it inside the function from the authenticated caller — ctx.user — never from the function's input: query the mapping model filtered on ctx.user!.userId through ctx.db3, the same way a function reads and writes any records.

A function reads every record of the app on the app's own authority, so the scoping is the code's job: the filter on ctx.user is what keeps one caller from reaching another's row. The same rule holds for ids the app minted itself — a householdId, an itemId — once they arrive as function input rather than as something the server derived. "External" describes where the id came from into this request, not who defined it.

Patterns That Hold Up ​

  1. Default-deny, then open up. Start restrictive — requireRole("admin") for a function's authorize, hasRole('admin') for a rule set or metadata rule — and widen deliberately. A function pushed with no authorize is refused FUNCTION_AUTHORIZE_REQUIRED.
  2. Keep each group's id where the code finds it. The server assigns every group's id, so a rule names the id its create returned, and a function reads the id of the group a record belongs to from where the app stored it: size(memberGroups()) > 0 || isMemberOf('01JD7E8V3K9Q2N6R4T5W0X1Y2Z').
  3. Membership over IDs. Manage who's in the group, not the rules — rules referencing groups rarely need to change.
  4. Gate the function, scope in the code. authorize says who may run a function; which records or databases that caller may touch is the function's code, filtering on ctx.user.
  5. Reach for authorize when the check needs a resource. A CEL rule only sees who the caller is. The moment a check needs to read the record the input names, move it into an authorize method instead of working around CEL's limits.
