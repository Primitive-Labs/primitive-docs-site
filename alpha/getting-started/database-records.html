Reading and Writing Records ​

Records are read and written through the models generated from a database's type. The same operations exist in three places:

  • On a device, against a synced database. Your web or iOS app works with its local copy: reads answer at once, writes apply at once and sync in the background. See Synced Databases for subscribing.
  • In a server function, against any database, synced or not. ctx.db3(db3Id, "<type>").model("<model>") reads and writes on the server, with the app's own authority. A model handle has get, query, count, aggregate, save, patch, delete, increment and bulk.
  • From the CLI, with primitive db3 records …, for inspecting and fixing data.
  • Over HTTP from a client, with client.db3.records(id) — query, count, aggregate, save, patch, delete, increment and bulk with the same options and refusals as ctx.db3 — for admin tooling and for databases with sync off.

Each example below shows the web client, the iOS client and a server function side by side. On a device, pass { db3: id } (Swift: QueryOptions(db3: [id]), save(in: id)) to say which database a read or write is for, or set one for calls that name none with BaseModel.setDefaultDb3(id) (Swift: client.setDefaultDb3(id)). Unless you name a database, a read applies to every database on the device.

Create, update, delete ​

ts
const task = new Task({ title: "Review pull request", priority: 2 });
await task.save({ db3: db3Id });

task.completed = true;
await task.save(); // writes only the fields you changed

await task.delete();
swift
var task = try Task(title: "Review pull request", priority: 2).save(in: db3Id)

task.completed = true
task = try task.save(in: db3Id) // writes only the fields you changed

try task.delete(in: db3Id)
ts
const tasks = ctx.db3(input.db3Id, "workspace").model("tasks");

const { record } = await tasks.save({ data: { title: "Review pull request", priority: 2 } });
await tasks.patch(record.id, { data: { completed: true } }); // merges the fields you name
await tasks.delete(record.id);

A record's id is generated for you when you don't give one. An update writes only the fields you changed, so another device's edit to a different field of the same record is kept.

Querying ​

Filter on any field, sort, page, and count. A query answers one page, not every matching row — if you're used to a store that returns everything, read on before you rely on a result's length:

ts
const one = await Task.find("task-id");

// A query answers one page at a time — 100 rows when you omit `limit`,
// never every matching row. Loop on `hasMore`/`nextCursor` to read them all.
const urgent: Task[] = [];
let cursor: string | undefined;
do {
  const page = await Task.query(
    { completed: false, $or: [{ priority: { $gte: 3 } }, { tags: { $contains: "urgent" } }] },
    { db3: db3Id, sort: { priority: -1 }, uniqueStartKey: cursor },
  );
  urgent.push(...page.data);
  cursor = page.hasMore ? page.nextCursor : undefined;
} while (cursor);

const remaining = await Task.count({ completed: false }, { db3: db3Id });
swift
let one = try Task.find("task-id")

// A query answers one page at a time — 100 rows when you omit `limit`,
// never every matching row. Loop on `hasMore`/`nextCursor` to read them all.
var urgent: [Task] = []
var cursor: String? = nil
repeat {
  let page = try Task.queryPaged(
    ["completed": false, "$or": [["priority": ["$gte": 3]], ["tags": ["$contains": "urgent"]]]],
    options: QueryOptions(sortOrder: [("priority", -1)], cursor: cursor, db3: [db3Id])
  )
  urgent.append(contentsOf: page.data)
  cursor = page.hasMore ? page.nextCursor : nil
} while cursor != nil

let remaining = try Task.query(["completed": false], options: QueryOptions(db3: [db3Id])).count
ts
const tasks = ctx.db3(input.db3Id, "workspace").model("tasks");

const one = await tasks.get("task-id"); // or null

// Omit `limit` for the default page of 100; loop on `hasMore` to read every row.
const urgent = [];
let cursor: string | undefined;
do {
  const page = await tasks.query({
    filter: { completed: false, $or: [{ priority: { $gte: 3 } }, { tags: { $contains: "urgent" } }] },
    sort: { priority: -1 },
    cursor,
  });
  urgent.push(...page.items);
  cursor = page.hasMore ? page.nextCursor : undefined;
} while (cursor);

const { count } = await tasks.count({ filter: { completed: false } });
OperatorMatches
{ field: value }, $eq, $neEqual, not equal
$gt, $gte, $lt, $lteRanges on numbers, dates and strings
$in, $ninOne of (or none of) a list
$existsWhether the field has been written
$startsWith, $endsWith, $containsTextText matches
$contains, $all, $sizeString sets: has a member, has all of them, has this many
$and, $orCombine conditions

Paging uses cursors: pass the page's nextCursor back with the same filter and sort. A page holds 100 records when you don't set limit, and at most 10,000 when you do — read Limits for the rest. A query compares values as stored, with no conversion: { n: 5 } matches the number 5, not the string "5".

Null and unset fields. { field: null } matches a record that never wrote the field and one that stored null. $exists: false matches only a field never written. $ne and $nin also match records where the field is unset or null, and { field: { $eq: null } } matches nothing. Sorting places unset and null values together — first ascending, last descending.

Aggregates ​

Group records and compute counts, sums, averages, minimums and maximums:

ts
const byCategory = await Task.aggregate({
  db3: db3Id,
  groupBy: ["category"],
  operations: [{ type: "count" }, { type: "sum", field: "estimatedHours" }],
  filter: { completed: false },
  sort: { field: "count", direction: -1 },
  limit: 10,
});
// [{ group: { category: "work" }, count: 8, sum_estimatedHours: 40 }, …]

// A string set groups per member; a date groups by "month", "quarter" or "year":
const byTag = await Task.aggregate({ db3: db3Id, groupBy: ["tags"], operations: [{ type: "count" }] });
const byMonth = await Task.aggregate({
  db3: db3Id,
  groupBy: [{ field: "dueDate", period: "month" }],
  operations: [{ type: "count" }],
});
// [{ group: { dueDate_month: "2026-03" }, count: 12 }, …]
swift
let byCategory = try Task.aggregate(AggregateOptions(
  groupBy: ["category"],
  operations: [AggregateOperation(type: .count), AggregateOperation(type: .sum, field: "estimatedHours")],
  filter: ["completed": false],
  sort: AggregateSort(field: "count", direction: -1),
  limit: 10,
  db3: [db3Id]
))
// [["group": ["category": "work"], "count": 8, "sum_estimatedHours": 40], …]

// A string set groups per member; a date groups by .month, .quarter or .year:
let byTag = try Task.aggregate(AggregateOptions(
  groupBy: ["tags"], operations: [AggregateOperation(type: .count)], db3: [db3Id]
))
let byMonth = try Task.aggregate(AggregateOptions(
  groupBy: [.datePeriod(field: "dueDate", period: .month)],
  operations: [AggregateOperation(type: .count)],
  db3: [db3Id]
))
// [["group": ["dueDate_month": "2026-03"], "count": 12], …]
ts
const rows = await ctx.db3(input.db3Id, "workspace").model("tasks").aggregate({
  options: {
    groupBy: ["category"],
    operations: [{ type: "count" }, { type: "sum", field: "estimatedHours" }],
    filter: { completed: false },
    sort: { field: "count", direction: -1 },
    limit: 10,
  },
});
// [{ group: { category: "work" }, count: 8, sum_estimatedHours: 40 }, …]

Each row holds its group's values under group and each operation's result beside it, named <operation>_<field> (count alone for a plain count). Group by a plain field, by each member of a string set, by whether a set contains a value ({ field: "tags", contains: "urgent" }), or by a date's month, quarter or year.

Loading related records ​

Ask for related records with the rows, instead of a follow-up query per row. Declare the relationships in the type, then include them:

ts
const posts = await Post.query({}, {
  db3: db3Id,
  include: [{ model: "authors", type: "refersTo", sourceField: "authorId", as: "author" }],
});
for (const post of posts.data as (Post & { _related?: { author?: Author } })[]) {
  console.log(post.title, post._related?.author?.name);
}

const authors = await Author.query({}, {
  db3: db3Id,
  include: [{ model: "posts", type: "hasMany", foreignKey: "authorId", as: "posts", limit: 10 }],
});
swift
let posts = try Post.query(nil, options: QueryOptions(db3: [db3Id]), include: [Post.includeAuthor()])
for post in posts {
  print(post.title, post.relatedAuthor?.name ?? "—")
}

let authors = try Author.query(nil, options: QueryOptions(db3: [db3Id]), include: [Author.includePosts(limit: 10)])
ts
const page = await ctx.db3(input.db3Id, "workspace").model("posts").query({
  include: [
    { model: "authors", type: "refersTo", sourceField: "authorId", as: "author" },
    { model: "comments", type: "hasMany", foreignKey: "postId", as: "comments", limit: 20 },
  ],
});
// page.items[0]._related.author, page.items[0]._related.comments

refersTo loads the record a field points at, hasMany the records that point back, and refersToMany the records a string set of ids names. Includes nest up to 3 levels and resolve within the same database.

Upserts ​

Create a record, or update the one that already holds a unique key — no need to look it up first:

ts
// `email` is declared unique: merges into the record with this email, if any.
await new AppUser({ email: "alice@example.com", name: "Alice" }).save({ db3: db3Id, upsertOn: "email" });

// A named compound constraint, `name_parentId`:
await Category.upsertByUnique(
  "name_parentId",
  ["Work", "root"],
  { name: "Work", parentId: "root", color: "blue" },
  { db3: db3Id },
);
swift
// `email` is declared unique: merges into the record with this email, if any.
_ = try AppUser(id: UUID().uuidString, email: "alice@example.com", name: "Alice")
  .save(in: db3Id, upsertOn: "email")

// A named compound constraint, `name_parentId`:
_ = try Category(id: UUID().uuidString, name: "Work", parentId: "root", color: "blue")
  .upsertByUnique("name_parentId", in: db3Id)
ts
const members = ctx.db3(input.db3Id, "workspace").model("members");
await members.save({ data: { email: "alice@example.com", name: "Alice" }, upsertOn: "email" });

upsertOn names a field declared unique or a named unique constraint. When two devices create the same key while offline, both writes land on one record, with their fields merged.

Conditional writes ​

A condition makes a write apply only if the record still matches it — the way to claim a task, reserve a seat, or change a status only from the state you read. The database checks it, so of two devices racing, exactly one wins:

ts
task.category = "claimed";
// Refused with DB3_CONDITION_NOT_MET if someone else changed it first:
await task.save({ condition: { category: "open" }, confirm: true });

// Create only if no record has this id yet:
await new Task({ id: "daily-standup", title: "Standup" }).save({ db3: db3Id, ifNotExists: true });

await task.delete({ condition: { completed: true } });
swift
var task = task
task.category = "claimed"
// Refused with DB3_CONDITION_NOT_MET if someone else changed it first:
task = try await task.save(in: db3Id, options: Db3WriteOptions(condition: ["category": "open"], confirm: true))

// Create only if no record has this id yet:
try await Task(id: "daily-standup", title: "Standup").save(in: db3Id, options: Db3WriteOptions(ifNotExists: true))

try await task.delete(in: db3Id, options: Db3WriteOptions(condition: ["completed": true]))
ts
const tasks = ctx.db3(input.db3Id, "workspace").model("tasks");

await tasks.patch(taskId, { data: { category: "claimed" }, condition: { category: "open" } });
await tasks.save({ id: "daily-standup", data: { title: "Standup" }, ifNotExists: true });
await tasks.delete(taskId, { condition: { completed: true } });

A failed condition is refused with DB3_CONDITION_NOT_MET, which carries the record as it is now. A condition takes the same filters as a query. Any save, patch, delete or increment on a device applies to the local copy and resolves before the database has seen it; pass confirm: true (in Swift, Db3WriteOptions(confirm: true)) to wait for its answer instead and have the call reject if it's refused — the only way to learn a conditional write's outcome synchronously.

Counters ​

increment adds to number fields without reading them first, so increments from many devices at once all count:

ts
const { views } = await Post.increment(postId, { views: 1 }, { db3: db3Id, confirm: true });
swift
let values = try await Post.increment(id: postId, fields: ["views": 1], in: db3Id, options: Db3WriteOptions(confirm: true))
ts
const { values } = await ctx.db3(input.db3Id, "workspace").model("posts").increment(postId, { views: 1 });
// values.views is the new total

A negative delta subtracts. Combine with a condition to keep a counter in bounds — decrement stock only while it is above zero. Incrementing a record that doesn't exist is refused with DB3_RECORD_NOT_FOUND.

String sets ​

A stringset field changes member by member: adding a tag on one device and removing another on a second device keeps both changes.

ts
const task = await Task.find(taskId);
if (task) {
  task.tags?.add("urgent");
  task.tags?.remove("low-priority");
  await task.save();
}
const urgent = await Task.query({ tags: { $contains: "urgent" } });
swift
if var task = try Task.find(taskId) {
  task.tags?.insert("urgent")
  task.tags?.remove("low-priority")
  try task.save(in: db3Id)
}
let urgent = try Task.query(["tags": ["$contains": "urgent"]], options: QueryOptions(db3: [db3Id]))
ts
await ctx.db3(input.db3Id, "workspace").model("tasks").patch(taskId, {
  data: { tags: { $add: ["urgent"], $remove: ["low-priority"] } },
});

Writing a whole array replaces the set; { $add: [...] }, { $remove: [...] } and { $clear: true } change members. Members come back without duplicates in a fixed order.

Batches ​

Group writes so they apply together, or not at all:

ts
await BaseModel.withTransaction(async () => {
  await new Task({ title: "Plan" }).save({ db3: db3Id });
  await new Task({ title: "Build" }).save({ db3: db3Id });
  await new Task({ title: "Ship" }).save({ db3: db3Id });
});

// `atomic: false`: each write stands on its own, so one refusal doesn't
// undo the others.
await BaseModel.withTransaction(async () => {
  await new Task({ title: "Optional" }).save({ db3: db3Id });
}, { atomic: false });
ts
// One model:
await ctx.db3(input.db3Id, "workspace").model("tasks").bulk([
  { action: "create", data: { title: "Plan" } },
  { action: "increment", id: counterId, fields: { planned: 1 } },
]);

// Several models, each op naming its model:
const result = await ctx.db3(input.db3Id, "workspace").bulk([
  { model: "tasks", action: "patch", id: taskId, data: { status: "done" } },
  { model: "posts", action: "create", data: { title: "Shipped it" } },
], { atomic: false });
// with atomic: false, result.results[i] says whether each op applied, and why not

A batch takes create, patch, delete, upsert and increment operations, each with an optional condition; up to 500 in one call. By default the whole batch applies or none of it does. With atomic: false each operation stands on its own, and one refusal leaves the rest applied.

Bulk loading ​

Saves and batches are for the writes an app makes in normal operation. To write thousands of records at once — an import, loading a reference dataset, a correction across a whole model — use a bulk load: one session that uploads every record and applies them together, far faster than one write per record.

Load from your app's code with rows it already holds:

ts
// rows: [{ model: "securities", id: "AAPL", patch: { name: "Apple Inc.", exchange: "NASDAQ" } }, …]
const chunks = await client.db3.ingests.buildChunks(rows);
const session = await client.db3.ingests.create(db3Id, { mode: "merge" });
for (const chunk of chunks) {
  await client.db3.ingests.uploadChunk(db3Id, session.sessionId, chunk);
}
await client.db3.ingests.commit(db3Id, session.sessionId);

let loaded = await client.db3.ingests.get(db3Id, session.sessionId);
while (!["complete", "failed", "aborted"].includes(loaded.state)) {
  await new Promise((resolve) => setTimeout(resolve, 1000));
  loaded = await client.db3.ingests.get(db3Id, session.sessionId);
}
// loaded.state is "complete", "failed" (loaded.failure says why) or "aborted";
// loaded.refusedRows counts rows the database refused, refusedSample names a few.
swift
// rows: [DocumentIngestRow(model: "securities", id: "AAPL", patch: ["name": "Apple Inc."]), …]
let chunks = try client.db3.ingests.buildChunks(rows: rows)
let session = try await client.db3.ingests.create(db3Id: db3Id, options: DocumentIngestCreateOptions(mode: .merge))
for chunk in chunks {
  _ = try await client.db3.ingests.uploadChunk(db3Id: db3Id, sessionId: session.sessionId, chunk: chunk)
}
_ = try await client.db3.ingests.commit(db3Id: db3Id, sessionId: session.sessionId)

var loaded = try await client.db3.ingests.get(db3Id: db3Id, sessionId: session.sessionId)
while !["complete", "failed", "aborted"].contains(loaded.state) {
  try await _Concurrency.Task.sleep(nanoseconds: 1_000_000_000)
  loaded = try await client.db3.ingests.get(db3Id: db3Id, sessionId: session.sessionId)
}
// loaded.state is "complete", "failed" (loaded.failure says why) or "aborted";
// loaded.refusedRows counts rows the database refused, refusedSample names a few.

Or from the CLI, with a directory holding one <model>.ndjson (or .ndjson.gz) file per model, each line a record id and its fields:

bash
primitive db3 ingest <db3-id> --input ./records -y
primitive db3 ingests get <db3-id> <session-id>
primitive db3 ingests abort <db3-id> <session-id>
primitive db3 ingests list <db3-id>
  • Rows. Each row names its model, its record id and a patch: values replace fields, null removes a field, and { "_deleted": true } deletes the record. buildChunks sorts the rows and cuts them into chunks within the platform's limits; it holds the whole load in memory, so load more than a few hundred thousand rows with the CLI.
  • Modes. merge (the default) adds or changes only the records the rows name. refresh also deletes every record of the rows' models that no row names — the way to replace a dataset wholesale.
  • All at once. The records become visible together when the load completes, and subscribed devices receive them in chunks; model subscriptions fire as they arrive.
  • Refused rows. A row that breaks the type or what a record holds, or collides on a unique key, is skipped and reported rather than failing the load. The session's refusedRows counts them and refusedSample names the first few.
  • Writes during a load made by your app land after it and win over a conflicting row.

Check the input before loading

A bulk load changes live records and cannot be undone. Stopping the CLI's wait does not stop the load; inspect its session to see how it ended.

Indexes ​

An equality query on a field is fast when the field is indexed. Fields the type declares indexed or unique are indexed in every database of the type; register an index on one database for a field you query without declaring it.

Every index has a write cost: each write to a record also updates the indexes on its fields, on the server and on every synced device. Index only the fields you actually filter on — you can always add an index later, by marking the field indexed in the type or registering one, and existing records are indexed when you do.

ts
const index = await client.db3.indexes.register(db3Id, { model: "contacts", field: "email" });
// index.name === "idx_records_contact_email"

try {
  await client.db3.indexes.register(db3Id, {
    model: "contacts",
    fields: ["accountId", "email"],
    unique: true,
    name: "account_email",
  });
} catch (err) {
  if (isJsBaoApiError(err) && err.code === "DB3_INDEX_NOT_UNIQUE") {
    // Up to ten shared keys, each with how many records hold it.
    console.warn((err.body as { details?: { duplicates?: unknown[] } }).details?.duplicates);
  }
}

for (const each of await client.db3.indexes.list(db3Id)) {
  console.log(each.name, each.fields, each.unique, each.origins);
}
await client.db3.indexes.drop(db3Id, index.name);
swift
let index = try await client.db3.indexes.register(
  db3Id, Db3IndexRegistration(model: "contacts", field: "email")
)
// index.name == "idx_records_contact_email"

_ = try await client.db3.indexes.register(
  db3Id,
  Db3IndexRegistration(model: "contacts", fields: ["accountId", "email"], unique: true, name: "account_email")
)

for each in try await client.db3.indexes.list(db3Id) {
  print(each.name, each.fields, each.unique, each.origins)
}
try await client.db3.indexes.drop(db3Id, name: index.name)
bash
primitive db3 indexes register <db3-id> --model contacts --field email
primitive db3 indexes list <db3-id>
primitive db3 indexes drop <db3-id> idx_records_contact_email
  • A one-field index is named idx_records_<model>_<field>. A registered index over several fields is a unique constraint, which needs unique and a name, and is idx_named_<model>_<name>; a compound constraint the type declares is idx_uc_<model>_<constraint>.
  • A unique index over records that already share a key is refused with DB3_INDEX_NOT_UNIQUE, naming up to ten shared keys in details.duplicates.
  • Registering and dropping need the database's owner or an app admin. Dropping an index the type declares is refused with DB3_INDEX_IN_USE; change the type instead.
  • String set fields don't take a registered index — $contains is fast without one.
  • A device picks up an index registered later at its next subscribe. In development, the client logs a warning for a query that scans every record of a model.

Inspecting and fixing records from the CLI ​

To look into a database or correct its data by hand, use the CLI. It works with your admin login on any database, synced or not, without a copy on your machine:

bash
primitive db3 records query <db3-id> tasks --filter '{"completed":false}' --sort '{"priority":-1}' --limit 50
primitive db3 records count <db3-id> tasks --filter '{"completed":false}'
primitive db3 records patch <db3-id> tasks <record-id> --data '{"completed":true}'

App code reads and writes records on a device or in a server function, as above. See Managing Databases for every primitive db3 command.

Gotchas ​

  • A read on a device needs the database resident. Naming a database the device doesn't hold is refused with DB3_NOT_RESIDENT; wait for the subscription's available first.
  • Index the fields you filter on. A query on an unindexed field reads every record of the model — fine for hundreds, slow for hundreds of thousands.
  • Retry server-side writes with the same requestId. A function call that times out may have applied; resending it with the same requestId (a ULID you generate) applies it once.
