Reading and Writing Records ​

Records are read and written through the models generated from a database's type. The same operations exist in three places:

  • On a device, against a synced database. Your web or iOS app works with its local copy: reads answer at once, writes apply at once and sync in the background. See Synced Databases for subscribing.
  • In a server function, against any database, synced or not. ctx.db3(db3Id, "<type>").model("<model>") reads and writes on the server, with the app's own authority. A model handle has get, query, count, aggregate, save, patch, delete, increment, batch and batchRead.
  • From the CLI, with primitive db3 records …, for inspecting and fixing data.
  • Over HTTP from a client, with client.db3.records(id) — query, count, aggregate, save, patch, delete, increment, batch and batchRead with the same options and refusals as ctx.db3 — for admin tooling and for databases with sync off.

Each example below shows the web client, the iOS client and a server function side by side. On a device, pass { db3: id } (Swift: QueryOptions(db3: [id]), save(in: id)) to say which database a read or write is for, or set one for calls that name none with BaseModel.setDefaultDb3(id) (Swift: client.setDefaultDb3(id)). Unless you name a database, a read applies to every database on the device.

Create, update, delete ​

ts
const task = new Task({ title: "Review pull request", priority: 2 });
await task.save({ db3: db3Id });

task.completed = true;
await task.save(); // writes only the fields you changed

await task.delete();
swift
var task = try Task(title: "Review pull request", priority: 2).save(in: db3Id)

task.completed = true
task = try task.save(in: db3Id) // writes only the fields you changed

try task.delete(in: db3Id)
ts
const tasks = ctx.db3(input.db3Id, "workspace").model("tasks");

const { record } = await tasks.save({ data: { title: "Review pull request", priority: 2 } });
await tasks.patch(record.id, { data: { completed: true } }); // merges the fields you name
await tasks.delete(record.id);

A record's id is generated for you when you don't give one. An update writes only the fields you changed, so another device's edit to a different field of the same record is kept. On the server, patch changes a record that exists: patching an id no record holds is refused with DB3_RECORD_NOT_FOUND and creates nothing, so create with save.

Querying ​

Filter on any field, sort, page, and count. A query answers one page, not every matching row — if you're used to a store that returns everything, read on before you rely on a result's length:

ts
const one = await Task.find("task-id");

// A query answers one page at a time — 100 rows when you omit `limit`,
// never every matching row. Loop on `hasMore`/`nextCursor` to read them all.
const urgent: Task[] = [];
let cursor: string | undefined;
do {
  const page = await Task.query(
    { completed: false, $or: [{ priority: { $gte: 3 } }, { tags: { $contains: "urgent" } }] },
    { db3: db3Id, sort: { priority: -1 }, uniqueStartKey: cursor },
  );
  urgent.push(...page.data);
  cursor = page.hasMore ? page.nextCursor : undefined;
} while (cursor);

const remaining = await Task.count({ completed: false }, { db3: db3Id });
swift
let one = try Task.find("task-id")

// A query answers one page at a time — 100 rows when you omit `limit`,
// never every matching row. Loop on `hasMore`/`nextCursor` to read them all.
var urgent: [Task] = []
var cursor: String? = nil
repeat {
  let page = try Task.queryPaged(
    ["completed": false, "$or": [["priority": ["$gte": 3]], ["tags": ["$contains": "urgent"]]]],
    options: QueryOptions(sortOrder: [("priority", -1)], cursor: cursor, db3: [db3Id])
  )
  urgent.append(contentsOf: page.data)
  cursor = page.hasMore ? page.nextCursor : nil
} while cursor != nil

let remaining = try Task.query(["completed": false], options: QueryOptions(db3: [db3Id])).count
ts
const tasks = ctx.db3(input.db3Id, "workspace").model("tasks");

const one = await tasks.get("task-id"); // or null

// Omit `limit` for the default page of 100; loop on `hasMore` to read every row.
const urgent = [];
let cursor: string | undefined;
do {
  const page = await tasks.query({
    filter: { completed: false, $or: [{ priority: { $gte: 3 } }, { tags: { $contains: "urgent" } }] },
    sort: { priority: -1 },
    cursor,
  });
  urgent.push(...page.items);
  cursor = page.hasMore ? page.nextCursor : undefined;
} while (cursor);

const { count } = await tasks.count({ filter: { completed: false } });
OperatorMatches
{ field: value }, $eq, $neEqual, not equal
$gt, $gte, $lt, $lteRanges on numbers, dates and strings
$in, $ninOne of (or none of) a list
$existsWhether the field has been written
$startsWith, $endsWith, $containsTextText matches
$contains, $all, $sizeString sets: has a member, has all of them, has this many
$and, $orCombine conditions

Paging uses cursors: pass the page's nextCursor back with the same filter and sort. A page holds 100 records when you don't set limit, and at most 10,000 when you do — read Limits for the rest. A query compares values as stored, with no conversion: { n: 5 } matches the number 5, not the string "5".

Null and unset fields. { field: null } matches a record that never wrote the field and one that stored null. $exists: false matches only a field never written. $ne and $nin also match records where the field is unset or null, and { field: { $eq: null } } matches nothing. Sorting places unset and null values together — first ascending, last descending.

A field can't go back to "never written" once a write has named it: assigning undefined (or null) stores null, and there's no operation that removes the key again. Clear a field by writing null to it; $exists: false will then no longer match the record, but { field: null } still does.

Aggregates ​

Group records and compute counts, sums, averages, minimums and maximums:

ts
const byCategory = await Task.aggregate({
  db3: db3Id,
  groupBy: ["category"],
  operations: [{ type: "count" }, { type: "sum", field: "estimatedHours" }],
  filter: { completed: false },
  sort: { field: "count", direction: -1 },
  limit: 10,
});
// [{ group: { category: "work" }, count: 8, sum_estimatedHours: 40 }, …]

// A string set groups per member; a date groups by "month", "quarter" or "year":
const byTag = await Task.aggregate({ db3: db3Id, groupBy: ["tags"], operations: [{ type: "count" }] });
const byMonth = await Task.aggregate({
  db3: db3Id,
  groupBy: [{ field: "dueDate", period: "month" }],
  operations: [{ type: "count" }],
});
// [{ group: { dueDate_month: "2026-03" }, count: 12 }, …]
swift
let byCategory = try Task.aggregate(AggregateOptions(
  groupBy: ["category"],
  operations: [AggregateOperation(type: .count), AggregateOperation(type: .sum, field: "estimatedHours")],
  filter: ["completed": false],
  sort: AggregateSort(field: "count", direction: -1),
  limit: 10,
  db3: [db3Id]
))
// [["group": ["category": "work"], "count": 8, "sum_estimatedHours": 40], …]

// A string set groups per member; a date groups by .month, .quarter or .year:
let byTag = try Task.aggregate(AggregateOptions(
  groupBy: ["tags"], operations: [AggregateOperation(type: .count)], db3: [db3Id]
))
let byMonth = try Task.aggregate(AggregateOptions(
  groupBy: [.datePeriod(field: "dueDate", period: .month)],
  operations: [AggregateOperation(type: .count)],
  db3: [db3Id]
))
// [["group": ["dueDate_month": "2026-03"], "count": 12], …]
ts
const rows = await ctx.db3(input.db3Id, "workspace").model("tasks").aggregate({
  options: {
    groupBy: ["category"],
    operations: [{ type: "count" }, { type: "sum", field: "estimatedHours" }],
    filter: { completed: false },
    sort: { field: "count", direction: -1 },
    limit: 10,
  },
});
// [{ group: { category: "work" }, count: 8, sum_estimatedHours: 40 }, …]

Each row holds its group's values under group and each operation's result beside it, named <operation>_<field> (count alone for a plain count). Group by a plain field, by each member of a string set, by whether a set contains a value ({ field: "tags", contains: "urgent" }), or by a date's month, quarter or year.

Loading related records ​

Ask for related records with the rows, instead of a follow-up query per row. Declare the relationships in the type, then include them:

ts
const posts = await Post.query({}, {
  db3: db3Id,
  include: [{ model: "authors", type: "refersTo", sourceField: "authorId", as: "author" }],
});
for (const post of posts.data as (Post & { _related?: { author?: Author } })[]) {
  console.log(post.title, post._related?.author?.name);
}

const authors = await Author.query({}, {
  db3: db3Id,
  include: [{ model: "posts", type: "hasMany", foreignKey: "authorId", as: "posts", limit: 10 }],
});
swift
let posts = try Post.query(nil, options: QueryOptions(db3: [db3Id]), include: [Post.includeAuthor()])
for post in posts {
  print(post.title, post.relatedAuthor?.name ?? "—")
}

let authors = try Author.query(nil, options: QueryOptions(db3: [db3Id]), include: [Author.includePosts(limit: 10)])
ts
const page = await ctx.db3(input.db3Id, "workspace").model("posts").query({
  include: [
    { model: "authors", type: "refersTo", sourceField: "authorId", as: "author" },
    { model: "comments", type: "hasMany", foreignKey: "postId", as: "comments", limit: 20 },
  ],
});
// page.items[0]._related.author, page.items[0]._related.comments

refersTo loads the record a field points at, hasMany the records that point back, and refersToMany the records a string set of ids names. Includes nest up to 3 levels and resolve within the same database.

Upserts ​

Create a record, or update the one that already holds a unique key — no need to look it up first:

ts
// `email` is declared unique: merges into the record with this email, if any.
await new AppUser({ email: "alice@example.com", name: "Alice" }).save({ db3: db3Id, upsertOn: "email" });

// A named compound constraint, `name_parentId`:
await Category.upsertByUnique(
  "name_parentId",
  ["Work", "root"],
  { name: "Work", parentId: "root", color: "blue" },
  { db3: db3Id },
);
swift
// `email` is declared unique: merges into the record with this email, if any.
_ = try AppUser(id: UUID().uuidString, email: "alice@example.com", name: "Alice")
  .save(in: db3Id, upsertOn: .email)

// A named compound constraint, `name_parentId`:
_ = try Category(id: UUID().uuidString, name: "Work", parentId: "root", color: "blue")
  .upsertByUnique(.name_parentId, in: db3Id)
ts
const members = ctx.db3(input.db3Id, "workspace").model("members");
await members.save({ data: { email: "alice@example.com", name: "Alice" }, upsertOn: "email" });

upsertOn names a field declared unique or a named unique constraint, and a batch's upsert operation names one the same way in constraint. Any other name, such as a field that isn't unique, is refused with DOCUMENT_ENTRY_INVALID and nothing is written. When two devices create the same key while offline, both writes land on one record, with their fields merged.

On a device, a generated model checks the name when it compiles. save's upsertOn takes one of the model's unique fields, and upsertByUnique one of its constraint names: a single unique field's constraint is <model>_<field>_unique, such as appUsers_email_unique. In JavaScript these are <Model>UniqueField and <Model>UniqueConstraint, so a misspelled literal fails typecheck while a name held in a string variable still compiles. In Swift they are the nested UniqueField and UniqueConstraint enums, as in upsertOn: .email, beside the String forms.

Conditional writes ​

A condition makes a write apply only if the record still matches it — the way to claim a task, reserve a seat, or change a status only from the state you read. The database checks it, so of two devices racing, exactly one wins:

ts
task.category = "claimed";
// Refused with DB3_CONDITION_NOT_MET if someone else changed it first:
await task.save({ condition: { category: "open" }, confirm: true });

// Create only if no record has this id yet:
await new Task({ id: "daily-standup", title: "Standup" }).save({ db3: db3Id, ifNotExists: true });

await task.delete({ condition: { completed: true } });
swift
var task = task
task.category = "claimed"
// Refused with DB3_CONDITION_NOT_MET if someone else changed it first:
task = try await task.save(in: db3Id, options: Db3WriteOptions(condition: ["category": "open"], confirm: true))

// Create only if no record has this id yet:
try await Task(id: "daily-standup", title: "Standup").save(in: db3Id, options: Db3WriteOptions(ifNotExists: true))

try await task.delete(in: db3Id, options: Db3WriteOptions(condition: ["completed": true]))
ts
const tasks = ctx.db3(input.db3Id, "workspace").model("tasks");

await tasks.patch(taskId, { data: { category: "claimed" }, condition: { category: "open" } });
await tasks.save({ id: "daily-standup", data: { title: "Standup" }, ifNotExists: true });
await tasks.delete(taskId, { condition: { completed: true } });

A failed condition is refused with DB3_CONDITION_NOT_MET, which carries the record as it is now. A condition takes the same filters as a query. Any save, patch, delete or increment on a device applies to the local copy and resolves before the database has seen it; pass confirm: true (in Swift, Db3WriteOptions(confirm: true)) to wait for its answer instead and have the call reject if it's refused — the only way to learn a conditional write's outcome synchronously.

Counters ​

increment adds to number fields without reading them first, so increments from many devices at once all count:

ts
const { views } = await Post.increment(postId, { views: 1 }, { db3: db3Id, confirm: true });
swift
let values = try await Post.increment(id: postId, fields: ["views": 1], in: db3Id, options: Db3WriteOptions(confirm: true))
ts
const { values } = await ctx.db3(input.db3Id, "workspace").model("posts").increment(postId, { views: 1 });
// values.views is the new total

A negative delta subtracts. Combine with a condition to keep a counter in bounds — decrement stock only while it is above zero. Incrementing a record that doesn't exist is refused with DB3_RECORD_NOT_FOUND.

String sets ​

A stringset field changes member by member: adding a tag on one device and removing another on a second device keeps both changes.

ts
const task = await Task.find(taskId);
if (task) {
  task.tags?.add("urgent");
  task.tags?.remove("low-priority");
  await task.save();
}
const urgent = await Task.query({ tags: { $contains: "urgent" } });
swift
if var task = try Task.find(taskId) {
  task.tags?.insert("urgent")
  task.tags?.remove("low-priority")
  try task.save(in: db3Id)
}
let urgent = try Task.query(["tags": ["$contains": "urgent"]], options: QueryOptions(db3: [db3Id]))
ts
await ctx.db3(input.db3Id, "workspace").model("tasks").patch(taskId, {
  data: { tags: { $add: ["urgent"], $remove: ["low-priority"] } },
});

Writing a whole array replaces the set; { $add: [...] }, { $remove: [...] } and { $clear: true } change members. Members come back without duplicates in a fixed order.

Vectors ​

A vector field is written and read as numbers on a device. A server function, the CLI and client.db3.records(id) see the stored base64 text, and convert it with encodeVector and decodeVector.

ts
// number[] or Float32Array in, Float32Array out.
const note = new Note({ title: "Kickoff", embedding: await embed(text) });
await note.save();
const read = await Note.find(note.id);
const embedding = read?.embedding; // Float32Array of 768 numbers
swift
// [Float] in and out.

note = try note.save(in: db3Id)
let embedding = try Note.find(note.id)?.embedding // [Float]? of 768 numbers
ts
import { decodeVector, encodeVector } from "primitive-functions";

const encoding = { dims: 768, element: "f16" } as const;
const notes = ctx.db3(input.db3Id, "workspace").model("notes");
const { record } = await notes.save({ data: { title: "Kickoff", embedding: encodeVector(input.embedding, encoding) } });

null clears the field. The device encodes with the field's element, so a read answers what the encoding kept: f16 rounds each number, and i8 keeps each to within 1/254 of the vector's largest magnitude. The JavaScript client exports encodeVector and decodeVector too, and the Swift client has VectorCodec.encode(_:encoding:) and VectorCodec.decode(_:encoding:). A value that doesn't fit is refused with DB3_VECTOR_INVALID, naming the field and its encoding; a device refuses it before anything is sent. The server stores vectors without searching them: a server query that uses $near is refused with QUERY_INDEX_NOT_ON_SERVER.

Nearest records ​

Register a vector index on a vector field, and $near on a device answers the k records nearest a vector, nearest first, each with its _distance:

ts
await client.db3.indexes.register(db3Id, {
  model: "notes",
  field: "embedding",
  kind: "vector",
  vector: { distance: "cos", index: { mode: "ann" } },
});

const { data } = await Note.query(
  { $near: { field: "embedding", vector: query, k: 10, filter: { pinned: false } } },
  { db3: db3Id }
);
for (const note of data) console.log(note.body, note._distance);

// "exact" from the first record, "ann" once this device has the shared model.
const index = (await client.db3.indexes.local(db3Id)).find((i) => i.name === "idx_vec_notes_embedding");
console.log(index?.mode);

// The owner has the model trained again, over the records as they are now.
await client.db3.indexes.deleteModel(db3Id, "idx_vec_notes_embedding");
swift
_ = try await client.db3.indexes.register(
  db3Id,
  Db3IndexRegistration(
    model: "notes", field: "embedding", kind: .vector,

  )
)

]

// The owner has the model trained again, over the records as they are now.

  • Options. distance is cos (the default) or l2; _distance is the cosine distance, or the squared Euclidean one. k is 10 by default and at most 10,000. filter holds conditions on the model's other fields, and $near is the query's only key. A vector index lives on devices: it is registered with on: "device" or none.

  • Exact or approximate. With index: "exact", the default, each query compares every vector the device holds. index: { mode: "ann" } answers from an approximate index once the device has its model, comparing a few candidates and ranking them on the full vectors; until then, and while it fills the index, it answers exactly, so no query waits. On 100,000 100-dimension embeddings in Node an ann answer found 95% of the exact ten nearest in about a fifth of the time. Prefer ann for wide vectors in the browser: there an exact query over 20,000 768-number vectors takes about 170 ms.

  • One model per database. The first device to hold enough records (at least 1,000) trains the ann model in the background, off the thread that serves queries, and uploads it; every other device fetches that model rather than training its own. client.db3.indexes.list shows it as the index's annModel, and client.db3.indexes.local shows each device's mode (exact or ann). The owner can delete it with client.db3.indexes.deleteModel to have it trained again over newer records; every device answers exactly until the new one arrives. A local-only database trains and keeps its own.

  • Where it runs. $near answers on a device whose store builds vector indexes: the Swift client, the browser's OPFS storage, and Node with the optional primitive-vec1-node package installed. Elsewhere the copy keeps syncing, and a $near is refused with DB3_INDEX_PLACEMENT_UNSUPPORTED, naming the storage in details.engine. A field with no vector index on the device is refused with QUERY_INDEX_NOT_ON_DEVICE.

  • Storage. A device keeps a 32-bit copy of each vector beside the record, whatever the field's element, and an ann index a little more again; f16 and i8 shrink only the record itself. For 100,000 records with a 768-number vector field:

    elementRecords, JavaScriptRecords, SwiftVector indexann index
    f32about 445 MiBabout 886 MiBabout 295 MiBabout 413 MiB
    f16about 397 MiBabout 790 MiBabout 295 MiBabout 413 MiB
    i8about 136 MiBabout 268 MiBabout 295 MiBabout 413 MiB

    An f16 record of 768 numbers takes about 2 KiB, so it saves little over f32 on the device; i8 saves the most. A shared ann model is at most 64 MiB.

Batches ​

Group writes so they apply together, or not at all:

ts
await BaseModel.withTransaction(async () => {
  await new Task({ title: "Plan" }).save({ db3: db3Id });
  await new Task({ title: "Build" }).save({ db3: db3Id });
  await new Task({ title: "Ship" }).save({ db3: db3Id });
});

// `atomic: false`: each write stands on its own, so one refusal doesn't
// undo the others.
await BaseModel.withTransaction(async () => {
  await new Task({ title: "Optional" }).save({ db3: db3Id });
}, { atomic: false });
ts
// One model:
await ctx.db3(input.db3Id, "workspace").model("tasks").batch([
  { action: "create", data: { title: "Plan" } },
  { action: "increment", id: counterId, fields: { planned: 1 } },
]);

// Several models, each op naming its model:
const result = await ctx.db3(input.db3Id, "workspace").batch([
  { model: "tasks", action: "patch", id: taskId, data: { status: "done" } },
  { model: "posts", action: "create", data: { title: "Shipped it" } },
], { atomic: false });
// with atomic: false, result.results[i] says whether each op applied, and why not

A batch takes create, patch, delete, upsert and increment operations, each with an optional condition; up to 100 operations in one call. By default the whole batch applies or none of it does. With atomic: false each operation stands on its own, and one refusal leaves the rest applied: a value outside an enforced enum, for one, answers that operation's results[i] with ok: false, code: "DB3_VALUE_NOT_IN_ENUM" and status: 400, and the other operations are written. In a default batch the same refusal fails the whole call with a 400 naming the operation's index, model and recordId.

A batch sent from a server function, with client.db3.records(id).batch or from the CLI can also carry reads among its writes: query, count and aggregate operations. Everything runs in order, so a read sees the writes before it and not the ones after, and each read is answered in the result's reads at its index. A retry with the same requestId answers the writes as they first applied and answers the reads again.

"Atomic" describes the entry the room applies, not the callback you pass to withTransaction: the room applies every save the callback made as one entry, or refuses that entry whole. If the callback itself throws, the saves it already made are not undone — they still land together, and the error is rethrown after.

Reading in one request ​

To answer several reads at once (a page of one model, a count of another, a grouped aggregate), send them as one batch read. Every read is answered from the same state of the database, each at its index, and the caller needs read access only:

ts
const records = client.db3.records(db3Id);
const { results } = await records.batchRead([
  { model: "projects", action: "query", sort: { updatedAt: -1 }, limit: 20 },
  { model: "tasks", action: "count", filter: { completed: false } },
  { model: "tasks", action: "aggregate", options: { groupBy: ["status"], operations: [{ type: "count" }] } },
]);
// results[0] is the page, results[1] the count, results[2] the rows, each at its index

// A batch of writes may carry reads too: each sees the writes before it.
const { reads } = await records.batch([
  { model: "visits", action: "create", data: { page: "/home" } },
  { model: "visits", action: "count" },
]);
swift

Each read takes what its own call takes (a query's filter, sort, limit, cursor and include), and no read can use another's result. A batch read carries up to 100 operations, and its whole answer is at most 8 MiB: a page that would pass that ends early with hasMore, and a read that still can't fit is refused with DB3_PAGE_TOO_LARGE. By default the first refused read refuses the request, naming its index; with atomic: false it is answered with its error in its place and the other reads are answered. From the CLI: primitive db3 records batch-read <db3-id> --data-file reads.json.

Bulk loading ​

Saves and batches are for the writes an app makes in normal operation. To write thousands of records at once — an import, loading a reference dataset, a correction across a whole model — use a bulk load: one session that uploads every record and applies them together, far faster than one write per record.

Load from your app's code with rows it already holds:

ts
// rows: [{ model: "securities", id: "AAPL", patch: { name: "Apple Inc.", exchange: "NASDAQ" } }, …]
const chunks = await client.db3.ingests.buildChunks(rows);
const session = await client.db3.ingests.create(db3Id, { mode: "merge" });
for (const chunk of chunks) {
  await client.db3.ingests.uploadChunk(db3Id, session.sessionId, chunk);
}
await client.db3.ingests.commit(db3Id, session.sessionId);

let loaded = await client.db3.ingests.get(db3Id, session.sessionId);
while (!["complete", "failed", "aborted"].includes(loaded.state)) {
  await new Promise((resolve) => setTimeout(resolve, 1000));
  loaded = await client.db3.ingests.get(db3Id, session.sessionId);
}
// loaded.state is "complete", "failed" (loaded.failure says why) or "aborted";
// loaded.refusedRows counts rows the database refused, refusedSample names a few.
swift
// rows: [DocumentIngestRow(model: "securities", id: "AAPL", patch: ["name": "Apple Inc."]), …]
let chunks = try client.db3.ingests.buildChunks(rows: rows)
let session = try await client.db3.ingests.create(db3Id: db3Id, options: DocumentIngestCreateOptions(mode: .merge))
for chunk in chunks {
  _ = try await client.db3.ingests.uploadChunk(db3Id: db3Id, sessionId: session.sessionId, chunk: chunk)
}
_ = try await client.db3.ingests.commit(db3Id: db3Id, sessionId: session.sessionId)

var loaded = try await client.db3.ingests.get(db3Id: db3Id, sessionId: session.sessionId)
while !["complete", "failed", "aborted"].contains(loaded.state) {
  try await _Concurrency.Task.sleep(nanoseconds: 1_000_000_000)
  loaded = try await client.db3.ingests.get(db3Id: db3Id, sessionId: session.sessionId)
}
// loaded.state is "complete", "failed" (loaded.failure says why) or "aborted";
// loaded.refusedRows counts rows the database refused, refusedSample names a few.

Or from the CLI, with a directory holding one <model>.ndjson (or .ndjson.gz) file per model, each line a record id and its fields:

bash
primitive db3 ingest <db3-id> --input ./records -y
primitive db3 ingests get <db3-id> <session-id>
primitive db3 ingests abort <db3-id> <session-id>
primitive db3 ingests list <db3-id>
  • Rows. Each row names its model, its record id and a patch: values replace fields, and { "_deleted": true } deletes the record. null stores null on a plain field, same as any other write; on a string-set field it empties the set. buildChunks sorts the rows and cuts them into chunks within the platform's limits; it holds the whole load in memory, so load more than a few hundred thousand rows with the CLI.
  • Modes. merge (the default) adds or changes only the records the rows name. refresh also deletes every record of the rows' models that no row names — the way to replace a dataset wholesale.
  • All at once. The records become visible together when the load completes, and subscribed devices receive them in chunks; model subscriptions fire as they arrive.
  • Refused rows. A row that breaks the type or what a record holds, or collides on a unique key, is skipped and reported rather than failing the load. The session's refusedRows counts them and refusedSample names the first few.
  • What a load skips. A load checks each row against the type (models, field types, enforced enums, unique keys) and fills declared defaults and auto_stamp fields. The type's rules (triggers, autoPopulatedFields and timestamps) do not run on loaded rows, and a load starts no database change trigger. Put those values in the rows themselves, and do any follow-up work from the code that runs the load.
  • Writes during a load made by your app land after it and win over a conflicting row.
  • What it cost. A session's timings.totals.counters gives, for each stage, the statements it ran and the rows it read and wrote, split byTarget as a batch's cost is. A load fills manifest (starting to apply), apply (the rows), reconcile (a refresh's deletions) and register (completing); primitive db3 ingests get prints them.

Check the input before loading

A bulk load changes live records and cannot be undone. Stopping the CLI's wait does not stop the load; inspect its session to see how it ended.

Indexes ​

An equality query on a field is fast when the field is indexed. Fields the type declares indexed or unique are indexed in every database of the type; register an index on one database for a field you query without declaring it.

A string set field takes a member index instead, registered with members: true (on the CLI, --set-elements; the CLI calls it a set-element index). Without one, $contains reads every record's set, which is fast for thousands of records and takes seconds for millions. With one, $contains, any-of (an $or of $contains), a membership group and an unfiltered facet on the field read the index: a $contains that matches a few records answers in milliseconds however large the database. Answers are the same with and without it.

Every index has a write cost: each write to a record also updates the indexes on its fields, on the server and on every synced device. A member index costs one stored row per member, about an eighth more storage for a set of two or three short members per record. Index only the fields you actually filter on — you can always add an index later, by marking the field indexed in the type or registering one, and existing records are indexed when you do.

A registered index lives on both sides unless you place it with on: "server" for a field only the database's own queries filter on (the record routes and server functions), "device" for one only the devices' queries filter on. Only the side that holds the index pays its write cost; a query on the other side reads every record of the model. A member index lives on the server unless you place it "device" or "both", and a local-only database keeps every index on the device.

ts
const index = await client.db3.indexes.register(db3Id, { model: "contacts", field: "email" });
// index.name === "idx_records_contacts_email"

const tags = await client.db3.indexes.register(db3Id, { model: "contacts", field: "tags", members: true });
// tags.name === "idx_members_contacts_tags", tags.members === true

// Only the database's own queries filter on `createdBy`: devices skip it.
const byCreator = await client.db3.indexes.register(db3Id, { model: "contacts", field: "createdBy", on: "server" });
// byCreator.kind === "scalar", byCreator.on === "server"

try {
  await client.db3.indexes.register(db3Id, {
    model: "contacts",
    fields: ["accountId", "email"],
    unique: true,
    name: "account_email",
  });
} catch (err) {
  if (isJsBaoApiError(err) && err.code === "DB3_INDEX_NOT_UNIQUE") {
    // Up to ten shared keys, each with how many records hold it.
    console.warn((err.body as { details?: { duplicates?: unknown[] } }).details?.duplicates);
  }
}

for (const each of await client.db3.indexes.list(db3Id)) {
  console.log(each.name, each.fields, each.unique, each.kind, each.on, each.origins);
}
await client.db3.indexes.drop(db3Id, index.name);
swift
let index = try await client.db3.indexes.register(
  db3Id, Db3IndexRegistration(model: "contacts", field: "email")
)

let tags = try await client.db3.indexes.register(

bash
primitive db3 indexes register <db3-id> --model contacts --field email
primitive db3 indexes register <db3-id> --model contacts --field tags --set-elements
primitive db3 indexes register <db3-id> --model contacts --field createdBy --on server
primitive db3 indexes list <db3-id>
primitive db3 indexes drop <db3-id> idx_records_contacts_email
  • Each index lists its kind (scalar, members for a member index, text for a text index, or vector for a vector index) and on. A declared field's index is on both.
  • To move an index, drop it and register it again: the same fields registered with another on are refused with DB3_INDEX_EXISTS, naming the index and where it lives in details.index and details.on. A field the type declares indexed or unique is indexed on both sides.
  • A unique index needs on: "server" or "both", as only the server sees every write; on: "device" is refused with DB3_INDEX_INVALID. A kind and placement no side builds is refused with DB3_INDEX_PLACEMENT_UNSUPPORTED, naming them in details.kind and details.on. On a local-only database, on: "server" or "both" is refused with DB3_LOCAL_ONLY.
  • A one-field index is named idx_records_<model>_<field>. A registered index over several fields is a unique constraint, which needs unique and a name, and is idx_named_<model>_<name>; a compound constraint the type declares is idx_uc_<model>_<constraint>. A member index is idx_members_<model>_<field>, lists with members: true, and takes no unique or name.
  • A unique index over records that already share a key is refused with DB3_INDEX_NOT_UNIQUE, naming up to ten shared keys in details.duplicates.
  • A string set field registered without members is refused with DB3_INDEX_SET_FIELD, and members: true on a field that holds single values with DB3_INDEX_NOT_SET_FIELD; both name the field in details.field. A field that already has the other kind of index is refused with DB3_INDEX_EXISTS: drop that one first.
  • Registering and dropping need the database's owner or an app admin. Dropping an index the type declares is refused with DB3_INDEX_IN_USE; change the type instead.
  • Registering or dropping answers what it cost, as cost beside the index (client.db3.indexes.register) or the name (drop): building an index writes a row for each record it covers, and a member index one for each member.
  • A member index on the server serves the database's own queries. Placed "device" or "both", each device's copy builds it too and answers $contains, any-of, membership groups and unfiltered facets on the field from it; without one, a copy answers them from the records it holds. A local-only database builds its member indexes on the device and keeps them on every write.
  • On the device that calls them, client.db3.indexes.register and drop change the copy of a database this client has subscribed before they return, so the next query uses the index. Every other device with the database open takes the change within moments, without reopening it; a device that doesn't have it open takes it at its next subscribe. At a subscribe, ready resolves once the copy holds the database's index list; a query made after available and before ready may still scan. In development, the client logs a warning for a query that scans every record of a model. With devMode: { servedIndexes: true }, the JavaScript client also logs which index served each read it answers on the device, as the read's plan names it, once per distinct read: [db3] Note.query read Note in <db3-id> through idx_records_note_year.

Indexes on each device ​

Each device builds the indexes placed "device" or "both" in its own copy, from the records it holds. A device can leave some of them out: client.db3.indexes.local lists each one with its status here, skipped lists the entries of the index list it built nothing for, and decline and accept change one on this device only. Nothing is sent, and the server and other devices keep the index.

ts
await client.db3.subscribe(db3Id).ready;

for (const index of await client.db3.indexes.local(db3Id)) {
  // "built", "building", "unbuilt" or "declined", with why when not built.
  if (index.status !== "built") console.log(index.name, index.status, index.reason);
}
// The entries this device built nothing for, with why: placed on the
// server only, or an index the device can't build.
for (const skipped of await client.db3.indexes.skipped(db3Id)) console.log(skipped.name, skipped.reason);

await client.db3.indexes.decline(db3Id, "idx_text_tasks");
try {
  await Task.query({ $search: "quarterly report" }, { db3: db3Id });
} catch (err) {
  // The index is declined here: search on the server, or accept it.
  if ((err as { code?: string }).code !== "DB3_INDEX_DECLINED_ON_DEVICE") throw err;
}

const index = await client.db3.indexes.accept(db3Id, "idx_text_tasks");
// index.status === "built"

  • Status. built, building, unbuilt or declined, with the reason when it isn't built. An index placed on the server only isn't listed. The subscription's state carries the same list in indexes, and its state event fires when a status changes.
  • Skipped. skipped lists, each with its reason, an index placed on the server only and one the device can't build: an index on id (the primary key serves it), a name that isn't an identifier, a member or vector index over more than one field, or text options it can't read. local lists none of them.
  • A build that fails. When a device can't build an index, for example because its storage is full, the copy keeps syncing without it and the index stays unbuilt: queries it would speed up read every record instead, and the client tries again at each sync.
  • Declining. decline drops the index from the copy before it returns. It stays declined across restarts, an evict, and the index being dropped and registered again, until accept or client.db3.delete. A $search that needs a declined text index, or a $near a declined vector index, is refused with DB3_INDEX_DECLINED_ON_DEVICE, naming the model and index in details.model and details.index; any other query only reads every record. accept builds the index again before it returns, and answers unbuilt with the reason when the build fails.
  • A device that builds fewer. The client's deviceIndexes option says which indexes a device builds when it hasn't already: "all" (the default), "none", or a list of kinds such as ["scalar", "members"] (.all, .none or .kinds([...]) in Swift). The ones it leaves out list as declined, and accept builds one anyway. An index a device already built stays built.
  • decline and accept refuse a name the database places on no device with DB3_INDEX_NOT_FOUND. A local-only database builds all of its indexes and refuses both with DB3_LOCAL_ONLY: drop the index instead.

Text search ​

A text index finds records by the words in their string fields, ranked by how well they match. Register one per model over the fields to search. Then filter with $search, and each record comes back with its _score (higher is a better match), the best first.

The index lives where you place it, like any other: "both" (the default) answers $search on each device that holds the database and in the database's own queries (the record routes and server functions); "device" on devices only, "server" on the server only. The server builds its copy from the model's records when you register it, and each device builds one from the records it holds; both keep it on every write. Given the same records, the server and a device answer the same matches in the same order with the same _score.

ts
await client.db3.indexes.register(db3Id, {
  model: "tasks",
  fields: ["title", "category"],
  kind: "text",
  on: "both",
  text: { weights: { title: 2 } },
});

// On the device, over the copy it holds.
const page = await Task.query({ $search: "quarterly report" }, { db3: db3Id });
for (const task of page.data) console.log(task.title, task._score);

// On the server, over every record.
const found = await client.db3.records(db3Id).query("tasks", { filter: { $search: "quarterly report" }, limit: 20 });
for (const row of found.items) console.log(row.title, row._score);

// A phrase, any of the words, and the title alone.
await Task.query({ $search: '"quarterly report"' }, { db3: db3Id });
await Task.query({ $search: { query: "report review", mode: "any", fields: ["title"] } }, { db3: db3Id });

// The start of a word: "repo" finds "report".
const started = await Task.query({ $search: { query: "repo", prefix: true } }, { db3: db3Id, sort: { _score: -1 } });

bash
primitive db3 indexes register <db3-id> --model tasks --field title --field category --kind text --weight title=2
primitive db3 records query <db3-id> tasks --filter '{"$search":"quarterly report"}' --limit 20
  • The search. $search takes the words to find, or { query, mode, prefix, fields }. Every word must match (mode: "all", the default) or any one ("any"); prefix: true matches each word as the start of a word; fields searches only some of the index's fields. A double-quoted run is a phrase, matched as adjacent words. Every other character is part of a word, so search boxes can pass user input as it is. $search goes at the top level of the filter and combines with the rest of it by AND.
  • Order. Without a sort, records come best first, then by id; sort can name _score or any field, and cursors page through either order. count counts the matches, and an aggregate whose filter has $search aggregates them.
  • The index. fields are one or more string fields; a value that isn't a string isn't indexed. text.tokenizer is unicode61 (the default: case and diacritics fold, so cafe finds café) or porter (English stems too, so run finds running). text.weights gives a field more weight in the ranking (1 by default). text.prefix lists word-start lengths to index, such as [2, 3], for fast prefix searches on short words. A model has one text index, named idx_text_<model>; a second is refused with DB3_INDEX_EXISTS. It takes no unique or name.

Gotchas ​

  • Search where the index is. A $search on a side that holds no text index for the model is refused: QUERY_INDEX_NOT_ON_SERVER from the record routes and server functions, QUERY_INDEX_NOT_ON_DEVICE from a device. Both name the model in details.model, and the index in details.index when it lives on the other side only. Place it "both" to search from either.
  • Large models. The server builds its copy while you wait, for a model of up to 2,700,000 records. Over that, the registration is refused with DB3_INDEX_TOO_LARGE, giving the model's record count and the limit in details.rows and details.limit. Register the index before loading the records, since every write after that keeps it, or place it on: "device".
  • Browser storage. In a web app, text search needs the copy kept in the browser's origin-private file system (databaseConfig: { type: "opfs" }, which the Vue template sets up). A copy kept another way keeps syncing and answering every other query, and refuses $search with DB3_INDEX_PLACEMENT_UNSUPPORTED, naming the engine in details.engine; registering a text index on a local-only database there is refused the same way.

What a call costs ​

The server's storage bills by rows read and rows written, and each index entry a write updates is a row written. So each call the server answers for a database reports both figures for that call, which shows what an index saves a query and what it costs a write:

ts
const contacts = client.db3.records(db3Id);
const before = await contacts.count("contacts", { email: "ada@example.com" });
await client.db3.indexes.register(db3Id, { model: "contacts", field: "email" });
const after = await contacts.count("contacts", { email: "ada@example.com" });
console.log(before.cost?.rowsRead, after.cost?.rowsRead); // every contact, then a handful
  • Reads. query, count and aggregate answer cost.rowsRead, the rows read to answer them; cost.rowsWritten is 0.
  • Batches. A batch answers cost.rowsRead and cost.rowsWritten for the whole call, the bookkeeping it set off included, and cost.byTarget splits them by what was touched: records (the records, and the field and unique indexes a record's write updates with it), members (member and text indexes), log (what orders writes and remembers their requestId), bookkeeping (the database's other tables, and the statistics queries are planned from).
  • Retries. A batch retried with the same requestId answers the first answer again, except cost, which is the retry's own: what finding that answer read, and no rows written.

Server functions get the same cost from query, count, batch and batchRead. A figure is null where the server's storage keeps no counter. Measure in rows, not time: the server's clock doesn't move while it works on the database, so a timing taken there reads 0.

Every read's rows are also recorded per query shape, so you can rank your app's most expensive queries across all its callers: see Finding expensive database queries.

Explaining a read ​

To see how the server answers a read, explain it. The server runs the query, count or aggregate as the record routes would, and answers which indexes it used, which models it scanned, the plan of each statement it ran and the rows it read, instead of the records:

bash
primitive db3 records query <db3-id> contacts --filter '{"email":"ada@example.com"}' --explain

To compare a read with and without an index, force it. --index <name> reads through that field or member index, and --index none reads as if the database had no index:

bash
primitive db3 records query <db3-id> contacts --filter '{"email":"ada@example.com"}' --index idx_records_contacts_email
primitive db3 records query <db3-id> contacts --filter '{"email":"ada@example.com"}' --index none
  • What it answers. indexes lists the indexes the read used, by the names primitive db3 indexes list shows. scanned lists the models whose records it walked instead of reaching them through an index or an id range. answered is the records the page held, the count or the groups, and cost.rowsRead is the rows read. scanned describes how the read reached the records; cost.rowsRead says how many it read.
  • Forcing. Under none, a string-set read checks each record's own array instead of the member index. A field index the read neither filters, sorts nor groups on (or whose records the read never reads, as a facet counted from its member index alone), a member index the read has no $contains, any-of, membership level or unfiltered facet for, and a text index are refused with DB3_INDEX_CANNOT_SERVE; details.reason says why. The force applies to that one call.
  • Who can explain. The database's owner, or an app owner or admin. A server function of the app calls ctx.api.db3.records.explain({ db3Id, model, body: { op: "query", filter, index } }); op is query, count or aggregate, and count and aggregate take --explain and --index in the CLI too.

To see which index served a read on the device, start the client with devMode: { servedIndexes: true } while developing. It logs each distinct read once, at info:

ts
const client = await initializeClient({ ...options, devMode: { servedIndexes: true } });
// [db3] Note.query read Note in <db3Id> through idx_records_note_year

Watch out when explaining:

  • An explain runs the read. --index none can read every record of the model, and is billed for the rows it reads: an id filter or a page limit can stop it sooner, so check cost.rowsRead for what it read. Compare on a model of the size you are tuning rather than in a loop. Explained reads are left out of the query-cost ranking.
  • A $search needs its text index, so --index none refuses it with reason: "search". Force a search onto a field index to compare.

Inspecting and fixing records from the CLI ​

To look into a database or correct its data by hand, use the CLI. It works with your admin login on any database, synced or not, without a copy on your machine:

bash
primitive db3 records query <db3-id> tasks --filter '{"completed":false}' --sort '{"priority":-1}' --limit 50
primitive db3 records count <db3-id> tasks --filter '{"completed":false}'
primitive db3 records patch <db3-id> tasks <record-id> --data '{"completed":true}'

App code reads and writes records on a device or in a server function, as above. See Managing Databases for every primitive db3 command.

Gotchas ​

  • A read on a device needs the database resident. Naming a database the device doesn't hold is refused with DB3_NOT_RESIDENT; wait for the subscription's available first.
  • Index the fields you filter on. A query on an unindexed field reads every record of the model — fine for hundreds, slow for hundreds of thousands. Its cost.rowsRead shows it.
  • Register a member index before a large load. Registering one builds it from the existing records in that one request, which holds for about 1,000,000 records. On a larger database the registration can run out of time and is refused, leaving no index; register the field first and load after, and each write keeps the index.
  • Retry server-side writes with the same requestId. A function call that times out may have applied; resending it with the same requestId (a ULID you generate) applies it once.
