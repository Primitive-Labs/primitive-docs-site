Interface: FunctionContext ​

ctx, the second argument every function handler and authorize receives: who and what triggered this run, and every platform capability a grant can open — ctx.api, ctx.db3, ctx.documents, ctx.locks, ctx.agents and the rest.

agents ​

agents: object

Agent sessions (project agents), on the header's subject rule: each call acts for userId, else the invoking user, and from any kind of run — a run with no caller must name the member.

createSession creates a session that member owns and answers { sessionId }. Variables failing the agent's inputSchema reject with AGENT_SESSION_VARIABLES_INVALID and details.errors. Once a tree has pushed, a key that is not an agent, and variables the agent's schema refuses, are compile errors. participants and viewers name initial members.

getSession and listSessions read the member's sessions — the ones they own or are a member of — as that member, with no admin arm whoever invoked the function: a session they are not in answers AGENT_SESSION_NOT_FOUND, and function code never sees a session's object, turnContexts or lastTurn.

deleteSession deletes a session the member owns, with the same outcome as the owner's delete from a client: the session, its document and every member's listing go, and a repeat answers the same. A session whose document is already gone can still be deleted. A participant or viewer is refused AGENT_SESSION_OWNER_ONLY, anyone else AGENT_SESSION_NOT_FOUND, with no admin arm. A userId that is present but not a string (null, a number) is refused SUBJECT_USER_INVALID, never read as the invoking user. Renaming and changing members are the owner's, from a client.

recordEvent records an event as the member, who must be the session's owner or a participant (AGENT_SESSION_PARTICIPANT_ONLY for a viewer); the row is authored app. The kind must be one the agent declares (AGENT_EVENT_KIND_UNKNOWN) and the data must match its schema (AGENT_EVENT_INVALID). An event never starts a turn; the model reads it in a later turn.

functions ​

functions: object

Start another function as a TASK run from inside this one.

The one nested door, and it is a START: code that wants a result composes by IMPORTING the other function, so there is no synchronous nested invocation to reach for.

The callee's access gate is not consulted — this function's own gate was the authorization — and every run in the tree is keyed by whoever started it, so the member who invoked the root polls and terminates them all. Nesting is bounded at four levels.

locks ​

locks: object

Named locks that WAIT. ctx.api.locks.tryAcquire is one attempt; these wait for the key, up to timeoutMs (at most one hour).

The owner defaults to ctx.runId, so a run never waits on its own hold: a resumed slice, or a second call on a key the run already holds, re-takes it at once with a fresh handle.

Under the TASK runtime the wait is durable: each attempt is a step that asks the platform to wait server-side for up to 30 s, so a wait costs one platform call and one acquire slot per half-minute, no CPU, and the slice's budget is refreshed at every attempt. It is not a suspension — the engine does not hibernate a wait shorter than five minutes. Under the REQUEST runtime the whole wait must fit the invocation's remaining budget, or the call fails FUNCTION_RUNTIME_REFUSED before any attempt (a webhook delivery has 5 s): hand longer waits to a task with ctx.functions.start.

prompts ​

prompts: object

Run one of the app's prompts, with nothing to declare.

The calling function's authorize is the authorization: it decided who may invoke the function, and so who may run the prompt, which carries no rule of its own. The provider request is bounded by the invocation's own deadline.

TYPED BY KEY. Where prompts/<key>.toml declares an outputSchema, the platform parses the answer, validates it against that schema and hands it back as parsed, typed — so the shape is written once in TOML instead of restated as a JSON.parse at every call site. Where only the config that ran declares outputFormat = "json", parsed is present but unknown. Where neither is declared the envelope is exactly what it has always been.

A shape the declaration refuses is success: false with an errorCode (PROMPT_OUTPUT_NOT_JSON or PROMPT_OUTPUT_SCHEMA_VIOLATION) and the text still in output; a PROVIDER failure has error and no errorCode, so the two are told apart without guessing.

Once a tree has pushed, a key it does not declare is a compile error.

runId ​

runId: string

The RUN this invocation belongs to, or null.

Set under the task runtime (every slice of the run, the first and every resume) and for a webhook-fired request run, which writes a row. Null for an HTTP invoke, which writes no run row at all.

It is the deterministic OWNER a task run presents to re-take its own lease: ctx.api.locks.tryAcquire({ body: { key, ttlMs, owner: ctx.runId } }) succeeds for the run that already holds the key, with a fresh handle.

runtime ​

runtime: "request" | "task"

Which RUNTIME is hosting this code.

Beside trigger, which says which DOOR fired, and they are different questions: an HTTP call is whichever runtime the caller chose (invoke or start), a cron fire is always a task and a webhook delivery is always a request.

To REFUSE a runtime rather than branch on it, call assertRuntime("task") — at module scope to refuse it outright, or in the handler to refuse one call.

sliceId ​

sliceId: string

The SLICE of the run this code is running in, or null.

The same identifier primitive functions runs and the run-status route's slice.sliceId report. A task run is a sequence of slices: it changes when the run hibernates and wakes, which is how a handler can tell a resume from a first pass.

Null under the request runtime: a request invocation is not a slice.

tool? ​

The agent session this tool call belongs to, when an agent turn called the function as a tool (ctx.trigger.kind === "tool"); otherwise absent.

usage ​

usage: object

One member's usage in this app, read-only.

forUser answers what userId drove over a UTC, half-open window, as a quantity per meter (costliest meter first), and the bytes they own now per storage meter. No field carries a cost. The window defaults to the 30 days before now; since may be no earlier than 90 days ago (USAGE_WINDOW_TOO_OLD), and a Date is sent as its ISO string.

Naming follows the header's subject rule for a read: a run may read its own caller; a run with no caller, or one an app owner or admin invoked, may read any member; a member's run may read another member only when this function declares users:readAny; a run an agent drives reads only its initiator (SUBJECT_USER_FORBIDDEN). Someone who is not a member of this app is SUBJECT_USER_NOT_FOUND.

Beta

A typed handle over one db3, typed from the pushed db3 types (primitive.d.ts):

ts
const orders = ctx.db3(input.db3Id, "orders").model("Order");
